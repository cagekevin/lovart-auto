三条各自两格：

1. **Proof**：把 `readFilesAsDataUrls` 改成 `throw new Error('x')`，再点「+」——现在界面无任何提示。**净效果**：删（补一层 catch）− 0 新增机制 = 正；本条只是让既有失败可见，不加概念。
2. **Proof**：删掉 `|| result.error || ''` 后跑一条 `reason:'storage'` 且带 `detail` 的路径，文案不变；只有"生产者漏字段"才会显示 `undefined`——那正是该暴露的。**净效果**：−1 种失败形态，不加机制 = 正。
3. **Proof**：把 `window.Library` 的 `invoke` 删掉改调 `window.Presets.…` 里的实现，`node --check` 仍过、行为不变。**净效果**：抽出 `ui/tauri.js` = −1 份重复 + 1 个文件/1 次 import ⇒ **接近零**；而 plan 20 明写「不新造第三个模块」。⇒ **不删，先裁定**（见 §三）。

**终态检查**：三条都不持有写入、回调或资源；选择器的 `event.target.value = ''` 已在读之前清空，重复选同一文件仍会触发 change（否则"再选一次同样的图"会静默失效）。

**生命周期四问**（仅第 1 条涉及状态）：`pendingRefSaves` 由 `addRefs` 写、`publish` 读；素材库这条链路**不加入**它（`send_to_library` 直接落盘，不经过编辑区），所以不会出现"发布前还在写的图"。

## 三、结论

- **已收口（本轮同批）**：`materialize_image` 的命名判据从字符串散落收到 `engine::refs::CONTENT_DIR_NAME` 一处，`service::refs` 不再自己拼 `data/var/refs`（改调 `workbench::refs_dir_of`）；`.jpeg` 归一成 `.jpg`（否则同一张图在同目录两份）；`list_inbox` 抽出 `list_inbox_core` 并补了组合行为用例（过滤 + 排序 + 目录不存在给空），探针证明会红；**TD-04-3 当场收口**（见下）。
- **TD-04-3 为什么没按债留着**：那一份重复是本轮**新写**的（`ui/library.js`），ADR-0001 明写「半收口当场修完，不许拆成两次」，登记债只适用于**既有**代码（AGENTS 6.2）。收口方式：`ui/tauri.js` 持有唯一的 `invoke`（失败折成 `{ok:false, reason:'storage', detail}`），`presets.js` / `library.js` 各留一行转调。`scan.mjs` 复查：该重复对已不在清单里。
  - 与 plan 20「不新造第三个模块」的关系：那句话约束的是**素材库的渲染/命令分工**（网格仍只在 `app.js`、命令代理仍只有 `library.js`）；这条 12 行包装不是素材库的模块，它是消除两个可抄样本的最小件。按 AGENTS §3「判据赢」（ADR 是判据层，plan 是一次性行为层），ADR-0001 #1 优先。
- **未收口**：第 1、2 条（`refPicker` / `presetRefPicker` 缺 catch；`presetMessage` 三种失败形态）—— 属既有代码，按 AGENTS 6.2「先登记债，继续手上的活」入账，未动。
- **判非债**：`app.js` 仍用裸 `invoke` + 各调用点 `try/catch`，与 `Tauri.invoke` 并存 —— 两者对应的契约不同：`Presets` / `Library` 命令的失败是**判别位形状**（`{ok:false, reason}`），代理只负责折叠一次；`app.js` 的那些命令（`get_state` / `publish_queue` …）失败是**异常**，就地 `notice`。合并要改 20+ 个调用点且会把两类失败压成一种（ADR-0003 判据 2 反例），⇒ 不合并。
- **判非债（显示名规则的两处实现）**：`engine::refs::label_of`（Rust）与 `ui/app.js::refLabelOf`（JS）各有一份"剥 `-8 位哈希`"。这不是半收口：**两个运行时之间没有共用件**，且前端**必须**能从路径取名（拖入的图、看板历史记录里的路径只有路径，没有任何生产者能给 label）。处置：规则的真身在 `label_of`（产生文件名的模块），JS 侧是与它逐字一致的镜像，两处注释互相指向，两处用例锁同一组样例（`portrait-1a2b3c4d.png` / `a-b-1.png` / `IMG_0001.png` / 纯哈希名 4 例）。
- **同轮收口（用户裁定「B 改、C 去掉」）**：
  - B：`preset_label_of` 从 `gui.rs` 搬成 `engine::refs::label_of`（文件名是该模块造的，显示名跟着走）；`refLabelOf` 补"剥 8 位哈希"⇒ 素材库点图与预设取用的芯片名从 `photo-1a2b3c4d` 变 `photo`。**行为变化**（两条取用路径的显示名），落盘名不变。
  - C：删掉 `addLibraryImages` 末尾的"已放入 N 张，M 张没进"汇总条 —— 逐条失败已由 `sendToLibrary` 报过，同一失败只说一次（ADR-0003）。
  - **输入粒度（同日第三轮裁定，写清免得下轮又"优化"）**：素材库弹窗「＋」**保留多选**（用户：「先加回来吧，我先看看好不好用，不好用再删」）；但发送仍是**逐张** —— 失败各自 `notice`、成功不播报、**不做汇总也不计数**。判据：多选是"一次挑几张"，不是"一个批量作业"；给它配进度或汇总，等于替每张图做总结（ADR-0003 一次法则 + ADR-0010 ②）。本轮的教训：**"部分失败怎么报"这个问题，是因为我先加了"批量"这个前提**；前提一撤，问题不存在，不需要在提示层打补丁。
- 裁定项（不在账本里，等一句话）：`is_plain_name` 守卫留不留 · `#maskLibrary` 用 `dialog-mid` 还是改回 plan 写的 `dialog-wide` · `list_inbox` 认不认 `.JSONL`（已生效）· **ADR-0001 #5 与 AGENTS §1 的冲突**（ADR 要求"每条改好了都有会红的检查"，AGENTS 写"改 `ui/` 的闸就 `node --check` 一条"；本轮前端改动仍只有手工 H1–H10）。
