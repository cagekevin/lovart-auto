# 写 plan 的方法：先做删除测试

> 用途：约束"写 plan 之前怎么想"，与具体功能无关。
> 触发语：**「减一遍」**、**「删除测试」**、**「只做掉了就没的那个」**、**「按 docs/写plan的方法-删除测试.md 写 plan」**。

## 1. 一句话

逐个要素问："把它去掉，需求还在吗？"
需求消失的那一个 = 第一性问题，只先解决它；其余不是不重要，是排在后面。

## 2. 三个动作，顺序不能换

### ① 删除测试（定"必要"）

全部列出来，不管多"炫"；每次只假设删掉一个：

| 判断 | 处理 |
|---|---|
| 去掉后**需求消失** | 第一性问题，本轮必做 |
| 去掉后需求仍在 | 不必要：表达方式 / 循环参数 / 内容来源 / 工程化 |
| 说不清去掉后会怎样 | 没想清楚，不许写进 plan |

依据只能是"需求是否消失"，不是"我觉得它重要"。

拿不准就套四象。它只处置"去掉需求仍在"的项，不给第一性问题打分：

| 象限 | 处置 |
|---|---|
| 高价值 · 低成本 | 先做 |
| 高价值 · 高成本 | 简化了再做，重的写进"之后" |
| 低价值 · 低成本 | 本轮不碰，也别为它加字段 / 参数 |
| 低价值 · 高成本 | 直接砍 |

原型里"炫"的功能多在下面两格——是给自己看的。

### ② 第一性（定"最小切片"）

最快能跑通的一小片：一次调用、一个函数、一处接入点。
这一片跑通即算需求满足（可以没界面、没配置）。

### ③ 排序（定"先后"，不是"取舍"）

```
第一性：核心能力（一次调用即可）
  └─ 紧邻：循环 / 复制 / 接入已有入口
       └─ 之后：内容来源（人工、外部生成、内置生成）
            └─ 之后：工程化（命令行、预览、去重、统计、提示）
```

排队 ≠ 否定。别写成"不重要"，也别混进第一版。

## 3. plan 的输出结构（照这个写）

1. **第一性问题**：一句话 + "去掉它需求就消失"的理由
2. **最小切片**：改哪一处、加什么、怎么算过
3. **紧邻的一步**：通常是循环 / 复制 / 接入已有入口
4. **之后**：每条一句说明为什么可以等
5. **不做**：四象落"低价值·高成本"的砍；落"低价值·低成本"的写明"留着，本轮不碰"
6. **验收**：跑什么、看什么、点哪几步

顺序不能倒：
**第一性问题 → 形状 → 职责（谁拥有判定）→ 数据链（谁产生 → 怎么变形 → 谁消费）→ 验收。**
先有第一性再谈形状，否则会为一个还不存在的机制设计字段。

## 4. 反模式

| 反模式 | 表现 | 后果 |
|---|---|---|
| 完整性代替必要性 | 把"以后可能用到"的能力一起设计 | 核心被淹没 |
| 把顺序讲成机制 | 把"以后做"写进第一版形状与数据链 | 形状被污染，改不动 |
| 一次给三层 | 表达方式 / 内容 / 产品化混在一段 | 分不清现在做什么 |
| 先扩后收 | 先加入口，后想删旧入口 | 两套并存，永久维护 |
| 把"能想到"当"必须做" | 用边缘情况充严谨 | 看起来完备，无法开工 |

## 5. 自检（动代码之前）

- [ ] 第一性问题一句话说得完，且"去掉就消失"成立（不是"我觉得重要"）？
- [ ] 最小切片只有一处接入点，跑通即算满足？
- [ ] 后面的层次都写成"之后"，没混进第一版？
- [ ] 没有为"完整"新增字段 / 参数 / 入口（含借"低成本"混进来的）？
- [ ] 被替代的旧实现同批删除？
