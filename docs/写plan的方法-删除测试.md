# 写 plan 的方法：先做删除测试

> 用途：约束"写 plan 之前怎么想"，与具体功能无关。
> 触发语：**「减一遍」**、**「删除测试」**、**「只做掉了就没的那个」**、**「按 docs/写plan的方法-删除测试.md 写 plan」**。

---

## 1. 一句话

**逐个要素问："把它去掉，需求还在吗？"**
需求消失的那一个 = 第一性问题，**只先解决它**；其余不是不重要，是**排在后面**。

---

## 2. 三个动作，顺序不能换

### ① 删除测试（定"必要"）

把需求拆成若干要素，**每次只假设删掉一个**：

| 判断 | 处理 |
|---|---|
| 去掉后**需求消失** | 第一性问题 —— 本轮必须解决 |
| 去掉后需求仍在 | 不是必要项：要么是表达方式，要么是循环/参数，要么是内容来源，要么是工程化 |
| 说不清去掉后会怎样 | 说明还没想清楚，不许写进 plan |

判断依据只能是"需求是否消失"，**不能是"我觉得它重要"**。

### ② 第一性（定"最小切片"）

第一性问题要用**最快能跑通的一小片**做出来：一次调用、一个函数、一处接入点。
判定标准：**这一片跑通，需求就算被满足**（哪怕只有一条、没有界面、没有配置）。

### ③ 排序（定"先后"，不是"取舍"）

剩下的按依赖顺序排队，并**明说它们属于下一层**：

```
第一性：核心能力（一次调用即可）
  └─ 紧邻：循环 / 复制 / 接入已有入口
       └─ 之后：内容来源（人工、外部生成、内置生成）
            └─ 之后：工程化（命令行、预览、去重、统计、提示）
```

⚠️ 排队 ≠ 否定。不要把"以后做"写成"不重要"，也不要把它混进第一版。

---

## 3. plan 的输出结构（照这个写）

1. **第一性问题**：一句话 + "去掉它需求就消失"的理由
2. **最小切片**：改哪一处、加什么、验收怎么算过
3. **紧邻的一步**：通常是"循环 / 复制 / 接入已有入口"
4. **之后（明确列出，明确不做）**：每条一句话说明为什么可以等
5. **不做**：本轮的排除项 + 理由
6. **验收**：能贴证据的检查（跑什么、看什么、点哪几步）

配套关系（顺序不能倒）：
**第一性问题 → 形状（数据是什么）→ 职责（谁拥有判定）→ 数据链（谁产生 → 怎么变形 → 谁消费）→ 验收。**

先有第一性，再谈形状；否则会为一个还不存在的机制设计字段。

---

## 4. 反模式

| 反模式 | 表现 | 后果 |
|---|---|---|
| **完整性思维代替必要性思维** | 把"以后可能需要的各种能力"都当成机制的一部分一起设计 | 核心被淹没；简单的事显得复杂 |
| **把顺序问题讲成机制问题** | 把"以后要做的事"写进第一版形状与数据链 | 形状被未来需求污染，改不动 |
| **一次给三层** | 同一段里混着"表达方式 / 内容 / 产品化" | 读者分不清哪个是现在要做的 |
| **先扩后收** | 先加入口、后想删旧入口 | 两套并存，永久维护两份 |
| **把"能想到"当"必须做"** | 列举所有边缘情况充当严谨 | 看起来完备，实际无法开工 |

---

## 5. 自检（写完 plan、动代码之前）

- [ ] 第一性问题是否**一句话**说得完？
- [ ] 它的"去掉就消失"理由是否成立（不是"我觉得重要"）？
- [ ] 最小切片是否**只有一处接入点**、跑通即算满足？
- [ ] 后面的层次是否**明确写成"之后"**，没有混进第一版？
- [ ] 有没有为了"完整"而新增的字段 / 参数 / 入口？
- [ ] 被替代的旧实现是否**同批删除**？

全部打勾才动代码。
