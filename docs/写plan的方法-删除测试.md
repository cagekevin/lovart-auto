# 写 plan 的方法：先做删除测试

> 用途：约束"写 plan 之前怎么想"，与具体功能无关。
> 触发语：**「减一遍」**、**「删除测试」**、**「只做删掉了就没的那个」**、**「按 docs/写plan的方法-删除测试.md 写 plan」**。

## 1. 一句话

逐个要素问："把它去掉，需求还在吗？"
需求消失的 = 第一性问题，先解决它；其余不是不重要，是排在后面。

**可能有多个第一性。** 如果两项各自删掉都会让需求消失，它们都是第一性，全都要，
最小切片必须同时覆盖——不许硬挑一个、把另一个错判成"不必要"。

## 2. 三个动作，顺序不能换

### ① 删除测试（定"必要"）

全部列出来，不管多"炫"；每次只假设删掉一个：

| 判断 | 定性 | 处理 |
|---|---|---|
| 去掉后**需求消失** | 第一性 | 本轮必做 |
| 去掉后需求仍在 | 非第一性 | 表达方式 / 循环参数 / 内容来源 / 工程化，排到后面 |
| 说不清去掉后会怎样 | 没想清楚 | 不许写进 plan |

依据只能是"需求是否消失"，不是"我觉得它重要"。

**"非第一性"不等于"不必要"。** 它们大多要做，只是不排在第一版（见 ③）。

拿不准排期就套四象限。**它只给"非第一性"项排先后，不判断第一性，也不判断"价值"**——
纵轴是"是否支撑第一性"，不是"我觉得它好不好"：

| 象限 | 处置 |
|---|---|
| 支撑第一性 · 低成本 | 先做 |
| 支撑第一性 · 高成本 | 简化了再做，重的写进"之后" |
| 不支撑第一性 · 低成本 | 本轮不碰，也别为它加字段 / 参数 |
| 不支撑第一性 · 高成本 | 直接砍 |

原型里"炫"的功能多在下两格——是给自己看的。

### ② 第一性（定"最小切片"）

最快能跑通的一小片：一次调用、一个函数、一处接入点。
这一片跑通即算需求满足（可以没界面、没配置）。

有多个第一性时，这一片要同时覆盖它们，否则跑通了也不算需求满足。

### ③ 排序（定"先后"，不是"取舍"）

```
第一性：核心能力（一次调用即可）
  └─ 紧邻：循环 / 复制 / 接入已有入口
       └─ 之后：内容来源（人工、外部生成、内置生成）
            └─ 之后：工程化（命令行、预览、去重、统计、提示）
```

排队 ≠ 否定。别写成"不重要"，也别混进第一版。

## 3. plan 的输出结构（照这个写，顺序不能倒）

1. **第一性问题**：一句话 + "去掉它需求就消失"的理由；多个就列多个
2. **最小切片**：改哪一处、加什么、怎么算过
3. **形状与数据链**：新加的东西长什么样、谁拥有判定；数据谁产生 → 怎么变形 → 谁消费
4. **紧邻的一步**：通常是循环 / 复制 / 接入已有入口
5. **之后**：每条一句说明为什么可以等
6. **不做**：四象限落"砍"的写清楚；落"留着"的写明本轮不碰
7. **验收**：跑什么、看什么、期望输出是什么

顺序不能倒：**先有第一性再谈形状**，否则会为一个还不存在的机制设计字段。
最小切片可以没有界面，验收就是"一次调用跑通 + 输出正确"，不是"点哪几步"。

## 4. 走一遍（示例）

需求原话：「给我一个命令，把一篇文章转成语音，用我的声音」

**删除测试**（每次只删一个）：

| 要素 | 删掉后 | 定性 |
|---|---|---|
| 文本输入 | 需求消失 | **第一性** |
| 音频输出 | 需求消失 | **第一性** |
| 参考音色克隆 | 需求消失（"用我的声音"没了） | **第一性** |
| 一次处理多篇 | 单篇仍成立 | 非第一性 → 紧邻 |
| 进度条 | 仍成立 | 非第一性 → 之后 |
| 落盘到指定目录 | 用户没提 | **不做**（见第 6 节第 1 条） |

**结论**：三个第一性，最小切片必须同时覆盖——
一次调用，输入文本 + 参考音色，输出一个 wav。跑通即算需求满足。

**不写进第一版**：批量、进度条、目录参数、配置界面。
**不写**：落盘策略、重启恢复、数量上限——用户没说。

## 5. 反模式

| 反模式 | 表现 | 后果 |
|---|---|---|
| 完整性代替必要性 | 把"以后可能用到"的能力一起设计 | 核心被淹没 |
| 把顺序讲成机制 | 把"以后做"写进第一版形状与数据链 | 形状被污染，改不动 |
| 一次给三层 | 表达方式 / 内容 / 产品化混在一段 | 分不清现在做什么 |
| 先扩后收 | 先加入口，后想删旧入口 | 两套并存，永久维护 |
| 把"能想到"当"必须做" | 用边缘情况充严谨 | 看起来完备，无法开工 |
| **臆想需求** | 用户没提的（持久化、重启恢复、数量上限、提示语、提前校验）被写进 plan | 白做一遍，还要返工 |
| **重写代替复用** | 已有认证 / 解析 / 队列 / 发布不查，自己再写一套 | 两份实现，必然漂移 |

## 6. 自检（动代码之前）

- [ ] 第一性问题一句话说得完，且"去掉就消失"成立（不是"我觉得重要"）？
- [ ] **多个第一性都列出来了**，最小切片同时覆盖它们？
- [ ] 最小切片只有一处接入点，跑通即算满足？
- [ ] 后面的层次都写成"之后"，没混进第一版？
- [ ] 没有为"完整"新增字段 / 参数 / 入口（含借"低成本"混进来的）？
- [ ] **每条新增都能指回一句用户原话**？指不回的删掉。
- [ ] **每项先问过"现有哪段能直接用"**？有现成的就复用，没有证据才新写。
- [ ] 被替代的旧实现同批删除？

全部打勾才动代码。

## 7. 四条硬规矩（2026-11-21）

1. **需求只来自用户原话。**
   用户没说的（落盘持久化、重启恢复、数量上限、提示语、提前校验、"顺手优化"）一律不做；
   要加，先让用户把这句话说出口，再写进 plan。

   *与第 3 条的关系*：不做落盘，就没有原子写问题；一旦决定要做落盘，原子写是必须。

2. **复用优先，能改就不新写。**
   动手前先列「现有哪段能直接用」：认证、body 解析、队列渲染、发布流程……
   列不出来才新写；每个新写项都要能通过删除测试（删了哪句需求就不成立）。

3. **限制必须先汇报，不许自己加；但「正确性」除外。**
   凡是「只能…」「最多…个」「仅本机…」「必须先…」「不许…」这类**限制**，只要不是用户原话，
   就**先摆给用户看、得到同意才写进 plan**；没同意的一律不写。
   常见的自加限制：一次最多 N 个 / 本机其他程序不许连 / 某类输入直接拒收 /
   超时自动清理 / 分批 / 提前校验 / 限制可选参数。

   **例外：正确性要求。** 判据是「**不做就会出错、丢数据、或者界面说谎**」——
   这类约束不是"限制"，是正确性，**直接做**，汇报时标明「这是正确性要求，必须这样做」。

   | 类别 | 判据 | 处理 | 例子 |
   |---|---|---|---|
   | **正确性** | 不做 ⇒ 出错 / 丢数据 / 说谎 | 直接做，汇报时标注 | 未知模型必须报错（否则整批悄悄跑成默认模型）、落盘要原子写、失败必须上报不许静默、体积上限防 OOM、路径不许越根 |
   | **偏好 / 体验** | 只是"我觉得这样更好" | **先汇报，得到同意才写** | 一次最多 N 个、拒绝某类合法输入、要不要提示语、分批、挑选、自动发布、要不要落盘 |

   汇报模板（写进 plan 前先填这张表）：

   | 限制 | 类别 | 我为什么想加 | 不加会怎样 | 用户裁定 |
   |---|---|---|---|---|
   | 例：一次最多 10 个 | 偏好 | 怕内存爆 / 怕刷屏 | 会无限堆积 | 待定 |
   | 例：未知模型直接 400 | 正确性 | 会被静默换成默认模型 | 整批跑错还不报错 | 已定（直接做） |

   **分不清是不是限制时，按限制算**（宁可多问一句）；分不清是不是正确性时，
   也按"不是正确性"算（先问）。

4. **复杂度不许推给调用方。**
   每加一条对外契约（要带什么头、要读什么文件、要转什么格式、要知道哪个字段名），
   成本都落在**调用方**身上。所以设计时问的是「**对方还要多做哪一步？**」，
   而不是「我这边多写几行」。

   能替对方做的就替：路径替它转、缺省替它填、失败替它说人话。
   对方最终只需要"发个 JSON、看得懂状态码"。

   这条与第 3 条配套：限制是"不许怎样"（二手判断），
   契约里的每一步都是"要怎样"——后者必须**从对方视角**写，不是从我视角。
