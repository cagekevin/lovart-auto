# 常驻调度器与常驻工作台 · 施工契约（State 1 契约 / State 2 数据流 / State 3 施工步骤）

> 状态：**规划中**（2026-11-07 立项，未开工）。
> 需求来源：编辑框升级三条（粘贴图片 / 发送后保留 / 运行中追加）。
> 本文是唯一规范：术语、不变量、命令表、语义、施工顺序、验收判据都以这里为准。
> 行号按 2026-11-07 版本；施工后以函数名为准。

---

## 0. 需求复述

1. 编辑框支持**粘贴图片**（截图直接进垫图），下游走 `data:` → CDN 的既有链路。
2. 发送后**编辑框的文字与图片保留**，只有人点删除才消失。
3. **运行中也能加任务**，进队列排队。

第 3 条不是加一个按钮：现状是「一次发布 = 一个批次 = 一个 `run_scheduler` 调用 = 一组 worker 线程，队列空即全部退出」（`scheduler.rs:1757-1776`）。要支持随时加，必须换掉这个生命周期模型。

### 0.1 为什么不用「追加区」小改（方案 A）

A 的形态是：`RunningBatch` 里塞一个 `Arc<Mutex<Vec<PromptTask>>>`，worker 遇 `Empty` 先 drain 再等，新增 `append_queue` 命令。它能在 1 天内跑通，但留下三条结构性债：

1. **两套入口**：`publish_queue`（起批）与 `append_queue`（追加）并存，往后每个「运行中做事」的需求都要再补一条。
2. **两个结束判据**：`queue` 空 + 追加区空 + 宽限期过，且 `Batch::Declared` / `Batch::Records` 各有一套建队逻辑（`scheduler.rs:1528-1650`）。结束早晚会再次漂移。
3. **口径四处打补丁**：`RunningBatch.ids`（进度条判据）、`current_ids`（报告过滤，`scheduler.rs:1724`）、`SchedulerSummary.total`、`finish_batch` 唯一出口。

结论：A 的补丁全部是「因为保留了批次」才需要的。**批次不该是执行单元，只该是统计单元。**

### 0.2 本期明确不做

- 不做「暂停 / 恢复」（停止已覆盖；常驻空闲不耗资源，加了就是第二种停止）。
- 不做多进程并行（CLI 与 GUI 同时跑，用文件锁拒绝第二个）。
- 不改任务 id 契约（`sha1(prompt)` 前 12 位，`prompt.rs:524-534`）。
- 不引入 async runtime（维持 std 线程 + `Condvar`）。
- 不做队列持久化的第二真相（`state.jsonl` 仍是唯一真相）。

# State 1 · 契约

## 1.1 术语

| 术语 | 定义 | 存在形式 |
|---|---|---|
| **Scheduler** | 进程内常驻调度器：worker 池 + 提交闸门 + 唯一的状态文件写者 | `Arc<Shared>`，由 `GuiState` 持有 |
| **Intake** | 把一批任务交给 Scheduler 的**唯一**入口 | `intake::enqueue(state, tasks, source)` |
| **Session** | 一次统计窗口：调度器从「空闲」被投喂 → 再次空闲 | `SessionRecord`（内存 + `run.log`） |
| **Live** | 调度器当前有活：队列非空或在飞任务 > 0 | `Scheduler::is_live()` |
| **Held** | 某条记录当前被调度器持有（在队列 / 在飞） | `Scheduler::held(id)` |
| **Parked** | 未完成但不需要调度器动作：`needs_confirm` / `unresolved` | 记录状态本身 |

## 1.2 四条不变量

| # | 不变量 | 破坏后的后果 |
|---|---|---|
| I1 | **`state.jsonl` 只有调度器一个写者**。所有删除 / 重置 / 投喂产生的写入都在调度器锁内完成 | 外部重写被在飞写回（复活 / 假删），现在靠「跑批中禁止删除」挡着 |
| I2 | **投喂只有一个入口** `intake::enqueue`。发布、追加、重跑、接着查、确认，全部走它 | 两条线，参数变更检测 / 去重 / 参考图上传各写一份 |
| I3 | **会话结束只有一个判据**：队列空且无在飞任务（`Parked` 不阻塞） | 批次永不结束，或提前结束丢任务 |
| I4 | **id 契约不变**：`sha1(prompt)` 前 12 位，同批同文本 `-2` / `-3` | 已有 `state.jsonl` 全部失效，断点续跑归零 |

## 1.3 语义重定义（旧 → 新）

### 1.3.1 「发布」→「投喂」

| | 旧 | 新 |
|---|---|---|
| 动作 | `publish_queue` 写 `var/queue.jsonl` → `start_run` 解析文件 → 起批 | GUI 直接构造 `Vec<PromptTask>` → `intake::enqueue` |
| 失败面 | 文件解析失败整批拒绝开跑 | 逐条校验，**逐条回报**（哪条、为什么），通过的就入队 |
| 按钮 | 「发布任务」→ 确认弹窗「提交后这 N 条会出现在左侧处理中」 | 「提交任务」；确认弹窗保留，文案改为「进入调度器后立即排队」 |

CLI 不变：`--prompts <file>` 仍解析文件，内部同样走 `intake::enqueue`。**文件只是 CLI 的输入形式，不是调度器的第二真相。**

### 1.3.2 「批次」→「会话」

| | 旧 | 新 |
|---|---|---|
| 是什么 | 执行单元，结束 = worker 全部退出 | **统计窗口**，只用于日志标记、报告、进度条分组 |
| 何时开始 | 用户点发布 | 调度器处于空闲时，第一次投喂到达 |
| 何时结束 | `take_job` 返回 `Empty` | 队列空且无在飞任务；**封口后新投喂属新会话** |
| 标识 | `label`（文件名 / `派工 N 条`） | `sessionId = 本地时间 %Y%m%d-%H%M%S` |

`Batch::Declared / Batch::Records` 退役为 `IntakeSource::Declared / Records`，只影响「参数以谁为准」这一件事，不再影响生命周期。

### 1.3.3 「运行中」→「live」

| | 旧 | 新 |
|---|---|---|
| 判据 | `board.batch().is_some()` | `Scheduler::is_live()`：队列非空或在飞 > 0 |
| 为什么不能只看「有非终态记录」 | 旧注释已经踩过：`state.jsonl` 里有没人跟的 `running` 记录会画一条永不结束的进度条（`gui.rs:46-57`） | 接管的判定改为 **Held**：只有调度器真正持有才画进度条；`Parked` 不画 |
| `needs_confirm` / `unresolved` | 批次结束但记录留在未完成 | **Parked**：不阻塞会话结束、不算 live、不画转圈进度条（画成「等你处理」） |

### 1.3.4 「停止」→「停止本会话」

| | 旧 | 新 |
|---|---|---|
| 作用域 | 整个批次（`cancelled` 标志） | 当前会话：不再取新活 + 在飞任务协作式中断 |
| 记录处置 | 保留，可重跑 | **不变**：保留，可重跑 |
| 在飞任务归宿 | 中断后停在 `pending` / `running`，下次靠续跑接管 | **同左**，但**不入队**（`stopped` 时 `requeue` 只改状态），否则会把已清空的队列又填满（09 §1.5.7） |
| 标志语义 | 一个 `cancelled`，置位后调度器即死 | 三层分离：`stopped`（会话级，**可复位**）/ `shutdown`（进程级，永不复位）/ `deps.cancelled`（协议层），详见 09 §1.2.2 |
| worker 生命周期 | 随批次退出 | **不退出**，转 `Condvar` 等待；`enqueue` 自动复位 `stopped` |
| 与第 2 条需求的关系 | 停止后无法再提交（要重启批次） | 停止只是「这次会话到此为止」，编辑框照常，再提交就开新会话 |

### 1.3.5 「取消所有未完成」→ 调度器内删除

| | 旧 | 新 |
|---|---|---|
| 前置条件 | 必须先停批、等线程退出（`state.jsonl` 单写者，`docs/plan/03` §0） | **无前置条件**：命令投递给调度器，锁内执行删除 |
| 实现 | `remove_open_tasks_core` 外部打开 StateStore 重写 | `Scheduler::remove_open()`，与 worker 用同一把 `Mutex<Ctx>` |
| 用户感知 | 「正在停止…」等 60 秒 | 立即生效（在飞请求照常中断，不再生成记录） |

**这是本期最大的一处收益**：`remove_tasks` / `clear_finished_tasks` / `retry_one` / `confirm_task` 全部不再需要「跑批中禁止」的闸门。

### 1.3.6 「重跑 / 接着查 / 确认」→ 投喂或唤醒

| 旧命令 | 新形态 | 去处 |
|---|---|---|
| `retry_one` | `intake::enqueue(Records)`，只重置这一条 | 保留命令名 |
| `retry_abnormal` | `intake::enqueue(Records)`，取所有可重跑记录 | 保留，语义不变 |
| `resume_one` | 投喂这一条，调度器接手续查 | 保留 |
| `resume_unfinished` | 保留，内部改走 `intake::enqueue(Records)` | 行为不变，`btnResume` 保留 |
| `confirm_task` | 投递给调度器执行（锁内） | 保留 |

### 1.3.7 断点续跑 → 仍是手动，但入口改走投喂

**行为不变（2026-11-07 拍板）**：调度器启动时**不自动接管**任何记录，用户不点就不跑。

- `resume_unfinished` 保留，点击 = `intake::enqueue(Records)`（投喂），结果与现在一致。
- `unresolved` 只能靠「接着查」处理，不会自行重跑。
- `needs_confirm` 仍由用户逐条确认。
- 差别只在内部：过去是「伪造一份单行文件 → 起批」，现在是「投喂给常驻调度器」。

### 1.3.8 参数分类

| 类别 | 键 | 生效时机 | 理由 |
|---|---|---|---|
| **运行期** | 并发、任务间隔、轮询间隔/封顶、各类超时、重试上限 | **改了就生效**（调度器每次取件读一次） | 常驻进程不能「等下一批」；用户调并发就是为了当前这批 |
| **任务期** | `LOVART_DEFAULT_MODEL` / `RATIO` / `SIZE` | **投喂时快照**，已入队的不受影响 | 同一会话内两条任务用两套默认值是灾难 |

并发立即生效的边界：只在下一轮取件生效，已在飞的 N 条不打断。

### 1.3.9 排队位置

- 严格**队尾**，不插队、不抢占。
- 同优先级内按投喂顺序（FIFO），保持 `take_job` 现有的「状态优先级 → 同优先级按 `queue` 顺序」（`scheduler.rs:658-663`）。
- 追加不影响在飞任务，不重排已有队列。

### 1.3.10 同 id 冲突 → 显式拒绝（不再静默跳过）

| 场景 | 旧行为 | 新行为 |
|---|---|---|
| 同文本已在队列 / 在飞 | `queue.push` ⇒ 同 id 重复入队、可能重复提交 | **拒绝**，回报「这条正在排队或处理中」 |
| 同文本已终态、参数相同 | `continue` 静默跳过 | **拒绝**，回报「这条已完成；要再出一张请点『重跑这一条』」 |
| 同文本已存在、参数不同 | 建队时重置重跑 | **投喂时即时判定**并重置（`scheduler.rs:1536-1577` 的逻辑搬进 intake） |

这条与需求 2 强绑定：编辑框保留文字后，用户很容易重复点提交，静默跳过就是「假成功」。

**判据是「是否被持有」（在队列 / 在飞），不是 `status`。** `stop_session` 清空队列后记录仍是 `pending`；若按状态判，这条会被误拒，用户再也投不进来。完整七级优先级见 09 §3.1。

### 1.3.11 `var/queue.jsonl` 退役

- GUI 不再写它（现状 `write_queue_file` 只在 `publish_queue` 用，`gui.rs:1089-1143`）。
- CLI 的 `--prompts` 保留，是 CLI 的输入文件，不再复用这个文件名。
- 现存 `var/queue.jsonl` 不作迁移，留作排障快照，不再被任何代码读取。

### 1.3.12 单实例锁

`state.jsonl` 一个写者 ⇒ 进程级 `var/.lock` 文件锁：

- GUI 启动拿不到锁 ⇒ 弹窗「已有进程在跑（CLI 或另一个窗口），请先退出」。
- CLI 启动拿不到锁 ⇒ 报错退出（exit code 非 0），**不静默等待**。
- 锁随进程退出释放（OS 层），不做超时抢占。

### 1.3.13 报告与日志

| 产物 | 旧 | 新 |
|---|---|---|
| `var/report.csv` | 每批覆盖 | 每**会话封口**覆盖（格式不变）；**覆盖前把旧文件归档到 `var/reports/`**（详见 09 §3.5） |
| `var/run.log` | `===== 批次开始：{label}（N 条，并发 M）=====` | `===== 会话开始：{sessionId}（N 条，并发 M）=====` / `===== 会话结束：{sessionId}（…）=====` |
| 会话内的追加 | 不可能 | `---- 会话内追加：N 条（累计 M 条）----`（同一 sessionId） |

# State 2 · 数据流

## 2.1 投喂链路（GUI / CLI 同一条）

```
[GUI] 编辑框 → addToQueue（内存队列）→ 点提交
[CLI] --prompts 文件 → parse_prompts
                    ↓
        intake::enqueue(src, tasks)
          1. 校验（模型别名 / ratio / size / refs）—— 逐条，失败逐条回报
          2. 参考图上传（data: / 本机路径 → CDN）—— 网络，锁外
          3. 去重与参数变更检测（I4 / 1.3.10）
          4. 锁内：state.create / state.update + queue.push + task_by_id.insert
          5. 唤醒 worker（Condvar.notify_all）
                    ↓
        Scheduler（常驻）→ worker 取件 → 提交 → 轮询 → 下载 → 终态写盘
```

校验必须与 `parse_prompts` 同源：`intake` 里只做「单条 PromptTask 的等价校验」，**不允许**在 GUI 侧另写一套模型别名表。

## 2.2 调度器生命周期

```
         ┌──────────┐  enqueue  ┌──────────┐  队列空 + 在飞=0  ┌──────────┐
启动 ───▶│  Idle    │──────────▶│  Live    │──────────────────▶│  Idle    │
  自动接管└──────────┘           └──────────┘  封口会话、写报告   └──────────┘
         │                            │
         └──── stop_session ──────────┘（取消标志 + 清队列，记录保留）
```

- **Idle 不退出**：worker 在 `Condvar` 上等待，不占 CPU。
- **shutdown**：窗口关闭 / CLI 跑完 → 置取消标志 + `notify_all` → join → `state.flush()`。
- `Arc::try_unwrap(shared)` 那套收尾（`scheduler.rs:1715`）删除：`Shared` 不再被回收。

## 2.3 会话边界判据（唯一实现）

```text
is_idle = queue.is_empty() && in_flight == 0
会话打开：is_idle 且收到 enqueue
会话封口：is_live 且变为 is_idle
```

`Parked`（`needs_confirm` / `unresolved`）不参与 `in_flight`，因此不阻塞封口。

## 2.4 删除 / 清空链路

```
cancel_all_tasks → Scheduler::remove_open()
                    ├─ 置取消标志（在飞任务协作式中断）
                    ├─ 锁内 state.remove(所有非终态 id)
                    └─ 清 queue / task_by_id
```

不再有「等批次线程退出」的中间态，`ClearIntent::Waiting` 分支删除。

## 2.5 UI 状态映射（`get_state`）

| 字段 | 旧来源 | 新来源 |
|---|---|---|
| `running` | `board.batch().is_some()` | `Scheduler::is_live()` |
| `following` | `RunningBatch.ids` | `Scheduler::held_ids()`（在队列 ∪ 在飞） |
| `clearing` | `Board.wipe` | 删除（无异步清空） |
| `sessionId` / `sessionLabel` | 无 | 新增，供标题行显示「本次会话 18:33 开始」 |

`Parked` 记录单独下发 `parked: true`，前端画「待处理」态而非转圈。

## 2.6 参考图上传时机

- 在 `intake` 内、锁外完成；失败的条目**单独报错、不阻塞其他条目**。
- `refs-cache.json` 继续复用（同一张图重复上传只发生一次，`run.rs:1220-1241`）。
- 追加任务同样走这条路径，**不能**因为「批次已在跑」跳过上传。

- **验收**：现有 `cargo test` 全绿 + `fixtures/` 7 个场景结果不变。

## Step 3 · Scheduler 常驻化 —— ✅ 2026-11-07 完成（含 GUI 迁移）

## 4. 风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | 自动接管在用户不知情时消耗积分 | 界面明示条数 + 设置页开关？**需用户决策**（见 §6-①） |
