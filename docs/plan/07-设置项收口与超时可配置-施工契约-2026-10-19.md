## 0. 需求复述

2. 同一批把「挂机时长」相关的另 3 项一并进设置：复查超时、失败重试上限、超时次数上限。

   直接加 8 个新键，只会把「份数」翻倍。

# State 1 · 契约

## 1.1 新增设置项（唯一权威表）

存储单位一律 **毫秒 / 次数**（与 `Duration`、既有 `LOVART_TASK_INTERVAL_MS` 同惯例）；
UI 单位一律 **分钟 / 秒 / 次**，**换算只在 `gui.rs` 一处**，前端不做任何换算。

| # | `.env` 键 | 默认值 | 边界（硬夹紧） | UI 字段（`get_settings` / `save_settings`） | UI 单位 | 位置 |
|---|---|---|---|---|---|---|
| S1 | `LOVART_TASK_TIMEOUT_MS` | `5400000`（90 分） | `60_000..=86_400_000`（1 分 ~ 24 时） | `taskTimeoutMin` | 分 | 主面板 |
| S2 | `LOVART_RECHECK_TIMEOUT_MS` | `1800000`（30 分） | 同 S1 | `recheckTimeoutMin` | 分 | 主面板 |
| S3 | `LOVART_MAX_ATTEMPTS` | `3` | `1..=20` | `maxAttempts` | 次 | 主面板 |
| S4 | `LOVART_MAX_TIMEOUTS` | `3` | `1..=10` | `maxTimeouts` | 次 | 主面板 |
| S5 | `LOVART_MAX_BUSY_RETRIES` | `300` | `1..=5000` | `maxBusyRetries` | 次 | 高级 |
| S6 | `LOVART_DOWNLOAD_RETRIES` | `3` | `1..=10` | `downloadRetries` | 次 | 高级 |
| S7 | `LOVART_POLL_INTERVAL_MS` | `10000` | `1_000..=600_000` | `pollIntervalSec` | 秒 | 高级 |
| S8 | `LOVART_POLL_MAX_INTERVAL_MS` | `60000` | `1_000..=3_600_000`，且 **≥ S7** | `pollMaxIntervalSec` | 秒 | 高级 |

**为什么 S1/S2 必须成对**：单任务墙钟上限 =
`task_timeout + recheck_timeout × max_timeouts`（默认 90 + 30×3 ≈ **3 小时**）。
只放 90 不放 30，用户把 90 调成 180 后复查仍卡 30，会以为设置没生效。

**为什么 S7/S8 也要成对**：只改起始间隔、封顶仍是 60s，等于只改了第一轮退避，
第二轮起又回到旧节奏 —— 用户无法解释"为什么只快了一下"。

## 1.2 只读提示（设置页底部一行）

```
单轮：90 分 + 复查 30 分 × 3 次 = 180 分。
超时不重新提交，也不会重复扣费。
```

后半句是**目前只存在于代码注释里的保证**（`config.rs:28-30`），
不写出来，用户不敢把超时调小。

**「单轮」这个词不能省**。按 `scheduler.rs:1278-1329` 的实际时序数：

| 段 | 用哪个超时 | `timeout_count` |
|---|---|---|
| 首次提交后轮询 | `task_timeout` | 0 → 1 |
| 第 1 次复查（`Timeout` 状态，占槽） | `recheck_timeout` | 1 → 2 |
| 第 2 次复查 | `recheck_timeout` | 2 → 3 ≥ max ⇒ `unresolved`，释放槽位 |
| 收尾 `RecheckFinal`（`run_final`） | `recheck_timeout` | **不计入**（`scheduler.rs:1282-1283` 明确） |

合计 = `task_timeout + recheck_timeout × max_timeouts`，默认 `90 + 30×3 = 180` 分。
**但 `unresolved` 会在下次运行时继续查**（`resume_unfinished`），跨运行没有上限 ——
所以文案只能承诺「单轮」，写成「最长 3 小时」就是第二句假话。

> `README.md:202` 现在写的是「默认 3 次 = 90+30+30 分钟」，**少算了一次复查**，
> 本期一并改成 `90+30×3`。

**文案里的数字和「单轮 X 分」全部由后端算好下发**（`get_settings.maxWallClockMin`），
前端只做字符串插值 —— 见 2.8。前端若自己乘加，就是第二份时间口径。

## 1.3 非法值与边界

| 场景 | 行为 |
|---|---|
| `.env` 缺键 | 用内置默认，**不告警**（正常） |
| `.env` 值非法 / 越界 | 用内置默认 + **一条告警**（进 `get_settings.warnings`，界面可见） |
| 设置页输入非法 / 越界 | **整次保存拒绝，不落盘**，返回错误文案（照 `PromptDefaults::validated` 的「先校验后写盘」） |
| 设置页输入小数（`90.5`） | 拒绝并提示「请输入整数」。**禁止用 `Value::as_u64` 静默返回 `None`** —— 那会变成「保存成功但没生效」 |
| payload 缺某个字段 | 该字段**不改**（表驱动的前提，见 2.4） |
| 写盘成功但 `reload_dot_env` 失败 | **不回滚、不返回 `Err`**，改为返回 `warnings`（见 2.5） |
| 保存成功 | `update_env_keys` 按行改，注释/空行/其它键原样保留（既有行为） |

**不允许"保存成功但没生效"**：这是 `DEBT TD-05-19` 的同型问题。

`get_settings` 新增一个字段：

```
warnings: [string]   // 每个非法键一条，不合并、不截断；正常情况下是空数组
```

**这是补齐一个既存缺口**：`gui.rs:1366` 现在是 `let (defaults, _) = PromptDefaults::from_env();`
—— 兜底参数的 warnings 被 `_` 丢掉，`.env` 手改非法在 GUI 里**完全不可见**
（只有 CLI `run.rs:892-895` 会打印）。本期的 S1~S8 若照抄这个写法，等于新增 8 个不可见的静默回退。

## 1.4 生效时机

| 动作 | 是否生效 |
|---|---|
| 点「保存」 | 写盘 + `reload_dot_env`（覆盖语义）；**下一次开始**生效 |
| **手改 `.env` 后点「开始」** | **现在不生效** —— 见下方 N1，本期必须修 |
| 正在跑的批次 | **不打断**（`start_run` 每次重新构造 `SchedulerOptions`） |
| 「接着查 / 派工 / 重试一条」 | 走同一个 `start_run`（`gui.rs:999`、`1223`）⇒ **同样生效** |
| CLI | `命令行 > .env > 内置`，一次性进程，天然生效 |
| 自动确认（唯一特例） | **热更新**：`AtomicBool`，chip 一点就对当前批次生效 |

### N1（本轮发现，会推翻「手改即生效」的承诺）

`gui.rs:534` 的 `start_run` 调的是 **`load_dot_env`**，而它是「不覆盖」语义：

```275:284:src-tauri/src/lovart/connection.rs
/// **首次载入**：不覆盖已存在的变量。
/// ⚠️ 正因如此，**它不能拿来"重载"**：已经载入过一次的键会被**整段跳过**。
pub fn load_dot_env(path: &Path) -> Result<(), String> {
    inject_dot_env(path, false)
}
```

启动时 `GuiState::new` 已经载入过一次 ⇒ 之后再调 `load_dot_env` **等于空操作**。
所以「用户手改 `.env` 的 `LOVART_TASK_TIMEOUT_MS`，点开始」实际用的是旧值，必须重启。

**裁决**：

| 入口 | 用哪个 | 理由 |
|---|---|---|
| GUI `start_run` | **改为 `reload_dot_env`** | GUI 是「以 `.env` 为权威」的形态，用户通过设置页/文本编辑改配置，期望点开始就生效 |
| CLI | **保持 `load_dot_env`** | 遵循 dotenv 标准：shell `export` / 容器变量优先，脚本行为不变 |

代价（必须写明）：GUI 里点过一次开始后，`.env` 会覆盖同名系统环境变量。
这与 `save_settings` 已经在做的事一致（它本来就 `reload_dot_env`），不是新增语义。

除自动确认外，S1~S8 / 并发 / 提交间隔 / 输出目录一律「**下一次开始生效**」。
`Ctx` 里这些是 `Duration` / `usize` 值类型，热更新要加锁改造，收益远小于成本（见 2.7）。
设置页底部必须写出这句，否则用户改完在跑批里找不到变化。

### N2（本轮发现：上一版 R1-6 的解法是假的）

如果只抽一个 `SchedulerTuning`，而两边仍写

```rust
SchedulerOptions { task_timeout: t.task_timeout, recheck_timeout: t.recheck_timeout, /* ×11 */ }
```

那 R1-6 只是把「默认值重复」换成了「**字段搬运重复**」—— 加字段照样必漏一边。
真正解法是让 options **持有** tuning：

```rust
pub struct SchedulerTuning {          // 11 个，全部实现 Default
    pub concurrency: usize,
    pub task_timeout: Duration,
    pub recheck_timeout: Duration,
    pub max_timeouts: u32,
    pub download_retries: u32,
    pub max_attempts: u32,
    pub max_busy_retries: u32,
    pub task_interval: Duration,
    pub busy_backoff_base: Duration,        // 测试缝，from_settings 不读 .env
    pub rate_limit_backoff_base: Duration,  // 测试缝，同上
}

pub struct SchedulerOptions {
    pub deps: ClientDeps,
    pub batch: Batch,
    pub state: StateStore,
    pub output_dir: PathBuf,
    pub tuning: SchedulerTuning,        // ← 11 个配置字段收成 1 个
    pub retry_failed: bool,
    pub auto_confirm: Arc<AutoConfirm>,
    pub log: LogFn,
    pub ports: Option<Arc<dyn Ports>>,
}
```

`Ctx` **保持扁平**（`run_scheduler` 里把 `tuning` 解构进去），
这样 `ctx.task_timeout` / `ctx.concurrency` 的十几处引用一行都不用改。

构造点共 **4 处**，全部只需把 11 行换成 `tuning: ...` 一行：
`run.rs:1092`（CLI 覆盖后）、`gui.rs:673`（`from_settings`）、
`tests/support/mod.rs:425`、`tests/golden_replay.rs:356`（测试用 `Default` + 改单项）。

**禁止**给 `SchedulerOptions` 提供 `Default`（`state` / `batch` / `deps` 没有合理默认值，
给了就会有人真的去 `..Default::default()` 然后跑一个空批次）。

### N7（本轮发现：`get_settings` 一半读文件一半读环境 ⇒ 一条数据丢失路径）

现状 `get_settings`：`accessKey` / `secretKey` 读**文件**（`gui.rs:1355` 的 `parse_dot_env`），
其余全部读**进程环境**（`concurrency()` / `task_interval_ms()` / `PromptDefaults::from_env()`）。

于是：

| 步 | 用户动作 | 系统状态 |
|---|---|---|
| 1 | 手改 `.env`：`LOVART_TASK_TIMEOUT_MS=7200000` | 文件=120 分，环境=90 分 |
| 2 | 打开设置页 | 显示 **90**（读环境） |
| 3 | 顺手改了下「并发」，点保存 | 整包提交，`taskTimeoutMin: 90` |
| 4 | 写盘 | **`LOVART_TASK_TIMEOUT_MS=5400000` —— 手改被覆盖** |

这是静默的数据丢失，用户不会收到任何提示。

**裁决：`get_settings` 全部读文件。** 理由是三条路必须对齐：

```
设置页显示 = 文件内容 = 点「开始」后的生效值（N1 保证 start_run reload）
```

两个入口共用同一套解析，不允许各写一份：

```rust
impl Settings {
    /// 唯一解析 + 校验 + 告警收集。不碰 I/O、不碰 env。
    fn from_pairs<'a>(pairs: impl Iterator<Item = (&'a str, &'a str)>) -> (Self, Vec<String>);

    /// 设置页 / save_settings 的「当前值」。
    pub fn from_file(path: &Path) -> (Self, Vec<String>);

    /// 运行时（start_run / CLI / to_client_deps）。
    pub fn from_env() -> (Self, Vec<String>);
}
```

`from_file` 对**同名多行采取「后者覆盖前者」**，与 `inject_dot_env` 的 `set_var` 语义一致
（`inject_dot_env` 按 entries 顺序 set，最后一个赢）。现在 `get_settings` 用 `find()` 取**第一条**，
文件里出现两行同名键时，设置页显示的值和实际运行的值就不同 —— 一并修正。

### N8（本轮发现：整包提交 + 整数分钟 ⇒ 静默改写）

`.env` 里写 `LOVART_TASK_TIMEOUT_MS=90000`（1.5 分钟，CLI 允许小数）：
`get_settings` 换算成整数分钟显示 `2` → 用户只改了「并发」→ 整包提交 → 写回 `120000`。
**1.5 分钟被静默改成 2 分钟。**

**裁决**：`save_settings` 对 S1~S8（以及并发 / 间隔 / 输出目录）增加
**「换算后与文件中当前值相同 ⇒ 不写入」**。这样未触碰的字段永远不会被整包提交改写。
实现上正好复用 N7 的 `Settings::from_file`：读一次当前值 → 与 payload 逐项比较 → 只写差异。

### N9（本轮发现：写回的值可能破坏下次解析）

`update_env_keys` 写的是 `KEY=value`，**不加引号**；
而 `parse_dot_env` 对未加引号的值执行 `raw.find(" #")` 截断（`connection.rs:72-74`）。

所以输出目录填 `my #dir` → 写成 `LOVART_OUTPUT_DIR=my #dir` → 下次解析得到 `my`。
**一次保存把路径改坏了。**

**裁决**：`update_env_keys` 在**值包含 ` #`、或首尾有空白、或包含引号**时用双引号包裹
（`parse_value` 已支持单/双引号，`connection.rs:55-68`）。这是 `update_env_keys` 的通用修正，
自动确认开关（`true`/`false`）不受影响。

## 2.4 CLI 如何区分「没指定」（R1-6 的前提）

现状的 `arg_number(&args, key, fallback)` **无法表达「用户没写这个参数」** ——
它一定返回一个数。若照搬，CLI 层就得写死一份默认值，等于把 R2 的重复又造回来。

新增（`cli.rs`，与 `arg_value` 同层）：

```rust
/// 未给出 → None；给出且可解析为有限数 → Some；给出但非法 → None + eprintln 告警。
pub fn arg_number_opt(args: &ParsedArgs, key: &str) -> Option<f64>
```

`SchedulerTuning` 的构建顺序固定：

```rust
let mut tuning = SchedulerTuning::from_settings();   // 全部来自 .env / 内置
if let Some(v) = arg_number_opt(&args, "task-timeout") { tuning.task_timeout = minutes(v); }
// … 其余 7 项同构
```

**禁止**再写 `arg_number(&args, key, 默认值)` 的形式 —— 那会把默认值搬进 CLI 层。
「非法值只告警不中断」是对既有 `arg_number` 静默兜底的修正：不阻断（保持一致），但不再无声。

| 单个键非法 / 越界 | 该键回退内置默认 | `get_settings.warnings` + 启动告警 |
| 多个键非法 | 每键一条，不合并、不截断 | 同上 |
| `get_settings` 读文件失败 | 返回 `Err` | 前端 `notice`，**面板不打开**（`app.js:1643` 既有行为） |
| 保存时任一键非法 | 整次拒绝，**不做部分保存** | 前端红字，盘不动 |
| payload 缺某键 | 该键**不改** | — |
| payload 类型不对（超时填 `90.5` / 字符串） | 拒绝并提示「请输入整数」 | 前端红字 |
| **UI 输入越界（并发填 99）** | **拒绝**，不再静默 `clamp` | 前端红字 |
| `.env` 里 `poll_max < poll_interval` | 抬到 interval + 一条告警 | `warnings` |
| `.env` 写完断电 / 崩溃 | `update_env_keys` 用 `fs::write` 直接覆盖，**非原子** | 下次启动 parse 报错 → 告警（既有风险，见 1.8-F） |
| 写盘成功、reload 失败 | 不回滚，转 `warnings` | 设置页黄字 + 提示重启 |
| `.env` 被外部同时改 | `env_lock` 串行化（既有） | — |

### N4（本轮发现：校验策略现在是两套）

同一个面板里已经并存两种容错：

| 字段 | 现有做法 | 用户感受 |
|---|---|---|
| `concurrency` | `value.clamp(1, 8)`（`gui.rs:1399`） | 填 99 → 保存成功，实际变 8 |
| `defaultModel/Ratio/Size` | `PromptDefaults::validated(...)?` | 填错 → 报错，不落盘 |

**裁决：UI 入口统一为「拒绝」**，读取入口（`.env` 手改）统一为「回退 + 告警」。
两条入口的容错级别不同是刻意的：UI 背后有人可以立刻改，文件背后没人可问。

行为变化：并发填 99 从「静默变 8」改为「报错」。这是修正，不是回归（静默夹紧就是 TD-05-19 同型）。

### N5（本轮发现：`taskIntervalSec` 必须是 `f64`）

`app.js:1656` 现在是 `Math.round(intervalSeconds * 1000)` —— **前端在做 ×1000**。
若后端仍收 `xxxMs`，这个换算无法消除，「前端零换算」就是空话。

裁决：

| 项 | 类型 | 范围 | 后端换算 |
|---|---|---|---|
| `taskIntervalSec` | `f64`，允许 1 位小数（`step="0.1"`，1.5s 有效） | `0.0..=600.0` | `(sec * 1000.0).round() as u64` |
| `taskTimeoutMin` / `recheckTimeoutMin` | 整数 `u64` | `1..=1440` | `min * 60_000` |
| `pollIntervalSec` / `pollMaxIntervalSec` | 整数 `u64` | `1..=600` / `1..=3600` | `sec * 1000` |

所以字段名统一以 **UI 单位**结尾（`Sec` / `Min`），单位换算只在 `gui.rs` 一处完成。

### N11（本轮发现：前端兜底会静默改值）

`app.js` 现在有 6 处兜底：`Number(x) || 7`、`|| 5000`、`|| 'output'`。
后果：

| 用户输入 | 前端实际发出 | 用户以为 |
|---|---|---|
| 并发 `0` | `7`（`0 \|\| 7`） | 设成了 0 |
| 清空输出目录 | `'output'`（`\|\| 'output'`） | 设成了空 / 没改 |
| 清空并发 | `7` | 没改 |

这与 N4 的「UI 一律拒绝」直接冲突 —— 前端先把非法值改成合法值，后端根本没机会报错。

**裁决**：前端**去掉全部 `||` 兜底**，空值发 `null`；后端按三态处理：

| payload 状态 | 语义 | 行为 |
|---|---|---|
| 键不存在 | 前端没渲染这一项（旧版前端） | **不改** |
| `null` / `""` | 用户清空了 | **`Err`「不能为空」** |
| 有值 | 正常 | 校验 → 写入 |

例外：`accessKey` / `secretKey` 允许空串（用户可能就是要清空凭据），且不参与"不能为空"校验。

`save_settings` 的提取器因此要区分 `Missing` 与 `Null`，
不能再写 `payload.get(k).and_then(Value::as_u64)`（两者都会被吞成 `None`）。

### N12（本轮发现：倒挂防御只在配置层不够）

`settings` 会在读取时把 `poll_max < poll_interval` 抬到 `interval`。
但 `ClientDeps` 是 `pub` 结构，测试和未来调用方都能直接构造倒挂的值。

**裁决**：`poll_thread` 里做一次防御：

```rust
let max_interval = deps.poll_max_interval.max(deps.poll_interval);
```

配置层负责「给用户一个合理的值 + 告警」，运行层负责「绝不原地死循环」。
两层都要，不冲突。

## 2.6 告警投递（补齐既存缺口）

`gui.rs:1366` 现在是 `let (defaults, _) = PromptDefaults::from_env();` ——
**warnings 被 `_` 丢掉**，所以 `.env` 里非法的兜底参数在 GUI 里完全不可见
（只有 CLI `run.rs:892-895` 打印）。本期的 S1~S8 若照抄，就是新增 8 个静默回退。

| 时机 | 通道 | 读哪个入口 |
|---|---|---|
| 启动 | `GuiState::new` 的**既有循环**（`gui.rs:246-250`，现在只处理 `PromptDefaults`） | `from_env`（此时 `load_dot_env` 刚跑完，环境≈文件） |
| 打开设置 | `get_settings.warnings: [string]` → 渲染进 `#settingsNote` | `from_file`（N7） |
| 保存后 | `save_settings` 返回 `warnings: [string]` → 替换 `#settingsNote` | `from_file` |

**不新开通道**：`GuiState::new` 里那条 `for warning in default_warnings { push_alert }`
已经存在，把 `Settings::from_env()` 的 warnings 拼进同一个 `Vec` 即可。

启动用 `from_env` 而非 `from_file`，是因为它反映的是**此刻真正生效的值**
（`load_dot_env` 已执行）。两者只有在「系统环境变量覆盖了 `.env`」时才会不同 ——
那种情况下启动告警说的是生效值、设置页说的是文件值，差异本身是有意义的，不做统一。

## 2.7 热更新边界

| 参数 | 热更新 | 说明 |
|---|---|---|
| 自动确认 | **是** | `AtomicBool`，chip 一点就对当前批次生效（既有） |
| S1~S8 / 并发 / 提交间隔 / 输出目录 | **否** | `Ctx` 里是 `Duration` / `usize` 值类型；改造要加锁，收益低于成本 |

统一「下一次开始生效」。设置页底部的说明必须写出这句（1.4）。

## 2.8 谁算「最长 3 小时」

| 数 | 谁算 | 谁用 |
|---|---|---|
| `taskTimeoutMin` / `recheckTimeoutMin` | `settings` 读 + `gui.rs` 换算 | 输入框初值 |
| `maxWallClockMin = taskTimeoutMin + recheckTimeoutMin × maxTimeouts` | **`get_settings` 里算** | 只读提示 |
| 提示文案 | 前端**纯字符串插值** | 界面 |

公式已在 N3 对照 `scheduler.rs:1278-1329` 的实际时序验证：初次轮询 1 次 + 复查 `max_timeouts-1` 次
+ 收尾 1 次 = 复查共 `max_timeouts` 次，与 `task + recheck × max` 吻合。

**语义限定**：`maxWallClockMin` 是**单轮**上限（一次 `run_scheduler` 内），
不含下次运行继续查 `unresolved`。字段名里没体现「单轮」，所以文案必须写。

前端不得出现 `* 60` / `* 1000` / `/ 1000` 之类的时间算术（06 契约 2.1 同一口径）。

### N19（看板与设置页在「手改」后会短暂不一致）

`get_state` 的产物存在性用 `state.output_dir()` → `output_dir_name()` 读**环境**；
`get_settings` 从本轮起读**文件**。手改 `LOVART_OUTPUT_DIR` 后、点「开始」之前：
设置页显示新目录，看板仍按旧目录检查产物（可能显示「产物缺失」）。

**裁决**：不特殊处理。N1 保证点「开始」后统一；设置页底部那句「直接改 .env 的话，点开始后才生效」覆盖这个窗口。
**不要**为了让 `get_state` 也读文件而每秒读一次磁盘 —— `get_state` 是 1Hz 轮询。

### N14（`maxWallClockMin` 只描述「新提交的任务」）

「接着查 / 派工」走 `Batch::Records`，状态已是 `timeout` / `unresolved`，
直接进 `run_recheck` / `run_final`，**不经过 `task_timeout`** ⇒ 单轮最多 `recheck_timeout`。

所以文案只能写「**新任务**单轮 180 分」，不能写「一条任务最多 180 分」。
字段名不变，语义在文案与 README 里限定。

### N16（「未变不写」与「非法值永久告警」互相矛盾）

`.env` 里 `LOVART_TASK_TIMEOUT_MS=abc`：`from_file` → 90 + warning。
用户只改并发 → 按 N8 比较「解析值 90 vs payload 90」相同 → 不写
⇒ 非法值永远留着，**每次打开设置都告警一遍**。

**裁决**（两条规则并存）：

| 文件里该项 | 保存时 |
|---|---|
| 合法，且与 payload 相同 | **不写**（N8） |
| **非法**（`from_file` 报了 warning） | **无条件重写为默认值**，返回 `warnings` 加一条「已修复 N 个非法值」 |

不动它 ⇒ 一次保存顺手修好，之后不再告警；主动改 ⇒ 正常写入。

### N17（只读提示不做「实时联动」）

`maxWallClockMin` 由后端算。若要求输入框一改提示就变，前端就得写
`timeout + recheck * maxTimeouts` —— 又是前端算时间（违反 06 契约 2.1）。

**裁决**：提示只在「打开设置」「保存成功」两个时刻刷新，输入过程中不变；文案不暗示实时。

### N15（改输出目录的可见后果没提示）

`outputDir` 从 `output` 改成 `output2` 后，记录里的相对路径仍指向旧图，
`filesPresent` 按新目录检查 ⇒ 看板显示「产物缺失」，图还在旧目录。

**裁决**：不阻止（合法操作），在该项下加一行提示：
`改目录后，已有任务的产物仍留在旧目录，看板会显示缺失`。
**不做**迁移/复制。
