## 1.2 核心类型

### 1.2.1 Scheduler（唯一公开面）

```rust
/// 进程内常驻调度器。`start` 之后一直活着，直到 `shutdown`。
/// 只有它能写 `state.jsonl`（不变量 I1）。
pub struct Scheduler {
    shared: Arc<Shared>,
}

impl Scheduler {
    /// 起 worker 池并进入 Idle。**不**自动接管未完成记录（现状行为）。
    pub fn start(opts: SchedulerOptions) -> Result<Self, LovartError>;

    /// 唯一投喂入口（不变量 I2）。同步返回，逐条给出接受 / 拒绝原因。
    pub fn enqueue(&self, source: IntakeSource, tasks: Vec<PromptTask>) -> IntakeReport;

    /// 有活：队列非空或在飞非空。会话封口判据（不变量 I3）。
    pub fn is_live(&self) -> bool;

    /// 当前被持有的 id（在队列 ∪ 在飞）。界面进度条的**唯一**判据。
    pub fn held_ids(&self) -> BTreeSet<String>;

    /// 会话视图：id / 开始时间 / 条数 / 是否 live。
    pub fn session(&self) -> SessionView;

    /// 停止本会话：置会话停止标志 + 清队列，**不删记录**（可重跑）。
    /// ⚠️ 停止**可复位**：下一次 `enqueue` 自动恢复（见 §3.4）。停止不等于关停调度器。
    pub fn stop_session(&self);

    /// 取消所有未完成：锁内取消 + 删非终态记录。返回删除条数。
    pub fn remove_open(&self) -> Result<usize, LovartError>;

    /// 协作式收尾：取消 → 唤醒 → join → flush。返回会话摘要。
    pub fn shutdown(self) -> Result<SessionSummary, LovartError>;
}
```

**为什么 `held_ids` 需要显式的 `processing` 集合**：`slots_in_use(&state)`（`scheduler.rs:624`）算的是并发预算，`issued` 算的是「本次派出去的活」。两者在 Parked 记录上口径不同，**不许合并**；UI 只认 `held_ids`，否则又回到「没人跟的 running 记录画一条永不结束的进度条」（`gui.rs:46-57`）。

### 1.2.2 Shared / Ctx

```rust
struct Shared {
    ctx: Mutex<Ctx>,
    log: LogFn,                     // 契约：回调内**禁止**锁 ctx（scheduler.rs:571）
    auto_confirm: Arc<AutoConfirm>,
    wake: Condvar,                  // 新增：worker 等待 / enqueue 唤醒
    session: Mutex<SessionState>,   // 新增：会话统计
    /// **会话级**停止。`stop_session` 置位、`enqueue` 复位。
    /// 它只让 `take_job` 返回 Empty，**不让 worker 退出**。
    stopped: AtomicBool,
    /// **进程级**关停。worker 唯一的退出条件，永不复位。
    shutdown: AtomicBool,
}
```

**三个「取消」必须分开（这是最容易写错的一处）**：

| 标志 | 层级 | 谁置位 | 谁复位 | 作用 |
|---|---|---|---|---|
| `deps.cancelled` | 协议层（现有） | 上述两者都联动置位 | `enqueue` | 让在飞 HTTP 立刻跳出 |
| `Shared.stopped` | 会话级 | `stop_session` / `shutdown` | `enqueue` | 不再取新活 |
| `Shared.shutdown` | 进程级 | `shutdown` | 永不 | worker 退出 |

现状 `start_run` 把 `deps.cancelled` 直接当批次标志用（`gui.rs:758`），一旦置位调度器就死；常驻后必须拆成上表三层，否则「停止一次就再也起不来」。

## 1.5 底层原语约束（先定原语，再谈形状）

本节约束「用哪些原语、怎么配对」。违反任何一条都不会报编译错误，只会变成随机卡死、丢唤醒或数据丢失。

### 1.5.1 取件与等待必须在同一把锁内

现状 `take_job(&self)` 内部自己加锁（`scheduler.rs:621-622`），返回时锁已释放。常驻后若写成「`take_job` 返回 `Empty` → 放开锁 → `Condvar::wait`」，中间到达的 `enqueue` 的 `notify_all` 会**丢**，worker 永久睡死。

形状必须改成：

```rust
// Ctx 上：**假定调用方已持锁**
fn try_take_locked(&mut self) -> TakeOutcome;

// Shared 上：加锁 + 等待循环，唯一持有 guard 的地方
fn next_job(&self) -> Option<Job> {
    let mut ctx = self.lock();
    loop {
        if self.shutdown.load(SeqCst) { return None; }
        match ctx.try_take_locked() {
            TakeOutcome::Job(job) => return Some(job),
            TakeOutcome::Empty => {
                ctx = self.wake.wait(ctx).unwrap_or_else(|e| e.into_inner());
            }
            TakeOutcome::Wait(ms) => {
                // 退避等待也必须在同一个 guard 上 wait_timeout，不许放开锁睡
                let (guard, _) = self
                    .wake
                    .wait_timeout(ctx, Duration::from_millis(ms))
                    .unwrap_or_else(|e| e.into_inner());
                ctx = guard;
            }
        }
    }
}
```

`stopped` 为真时 `try_take_locked` 直接返回 `Empty`（不取新活、**不打日志**，否则每次停止都刷屏）。

### 1.5.2 Ordering 一律 `SeqCst`

`stopped` / `shutdown` / `deps.cancelled` 全部沿用现有 `SeqCst`。**不许顺手改 `Relaxed`**：这三个标志跨越「worker 线程 ↔ Tauri 命令线程」，弱化后要重新证明可见性，收益为零。

### 1.5.3 两把锁不许反向嵌套

`scheduler 槽（`Mutex<Option<Scheduler>>`）` 与 `Mutex<Ctx>` 只允许一种顺序：槽锁先、立刻释放，再锁 ctx。

```rust
// 对：返回克隆，guard 不出函数
fn ensure_scheduler(&self) -> Result<Scheduler, String>;

// 错：guard 逃出函数 ⇒ 调用方持槽锁去锁 ctx ⇒ 任何反向路径死锁
fn ensure_scheduler(&self) -> Result<MutexGuard<'_, Option<Scheduler>>, String>;
```

因此 `Scheduler` 必须实现 `Clone`（克隆内部 `Arc<Shared>`，不复制任何状态）。

### 1.5.4 `intake` 上传阶段必须串行

`refs-cache.json` 是「读 → 合并 → 写」的整文件操作（`run.rs:1220-1241`）。两个并发的 `enqueue` 在锁外同时上传，会互相覆盖缓存项（丢更新，下次重传同一张图）。

- 形状：`GuiState.intake_lock: Mutex<()>`，`enqueue_tasks` 全程持有（上传 + 入队）。
- 代价可接受：投喂是人工动作，串行不会成瓶颈；顺带挡住「连点两次提交」。
- **不许**把上传挪进 `Mutex<Ctx>`：网络 I/O 会卡住整个调度器。

### 1.5.5 只读命令不抢锁

`--status` / `--check` / `--dry-run` / `--list-models` 现在能与 GUI 并行跑（只读 `state.jsonl`）。若它们也抢 `var/.lock`，用户在跑批时查状态会被拒——**这是用户可感知的行为改变**。

| 命令 | 抢锁 | 理由 |
|---|---|---|
| 跑批（无子命令 / `--prompts`） | 是 | 唯一写者 |
| GUI | 是 | 同上 |
| `--status` / `--check` / `--dry-run` / `--list-models` | **否** | 只读，不写 state |

### 1.5.6 会话封口只有一个执行点

`is_live()` 由 true 变 false 的瞬间，所有 worker 都可能同时看到。若各自封口，会重复写 `report.csv` 与日志。

- 唯一执行点：`Shared::maybe_close_session(&mut Ctx)`，**持 ctx 锁**调用。
- 幂等判据：`SessionState.id.is_some()`，已封口直接返回。
- 调用位置：worker 在 `processing.remove(id)` 之后、进入 `next_job()` 之前各调一次。
- 封口时顺带清 `Ctx.removed`（此时 `processing` 必为空，墓碑不会再被命中）。

### 1.5.7 `requeue` 必须尊重 `stopped`

现状 `Shared::requeue` 无条件 `queue.push`（`scheduler.rs:608-610`），而停止时在飞任务回来正好走这条路（`handle_submit_error` 的取消分支，`scheduler.rs:906-915` 把记录退回 `pending`）。

若 `stop_session` 已清空队列，它会把这个 id **重新塞回去**，于是：

- 队列非空 ⇒ `is_live()` 恒为 true ⇒ 会话永远封不了口；
- worker 又取到它 ⇒ 再中断 ⇒ 再 requeue ⇒ 自旋。

规则两条：

1. `stopped` 为真时，`requeue` **只 `update` 状态、不 `push`**。
2. `stop_session` 必须**先**置 `stopped`、**后**清队列 —— 顺序反了，在飞任务就有机会在两者之间 push 回来。

## 2.1 提交链（GUI）

```text

  enqueue_tasks({tasks: TaskInput[]})

    ② 参考图上传（锁外）            data:/本机路径 → CDN，写 refs-cache.json
    ③ 锁内去重 + 参数变更检测      见 §3.1 矩阵
    ④ 锁内写盘 + 入队               state.create / state.update；queue.push；task_by_id.insert

  scheduler.shutdown() -> SessionSummary -> print_summary
```

`wait_idle` 是 CLI 独有的等待原语，**不进** `Scheduler` 的公开面（GUI 永远不会阻塞等空闲）。

## 2.3 运行链（worker 内，不变）

```text
worker_loop                       while !shutdown.load()     ← 唯一退出条件
  next_job()                      ← 加锁 + 等待循环（形状见 §1.5.1）
    └─ Ctx::try_take_locked(&mut ctx)
         ├─ stopped 为真 ⇒ Empty（不取新活、不打日志）
         ├─ 取件：queue.remove(index) → processing.insert(id)
         └─ 无可取 ⇒ Empty / Wait(ms)（退避也必须 wait_timeout，不放开锁睡）
  执行 → 终态/退回
    ├─ 终态：processing.remove(id) → update（命中 removed 则丢弃）→ maybe_close_session()
    └─ requeue：processing.remove(id) → queue.push(id)（现有 requeue，scheduler.rs:600）
```

**三条约束**：

1. **取件与等待必须同锁**：`try_take_locked` 假定调用方已持锁；`next_job` 是唯一持有 guard 的地方。写成「先返回、再 wait」必丢唤醒（§1.5.1）。
2. **`Empty` 不等于退出**：worker 只在 `shutdown` 置位时离开循环。`stopped` 只让取件返回 `Empty`，worker 转去 `wait`。
3. **唤醒来源有三个**：`enqueue`（新任务）、`stop_session`（让 worker 重新评估 `stopped`）、`shutdown`（退出）。

## 2.4 追加链

与 §2.1 **完全同一条**，差别只有 `IntakeReport.appended = true`。不新增命令、不新增分支。

## 2.5 删除链

```text
cancel_all_tasks → Scheduler::remove_open()
    ├─ stopped.store(true) + deps.cancelled.store(true)   在飞请求协作式中断
    ├─ 锁内 state.remove(非终态 ids)
    ├─ 锁内 removed.extend(被删 ids)                       墓碑
    └─ queue.clear() / processing.clear() / task_by_id.retain(终态)
```

`remove_tasks` / `clear_finished_tasks` 走同一把 `Mutex<Ctx>`，不再外部 `StateStore::open` 重写。

**墓碑是必须的，不是防御性冗余**：删除是同步完成的，但在飞任务还没回来。它收尾时会走 `Shared::update`，而记录已不存在 —— 现状那行会打「状态更新失败（内部 bug，请报告）：UnknownTask」（`scheduler.rs:576`）。删除越即时，这条假告警越频繁。

规则：`update` 命中 `removed` 中的 id ⇒ 静默丢弃；**不在** `removed` 里却查不到记录 ⇒ 仍是内部 bug，照常告警。

# 3. 契约

## 3.1 投喂结果矩阵

判据**不是 `status` 枚举**，而是「是否被调度器持有」+「是否终态」两问。

原因：`stop_session` 会清空队列，但记录仍是 `pending` / `running`。只看 status 会把「队列里已经没有的 pending」也判成 `AlreadyQueued` —— 用户重新投喂同一条永远进不来，死路。

| 优先级 | 条件 | 结果 |
|---|---|---|
| 1 | 无记录 | 新建 `pending` → 入队 |
| 2 | `held(id)`（在 `queue` 或 `processing`） | 拒绝 `AlreadyQueued` |
| 3 | `needs_confirm` | 拒绝 `ParkedConfirm`（花积分必须人工点头） |
| 4 | `unresolved` | 拒绝 `ParkedUnresolved`（提示点「接着查」；投喂即重跑会偷偷扣费） |
| 5 | 终态 + 参数相同 | 拒绝 `AlreadyFinished`（要再出一张请点重跑） |
| 6 | 终态 + 参数不同 | 重置 `pending` → 入队 |
| 7 | 其余（`pending` / `running` 但**未被持有**） | 同步参数 → 入队（恢复） |

第 7 行的两半，行为都安全：

- `pending` 未持有 ⇒ 重新提交（用户主动投喂，本意就是跑它）。
- `running` 未持有（已有 threadId）⇒ 入队后状态表给出 `Recheck`，**只查结果、不重新提交**（`status_row(...).job`，`scheduler.rs:639`）。
- `submitting` 走不到这里：启动扫描已改回 `pending`（§3.8）。

`held` 只能来自 `queue` / `processing`，**不许用 status 推导** —— 否则「停止后清空的队列」与「状态还是 pending」会被混为一谈。

**唯一主动改变用户可见行为的地方**：过去「同文本重复提交」是静默无反应，现在是明确拒绝 + 一句解释。任务结果完全一致，只是不再假装成功。这是需求 2（保留编辑框内容）的必要配套，否则用户会以为排上了。

## 3.2 命令契约

**`enqueue_tasks`**
- 幂等性：**不幂等，但重复提交安全**：已持有的 id 被拒（`AlreadyQueued`），未被持有的非终态 id 被接受（恢复路径，§3.1 第 7 行）。不存在「提交两次跑两遍」。
- 全量失败与部分失败：**部分成功是常态**，逐条返回，绝不整批回滚。
- 并发调用：两次调用串行进入 `Mutex<Ctx>`，第二次看到第一次的结果（因此会命中 `AlreadyQueued`）。
- 空 `tasks`：返回 `accepted=[]`，不报错（前端「提交」按钮已禁用空队列）。

**`cancel_all_tasks`**
- 调用即返回，返回 `cleared` 为**已删除条数**（同步完成，不再是 `stopping`）。
- 与 `enqueue_tasks` 并发时：两者串行，谁先谁生效；后到者看到的是前者之后的状态。

**`get_state`**
- 缓存键含 `rev`（原子递增），`enqueue` / 封口 / 停止都要 `rev.fetch_add(1)`。
- `following` 只含 `held_ids()`；`running` = `is_live()`。

## 3.3 会话契约

| 事件 | 判据（同一把锁内） | 动作 |
|---|---|---|
| 开会话 | `is_live() == false` 且 `accepted` 非空 | `id = 本地时间 %Y%m%d-%H%M%S`；`run.log` 写会话开始 |
| 续会话 | `is_live() == true` | `appended_rounds += 1`；`run.log` 写「会话内追加 N 条（累计 M 条）」 |
| 封口 | `is_live()` 由 true 变 false | ① 归档旧报告（若存在）→ ② 写 `report.csv`（覆盖）→ ③ `run.log` 写会话结束 → ④ 清 `SessionState` |

`Parked`（`needs_confirm` / `unresolved`）不参与 `is_live`：一条待确认记录不会让会话永远开着（现状 `批次结束：… needsConfirm=1` 同理）。

**封口与投喂竞态**：封口判定与 `queue.push` 都在 `Mutex<Ctx>` 内，不存在「刚封口又入队」的中间态；封口后到达的投喂天然开启新会话。封口的唯一执行点与幂等判据见 §1.5.6。

**停止时在飞记录的归宿**（沿用现状 `scheduler.rs:906-915` / `1243-1251`，不新增语义）：

| 在飞阶段 | 取消后状态 | 是否入队 |
|---|---|---|
| 已提交、未拿到 threadId | `pending`，`error = "已中断"` | **否**（§1.5.7） |
| 已有 threadId（轮询中） | `running`，保留 threadId | **否**（下次按 `Recheck` 复查，不重新提交） |
| 收尾复查中（final sweep） | `unresolved` | **否** |

停止**不把任何记录判为失败** —— 这是「停止后还能继续」的前提，也是现状行为。

## 3.4 锁与并发契约

- 调度器内部只有一把锁 `Mutex<Ctx>`；`session` / `alerts` / `view` / `env_lock` / `intake_lock` / scheduler 槽锁都是独立小锁，**互不嵌套**（持 ctx 时不得锁它们，反之亦然）。
- 唯一允许的组合顺序：`intake_lock` → 槽锁（取到 `Scheduler` 克隆后立刻释放）→ `Mutex<Ctx>`（§1.5.3、§1.5.4）。
- `Condvar` 必须与 `Mutex<Ctx>` 配对（`wake.wait(ctx)`），避免丢唤醒。
- 三个标志都是 `AtomicBool`，与锁无关：`stop_session` 置 `stopped` + `deps.cancelled` 后 `notify_all`，worker **转去等待**（不退出）；`shutdown` 置 `shutdown` 后 `notify_all`，worker 才离开循环（见 §1.2.2 表）。
- 停止后**不销毁** `Scheduler`：会话结束 ≠ 调度器结束，编辑框可以继续投喂（需求 3）。

## 3.5 文件契约

| 文件 | 写者 | 时机 | 变化 |
|---|---|---|---|
| `var/state.jsonl` | 仅 `Scheduler` | 记录创建 / 状态迁移 | 不变（单写者由 I1 保证） |
| `var/.lock` | 进程 | 启动获取，退出释放 | **新增**（实现见下） |
| `var/report.csv` | 会话封口 | 覆盖写（**最新会话**） | 不变 |
| `var/reports/report-<旧文件 mtime>.csv` | 会话封口 | 覆盖前归档旧报告 | **新增** |
| `var/run.log` | 调度器 | 只追加 | 批次标记 → 会话标记 |
| `var/queue.jsonl` | 无 | — | **退役**：GUI 不写不读；不迁移旧文件 |
| `var/refs-cache.json` | intake | 上传后 | 不变 |
| `inbox/**` | 导入命令 | 不变 | 不变 |

**报告归档规则**（用户 2026-11-07 采纳）：
- 主入口不变：`var/report.csv` 永远是最新会话，路径固定、行为与现在完全一致。
- 写新报告前，若旧文件存在，先 `rename` 到 `var/reports/report-<旧文件 mtime，格式 %Y%m%d-%H%M%S>.csv`，再写新的。
- 归档失败**只告警**，不阻断写主文件（`push_alert` 复用）。
- 用 mtime 命名而不是 sessionId：封口时上一会话的 id 已清空，而 mtime 就是那一刻，无需额外记账。

**.lock 实现**（不新增依赖）：Windows 用 `std::os::windows::fs::OpenOptionsExt::share_mode(0)` 独占打开，进程退出由 OS 释放；Unix 用已在依赖里的 `libc::flock(fd, LOCK_EX | LOCK_NB)`。**不引 `fs2` / 单实例插件**——`tauri-plugin-single-instance` 只覆盖 GUI 分支，而 CLI 是同一二进制的无 GUI 路径，管不到。

## 3.6 失败与可见性契约

| 失败 | 表现 | 禁止 |
|---|---|---|
| 单条校验失败 | 该条进 `rejected`，其余照常入队 | 整批拒绝 |
| 参考图上传失败 | 该条 `RefUpload`，其余照常 | 用空 refs 入队 |

- **旧 `queue.jsonl`**：不再读取，留在磁盘上不报错。
- **`prompt_hash`**：不改（否则全部记录失效、断点续跑归零）。

## 3.8 启动修复扫描（只改状态，不开跑）

`Scheduler::start` 里做一次，之后永不再做：

| 项 | 内容 |
|---|---|
| 扫什么 | `state.jsonl` 中 `status == submitting` 且 `thread_id` 为空的记录 |
| 改什么 | 置回 `pending`，`error = "上次提交未完成，重新提交"`（与现状文案一致） |
| **不改什么** | 不入队、不投喂、不写报告、不触发任何上游请求 |
| 失败怎么办 | 单条失败写日志，不影响启动 |

**为什么必须做**：`submitting` 的 `job` 为空（`status_row(...).job == None`），没有 threadId 就无处续查。现状靠建队时回退（`scheduler.rs:1628-1647`）——常驻后没有建队点，不修就永久卡死，而且用户重新投喂同一文本会被判 `AlreadyQueued`。

**为什么不违反「不自动接管」**：它只改一个状态字段，不产生任何积分消耗，用户看不到任务开始跑。这是修复，不是续跑。

2. 新增第二个 `Arc<Mutex<StateStore>>` 或第二把「整个调度器」级别的锁。
3. 在 `log` 回调里锁 `ctx`（死锁，已踩过）。
4. 在 worker 内调用 `enqueue`（持锁死锁）。
5. 让 `build_status_json` 依赖 `Scheduler`（CLI 无调度器）。
6. 前端自行判断模型别名 / 状态可做动作（一律读后端下发）。
7. 为「追加」新增第二条命令或第二个建队实现。
8. 在 `intake` 之外再写一份 `PromptTask` 校验。
