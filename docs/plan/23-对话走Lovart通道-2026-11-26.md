## 1. 先说结论：怎么接最合理

**三条接缝，各归其位；一行网络代码都不用新写。**

```
assistant::send(store, arg, transport)          ← 纯逻辑（组装 / 判失败 / 落盘），不 import lovart
        │  transport: &dyn ChatCompletion
        ▼
assistant::LovartCompletion::new(deps)          ← 唯一实现，只 import crate::lovart
        │  ensure project → set_mode(false) → 上传附件 → POST /chat → 轮询 → /chat/result
        ▼
crate::lovart::{project, client, contract}      ← 已有：send_chat / get_status / get_result / upload_file
```

为什么是这条，而不是另外三条：

| 备选 | 为什么不用 |
|---|---|
| 直接在 `assistant` 里 `use crate::lovart::client` 硬调 | 不能注入 ⇒ 九个分支只能联网测；且 `assistant` 与网关耦合，日后换通道要改业务代码 |
| 把 chat 编排放进 `lovart/`（它"本来就是协议层"） | `lovart` 不能依赖 `assistant` 的类型 ⇒ 它得自带一套错误，`send` 再映射一次 ⇒ **同一个失败变形两次**（S3 正面禁止） |
| 把 transport 实现放 `gui.rs` | gui 会变厚，违反"GUI 只做三件事"；且 `ClientDeps` 的构造属于 service |

**接缝的所有权**：`ChatCompletion` 是 `assistant` 的契约；`LovartCompletion` 也住 `assistant/`（同 crate，只依赖 `lovart`）；`ClientDeps` 由 `gui.rs` 用现成的 `service::wiring::to_client_deps` 构造后注入。⇒ 业务可单测、协议不重复、gui 仍是两行。

**project 归对话独有（用户裁定 2026-11-26）**：
「project 归 AI 助手独有，各归各的，图片归图片，chat 归 chat」+「缓存方式和图片保持一致」。
⇒ `LovartCompletion` 自持一个 `ProjectCache`，**不与 `engine::scheduler::RealPorts` 共享**；
⇒ 缓存机制与出图**逐字一致**：`ProjectCache::new()` —— 进程内、按 `accessKey` 做键、由 `send_chat_with_project` 负责 ensure；**不落盘、不新增状态文件**；
⇒ 代价（明写）：每次启动后首次对话会在上游建一个 chat 专用 project，与出图 project 互不影响。真要少建，唯一正确做法是给 `ProjectCache` 加持久化 —— 那会同时改出图侧，属另一条 plan。

## 3. 形状影响（S1–S4 逐条）

### S1 状态 —— **不变**
`ChatState` / `Conversation` / `ChatMessage` 一个字符都不动；所有改状态命令仍返回完整 `State`；`title` 仍只由后端算。
只多一个字段级事实：**`config.missing` 的取值集合变了**（见 S3）。

### S2 写入 —— **不变**
`ChatStore` 仍独占 `chat-history.json`；每次写 = 重读 → 改一个字段 → 原子写；网络期间不持锁、不持表。
新增的只有"上游往返"这一段：它是**纯读**，不写文件，所以对本形状零影响。

### S3 失败 —— **判据要改一个字**（这是本轮唯一的形状修正）

v1 我写"判据 = 上游是否 2xx"。**错**。这条通道有三段：提交 → 轮询 → 取结果；2xx 只覆盖第一段，而计费发生在"上游接受并建了 thread"。

**判据改为：拿到 `thread_id` 没有。**

| 阶段 | 失败 | Outcome | 可重试 |
|---|---|---|---|
| 组装（缺提示词 / 缺凭据 / 图片读不到 / 会话不存在） | 未提交 | `NotSent` | ✅ |
| 建 project / `set_mode` / 上传附件 失败 | 未提交 | `NotSent` | ✅ |
| `POST /chat` 连接失败 / 非 2xx / `code≠0` / **无 `thread_id`** | 未提交 | `NotSent` | ✅ |
| 轮询超预算 | **已提交** | `Delivered` | ❌ |
| `result` 无可用文本 | **已提交** | `Delivered` | ❌ |
| 落盘失败 / 会话已被删 | **已提交** | `Delivered{reply}` | ❌ |

⇒ `ChatError` 枚举与 `SendResult` 三态**结构不变**，只把"2xx"换成"thread_id"这个更真的边界。

`MissingPart` 缩成两个：`SystemPrompt`（`data/chat-system-prompt.txt` 读不到）· `Credentials`（`LOVART_ACCESS_KEY`/`SECRET_KEY` 任一缺失）。
**`LOVART_CHAT_BASE_URL` / `LOVART_CHAT_KEY` / `LOVART_CHAT_MODEL` 三个键整条删除**，改成复用出图那份；`message` 里改说"在 `data/.env` 配 `LOVART_ACCESS_KEY` / `LOVART_SECRET_KEY`"。

### S4 契约 —— **不变**
六条具名命令、两种返回形状、四 adapter、两实例方法；不允许泛型 op 包。
唯一变化：`assistant_send` 的**耗时**从"一次 HTTP"变成"提交 + 轮询"，插件侧无需感知（仍是一个 await），但**发送键禁用时长**要按"最长等待预算"设计（见 §5）。

## 4. 组装：`messages` 数组 → 一段 `prompt`

`build_messages` 换成 `flatten_prompt`（纯函数）：

```
system 提示词
<空行>
用户：第一问
<空行>
助手：第一答
<空行>
用户：本轮正文            ← 末尾附 "[图片缺失]"? 不：缺图标记留在原图位置
```

- 每段之间**一个空行**；role 用中文标签（`用户：` / `助手：`）—— 上游只吃字符串，标签是为了让模型分得清谁说的。
- 历史缺图 ⇒ 该条末尾追加 `[图片缺失]`，**不上传**（与本轮 `BadImage` 的分界见 plan 21 I-6）。
- **图片一律走 attachments（CDN），不进 prompt 文本**：本轮图 + **全部能读到的历史图**。
  ⚠️ 这条照参照实现（`maomao localTool/src/ai-relay/providers/lovart/index.ts` 的
  `extractChatTextAndImages` 会遍历**所有** messages 收图，再由 `resolveLovartAttachments` 全部上传）。
  我一度想改成"只传本轮、历史降级成标记"，理由是"怕重复计费"——那是**我的推测**，没有上游证据。
  在拿到"上游按消息归属附件"的证据之前，**照参照实现做**；代价已记账：每轮会把能读到的历史图重传一遍（上传时间 + token）。

## 5. 时间预算（不自造新数值）

| 值 | 取哪 | 后果 |
|---|---|---|
| 单请求超时 | 已有 `REQUEST_TIMEOUT_MS`（60s） | 不变 |
| 轮询总预算 | **同一常量**（60s 从提交起算） | 超过 ⇒ `Delivered`（钱可能花了），界面说"可能已计费，不要重发" |
| 轮询间隔 | 已有 `Settings::poll_interval_sec`（设置页可改） | 与出图同一口径 |

不新增任何常量；若真嫌 60s 短，由用户开口再调——那时才引入新数值，并同时改文档。

## 9. 两笔必须承认的代价

1. **每轮重传历史图**：上游只认"一次提交的 attachments"，没有"按消息归属"的入口 ⇒ 想让模型看得见历史图，就得每轮把能读到的历史图再传一遍（上传时间 + token 随对话长度增长）。这是照参照实现的代价，不是我们的发明。
2. **读不到的历史图只能降级**：会话存的是来源路径，文件被删就没有字节可传 ⇒ 该条正文写 `[图片缺失]`，模型知道"此处缺图"（plan 21 I-6）。用户问"这张和上一张比"，第一张已被删时，模型只能凭标记作答——**这是真话，不装成能看见**。

长对话变慢时**不许偷偷截断历史**（那就是"界面说谎"的另一种）：要么用户开新会话，要么由用户开口定"只回传最近 N 轮"，并把 N 写进文档。
