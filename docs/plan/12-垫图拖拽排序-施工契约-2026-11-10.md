# 垫图拖拽排序 · 施工契约

> 状态：**施工中**（2026-11-10）。
> 上游需求（用户原话）：编辑区的垫图要能拖拽调顺序；**发送区之后不归我们管**。
> 行号按 2026-11-10 版本；施工后以函数名为准。

---

## 0. 结论（一句话）

顺序**只允许有一个来源**：`draft.refs` 的数组顺序 = 编辑区缩略图从左到右 = 提交给后端的 `refs` = 文本里 `[img=图片N]` 的 N。
现在有两处会把这个顺序搅乱，必须同批拆掉，否则拖拽只是"看起来换了位置"。

---

## 1. 现状（为什么拖拽现在做了也没用）

| # | 位置 | 事实 | 后果 |
|---|---|---|---|
| R1 | `ui/app.js:1268` `addToQueue` | `mergeReferenceImageUrls(resolved.refImages, draft.refs)` 把 `@` 芯片引用的图**强行提到最前** | 缩略图条里的顺序 ≠ 提交顺序；拖了等于白拖 |
| R2 | `ui/promptChips.js:182` `resolvePromptChips` | `[img=图片N]` 的 N = 芯片在**文本里首次出现的顺序** | 拖动后参考图换了位次，文本里的「图片N」还指着旧位次 |
| R3 | `ui/app.js:1380` `renderRefs` | 缩略图**没有序号**、也没有拖拽 | 用户看不出哪张是「图片1」，拖完也无从核对 |

**已确认**：`refs` 数组顺序一路原样下传（`intake.rs:108` → `run.rs` → 上游参考图列表），中间没有任何排序，所以**只要数组顺序对，发出去就对**。

## 2. 施工项（同一批交付，缺一条算返工）

### S1 顺序收口到 `draft.refs`（`ui/promptChips.js` + `ui/app.js`）

- `resolvePromptChips` 改成：`[img=图片N]` 的 N = **这张图的 url 在传入 `refImages` 里的位次 + 1**；
  返回值只剩 `{ text }`（不再产出"排好序的图片数组"）。
- **删掉 `mergeReferenceImageUrls`**（不是改语义）：芯片图只可能来自 `draft.refs`（`mentionAssets` 的唯一来源），
  "合并两份列表"这件事本来就不存在；留着它就是第二个决定顺序的地方。
- `addToQueue`：`refs = draft.refs.map(...)`，直接按数组顺序提交；顺手删掉只为它服务的 `labelOf`。

**为什么**：同一件事在仓里能被抄到两个样本，下一个人不知道该信哪个 —— 这正是本轮要消灭的东西。

### S2 拖拽（`ui/app.js` `renderRefs`）

**用 pointer 事件自己实现，三条硬约束：**

1. **不用 HTML5 `draggable`**：窗口的 `dragDropEnabled` 默认开着（拖文件进窗口靠它，见
   `src-tauri/capabilities/default.json`），webview 内部的 `dragstart` / `drop` 会被吃掉。
2. **不用 `el.style.*`**（本文件头已写死零内联样式）：拖拽预览靠**直接挪 DOM 节点**
   （`nearest.before(node)` / `nearest.after(node)`），松手时读 DOM 顺序回写 `draft.refs`。
3. **拖拽中禁止 `renderRefs()`**：全量重建会把正在被拖的节点换掉，手势当场断掉。

细节：

- 起点：`pointerdown`（左键、不是 `.ref-remove`）→ `setPointerCapture`；
  位移 < 4px 视为点击，不启动拖拽（否则手一抖就换位）。
- 落点：取指针**最近的兄弟中心**，指针在中心右侧/下方 ⇒ 放它后面，否则前面（`flex-wrap` 下两行也能落对）。
- 收尾：读 `#refs .ref[data-ref-id]` 的顺序，按 id 回写 `draft.refs`（**id 不许变**：`@` 芯片按 id 引用，
  换 id 等于把芯片指到别的图上）；找不到 id ⇒ 直接抛错，不静默丢弃。
- `img.draggable = false`：否则浏览器原生图片拖拽会抢走手势。
- 收尾后 `renderRefs()` + `renderMentions()`（`@` 候选顺序跟着走）。

### S3 序号角标（`ui/app.js` + `ui/style.css`）

每张缩略图左下角显示 `1..N`（= 提交位次 = `[img=图片N]` 的 N）。
**没有它，拖完也核不出"文本里的图片2是哪张"** —— 序号是这条功能的验收面，不是装饰。

### S4 注释与文档同步

- `ui/promptChips.js` 文件头 / `resolvePromptChips` 文档注释：写清「N = 参考图列表位次，**不是**首次出现顺序」。
- `ui/app.js` `addToQueue` 的 `⚠️ **顺序是语义**` 段落改写成现在的口径。
- `ui/style.css` `.refs` / `.ref` / `.ref-num` 注释写清角标含义。

## 3. 明确不做

| 项 | 为什么不做 |
|---|---|
| 待发区域拖拽调序 | 用户 2026-11-10 明确：**到了发送区就不归我们管** |
| 已发任务重跑时改垫图顺序 | 重跑用的是后端记录的 `refUrls`，与"发送前"无关 |
| 键盘上下移动 | 本轮只做拖拽；要做就单独一轮，不留半套 |

---

## 4. 验收（交付时逐条贴证据）

1. 加 3 张（A B C）→ 拖成 C A B → 角标依次 1 2 3，第一张是 C。
2. 文本里 `@` 引用 C（现在排第 1）→ 发出去文本是 `[img=图片1]`；引用 B（排第 3）→ `图片3`。
3. 待发卡片首图 = C；「复制垫图地址」/ 导出 JSONL 的 `refs` 顺序 = C A B。
4. `grep -rn "mergeReferenceImageUrls" ui` = **0**；`grep -rn "首次出现顺序" ui` = **0**。
5. `make check`（`cargo test`）全绿；`ui/` 改动靠 `make win` 出的 exe 真机点（前端资源是编译期内嵌，拷旧 exe 不算）。

## 5. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| pointer capture 与删除键点击打架 | 点 × 变成拖拽 | `pointerdown` 命中 `.ref-remove` 直接不启动 |
| 拖拽中界面重渲染 | 手势中断 | 拖拽状态存模块级 `refDrag`，期间不调 `renderRefs()` |
| 序号与文本编号再次漂移 | 用户按序号写「图片2」，发出去对不上 | 两者都取 `draft.refs` 下标 + 1，一处生成 |
