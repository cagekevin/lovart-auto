# 追加卡死与锁内写盘 · 施工契约

> 状态：**规划中**（2026-11-09，未开工）。
> 上游症状来自用户 2026-11-09 反馈：200 条在跑时追加不了（红字报错 / 点发送后确认点不下去）、界面卡死。
> 行号按 2026-11-09 版本；施工后以函数名为准。
>
> **本次只做一件事**：把「改状态」与「碰磁盘」分开，并让 GUI 命令不再占主线程。
> 所有改动都必须一次交付完；任何一条只做一半（例如攒批写了但 `flush()` 的语义没改）都算返工。

---

## 0. 结论（一句话）

卡死不是网络慢，是我们的三处自伤：
**① 每条状态变更都开一次文件写一行；② 这些写都在全局锁里；③ 会碰磁盘的 GUI 命令跑在主线程上。**
追加 200 条 = 锁内 200 次 open/write/close，界面每秒的刷新与「发布」按钮都在这把锁后面排队。

## 1. 根因（按危害排序）

| # | 位置 | 事实 | 后果 |
|---|---|---|---|

| R3 | `gui.rs:909` `publish_queue`、`:951` `retry_one`、`:1068` `confirm_task`、`:1252` `remove_tasks`、`:1321` `clear_finished_tasks`、`:1341` `cancel_all_tasks`、`:1490` `stop_run` 全是同步 `fn` | Tauri 同步命令在主线程执行（`gui.rs:1186` 已写明这条规则，`get_state`/`probe_unfinished` 就是为此改成 `async`） | 点发布/确认时主线程被占 → 窗口整体不响应、确认按钮点不下去 |

## 2. 施工项（7 条，同一批交付）

### S1 攒批写盘（`engine/state.rs`）

**改什么**

- `StateStore` 增三个字段：`pending: String`、`pending_lines: usize`、`last_flush: Instant`。
- `write()`（`:971`）**不再碰磁盘**，只把行 push 进 `pending`，然后调 `maybe_flush()`。
- 新增三个私有/公开函数：
  - `maybe_flush()`：`pending_lines >= 200 || last_flush.elapsed() >= 2s` ⇒ `flush_pending()`。
  - `flush_pending()`：一次 `open(append) + write_all(pending) + close`，成功后清空；失败走既有 `record_write_error`（`on_write_error` 回调保持只调一次）。
  - `pub fn flush_now(&mut self) -> PersistOutcome`：先 `flush_pending()`，再返回既有健康度。
- `flush()`（`:902`）**语义不变**（非阻塞读健康度），只把文档注释改准：它从来不代表已落盘。
- `compact()` / `remove()` 的 `rename` 之前必须 `pending.clear()` —— 全量重写已经包含这些变更，不清会重复写一遍。
- 新增 `impl Drop for StateStore`：还有 `pending` 就 `flush_pending()` 一次（**幂等**）。`gui.rs:941/1094/1263/1280/1300` 那 5 处「没有调度器时临时 open 写一次」靠它兜住，**不逐点改**。
- `open_read_only()` 返回的实例 `pending` 永远为空，写方法若被调用要 `panic!("只读实例被写：内部 bug")` —— 不许静默丢弃（那等于丢数据）。

**为什么**：200 次开关文件压成 1 次（1~3ms），锁内耗时降两个数量级；不引线程、不引通道。

**验收**：追加 200 条后 `state.jsonl` 行数与记录数一致；`grep -c "OpenOptions::new" state.rs` = 1。

### S2 三个「必须立刻落盘」的调用点

| 位置 | 改成 | 理由 |
|---|---|---|
| `scheduler.rs:1919` `enqueue` 末尾 | `ctx.state.flush()` → `flush_now()`，失败仍中止 | 落盘失败不许开跑（语义不变，只是真的写了） |
| `run_submit` 写完 `thread_id/running` 之后（新增调用） | `Shared` 新增 `flush_now()`，**锁外**调用 | 花钱边界：进程被杀后不得重复提交 |
| `scheduler.rs:2051` `update_record` | `let _ = flush()` → `flush_now()`，失败**返回 Err** | 「确认」会花积分，吞掉落盘失败 = 钱花了状态没了 |

另外两处 `let _ = ctx.state.flush()`（`:543` `fix_orphan_submitting`、`:2038` `reset_for_retry`）同样换成 `flush_now()`：它们现在其实**一次盘都没写**，只是读健康度。

**验收**：`grep -rn "let _ = .*state.flush()" src-tauri/src` = 0。

### S3 会碰磁盘的 GUI 命令改 `async`（`gui.rs`）

`publish_queue` / `retry_one` / `resume_one` / `confirm_task` / `remove_tasks` / `clear_finished_tasks` / `cancel_all_tasks` / `stop_run` 的 `fn` 前加 `async`。

**为什么**：这条与 S1 是配套的 —— S1 让写变快，S3 保证即使某次慢也不占主线程。`gui.rs:1186` 的注释已经确立这条规则，这里只是把漏掉的补齐。

**验收**：`grep -n -A1 "#\[tauri::command\]" gui.rs`，会碰磁盘的 8 个命令下一行都是 `async fn`。

### S4 探针不阻塞刷新（`ui/app.js`）

- `:477` `await probeUpstreamIfNeeded(data)` → `void probeUpstreamIfNeeded(data)`。
- 函数内加节流：距上次探测不足 60 秒直接返回（`upstream.at` 时间戳）。
- 探测回来若结论变了，主动调一次 `refreshBoard()` 让标题行更新（否则要等下一次全量）。
- `publish()`：`busy = false` 提前到 `invoke` 成功之后、`await refreshBoard()` 之前（`:1763` 之前），`finally` 里再兜一次（保持幂等）。
- `flushAlerts()`：60 秒内最多弹一次。节流判断必须放在**取走之前**（`take_alerts` 取走即清，取了不弹就是丢告警）。

**为什么**：这是「确认点不下去」的直接原因。探针是**旁路信息**，不该挡住主流程。

**验收**：200 条在跑时点发布，按钮在 1 秒内恢复可点；`grep -n "await probeUpstreamIfNeeded" ui/app.js` = 0。

### S5 轮询降频（`ui/app.js`）

`REFRESH_MS` 从 1 秒改 3 秒（`document.hidden` 那条不变）。

**为什么**：`get_state` 每次是全量重算 + 序列化（`gui.rs:44` 记着 2263 条 ≈ 200ms / 4MB）。降频是当前规模下最省的一刀。

**验收**：记录 1000 条时，界面每秒 CPU 占用明显下降；卡片状态变化仍在 3 秒内出现。

### S6 参考图并发上传（`run.rs:1230`）

把串行 for 改成 4 路并发（`std::thread::scope` + 预分配结果槽，不引依赖），**单张失败仍然整批 `Err`**（语义不变，只改并发度）。

**为什么**：200 条各不相同垫图时，串行上传会占住 `intake_lock` 5~10 分钟，期间追加全部排队 —— 这是「追加不了」的第二来源。

**验收**：20 张不同参考图，上传总耗时约为串行的 1/3；失败路径与现在一致（整批不发 + 一句中文原因）。

### S7 垫图 `data:` 入口落盘（`gui.rs` + `ui/app.js`）

**症状**：发布时报 `发布失败：RangeError: Invalid string length`（2026-11-09 用户截图）。

**根因**：粘贴 / 文件选择得到的垫图是 `data:` base64（单张上限 10MB，base64 后约 13MB）。
待发队列每条任务各带一份，发布时 `invoke` 把**同一条 base64 重复序列化 N 遍** ⇒
超过 V8 的字符串上限（约 512MB），整批发不出去。实测 200 条里约 90% 是同一张图。

**改什么**

- 新增命令 `save_ref_image(data) -> path`（`gui.rs`）：`data:` 解码后按内容 sha1 前 16 位命名，
  落到 `var/refs/<hash>.<ext>`，已存在直接复用；非 `data:` 原样返回。
- `ui/app.js`：**在入口就把 `data:` 换成路径**，队列 / 导出 / 发布三条路因此都只有路径：
  - `saveRefImage(dataUrl)`：唯一实现，命中 `refPathCache` 就不重复落盘；
  - `addRefs`（编辑区：粘贴 / 选择 / 拖入）：异步落盘后 `pushRef`；
  - `toRefItems(urls)`（导入 inbox / 应用 JSONL）：整批落盘后再进队列；
  - `publish`：`await` 仍在落盘的那几张（`pendingRefSaves`），否则这一批会**静默少图**。
- `refs.rs` 的 `MAX_REF_BYTES` 改 `pub(crate)`，GUI 落盘复用同一上限（不写第二个数）。

**为什么不是「按图片池共享」**：`tasks[].refs` 是逐任务的数组，共享要改契约；
而「落盘换路径」顺带让 `refs.rs` 的既有能力（本机路径读盘 + 内容哈希缓存）直接生效。

**验收**：200 条、同一张 10MB 粘贴图 → 发布成功；`var/refs/` 下只有 1 个文件；
`run.log` 里「参考图：1 个素材（缓存命中 0，新上传 1）」。

### S8 删掉「消费者替生产者兜」的静默兜底（5 处）

**判据（2026-11-09 用户拍板）**：只有「让错误消失」的兜底才删 —— 少图、少任务、
名字变成哈希、失败被伪装成进行中。**「省略即默认」是契约不是兜底**：
模型 / 比例 / 尺寸留空走 `.env` 默认值，是为了少输，**不许删**。

| 位置 | 原兜底 | 现在 |
|---|---|---|
| `run.rs` `resolve_refs_core` | 垫图地址缺失 `filter_map` + `continue` ⇒ 静默退化成文生图 | 报错「参考图没解析出地址（内部 bug）」 |
| `intake.rs` `tasks_from_inputs` | `refs` 里空项被 `filter` 丢弃 | 报错「第 N 条：refs 里有空项」 |

**验收**：`grep -rn "缺少任务定义，跳过" src-tauri/src` = 0；
`grep -rn "filter(|value| !value.is_empty())" src-tauri/src/engine/intake.rs` = 0。

**另外 8 处「多余操作」，直接删（不是改成报错）**：

| 位置 | 多余的东西 | 为什么是多余 |
|---|---|---|
| `gui.rs` `save_ref_image_core` | 「非 `data:` 就原样返回」分支 | 前端只在 `data:` 时调用；留着让「该转却忘了转」无声通过，最后又在发布时炸 |

## 3. 明确不做

| 项 | 为什么不做 |
|---|---|
| 独立 writer 线程 / 落盘队列 / 屏障序号 | S1 的攒批已经把 200 次降到 1 次，收益的 99% 拿到了；加线程要多一套生命周期与死锁面 |
| 拆 `Mutex<Ctx>`（队列/状态/闸门三把锁） | 锁内已经不再有磁盘 IO，争用回到微秒级。只有实测 P99 > 5ms 或记录 > 5000 条时才值得冒这个险 |
| `get_state` 增量载荷 | 记录 2000 条以内降频足够；超过再单独立项 |
| 每条提交前的 `ensure_mode`（1.6s/条） | 那是「不会静默扣积分」的硬约束，不能为提速窗口化 |
| 前端虚拟列表 | 属于「记录几千条」那一档的问题 |

## 6. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 进程被强杀 | 丢最多 2 秒 / 200 行状态 | 三个花钱边界用 `flush_now()`；其余状态重启后走 `unresolved → 复查`（有 threadId，不重复生成） |
| `Drop` 里写盘失败 | 静默丢最后一批 | `Drop` 内只调一次 `flush_pending()`，失败结果无法上报（Rust 限制）—— 由下一次 `open` 时的健康度与日志体现，文档写明 |
| 锁内 `flush_now()` | 仍有一次 1~3ms 写 | 允许：只写一批，不是逐条；禁止的是逐条 open |
| 改 async 后命令并发 | 两个命令同时写 `state.jsonl` | 写者仍是唯一调度器（不变量 I1）；`publish_queue` 内部已有 `intake_lock` |
| 参考图并发 | 上传顺序变化导致缓存写回竞争 | 缓存只在并发结束后**写回一次**，不在线程内写 |

## 7. 待拍板（施工前需要确认）

1. 攒批阈值取 **200 行 / 2 秒**（先到先落）是否接受。
2. 轮询 **1 秒 → 3 秒** 是否接受（会让人感觉状态更新稍慢）。
