## 1. 第一性问题（一句话）

**「这次提交走免费队列还是 fast 计费通道」没有任何可切换的来源 —— 它现在写死在 `scheduler.rs::Shared::ensure_mode` 里。**

去掉它需求就消失：来源写死成 `Mode::Queue`，加多少界面都只是空转；反过来，只要这一处能跟着一个内存标志走，"花积分"就已经成立（哪怕没有按钮）。

---

## 2. 最小切片（一处接入点，跑通即算满足）

**改哪一处**：`scheduler.rs::Shared::ensure_mode` —— 全项目**唯一**在提交前设服务端模式的地方（`cli` 的开工前那次属于另一件事，见 §5）。

**加什么**：
- `spend_mode: Arc<AtomicBool>` 沿 `SchedulerConfig` 进来（CLI 走 `run_scheduler` ⇒ 传 `Arc::new(AtomicBool::new(false))`，永远免费）；
- `ensure_mode` 读它：`let mode = Mode::from_spend(self.spend_mode.load(Ordering::Relaxed));`；
- `Mode::from_spend(bool)` 是**唯一的 bool → Mode 映射**（`true ⇒ Fast`），带单测 —— 这一位反了就是整批按 fast 计费，必须由测试锁住，不能靠人读代码；
- **同批删掉** `let mode = Mode::Queue;` 这行硬编码。**不留**"硬编码 + 开关分支"两套。

**形状**（数据是什么）：
- `Mode { Queue, Fast }` —— 已在工作区（`client.rs`），带 `unlimited()`，是 `/mode/set` 报文语义的唯一出处；
- `spend_mode: Arc<AtomicBool>` —— **不落盘、不进 `Ctx`、不进 `.env`**；`Shared` 持一份（与 `AutoConfirm.enabled` 同一手法：切换立即生效）。
- 它不进 `Ctx` 的理由：`Ctx` 是**排队上下文**，花钱策略不该渗进去（`AutoConfirm` 的注释已写明同一条边界）。

**验收怎么算过**（没有界面也算过）：
- `cargo test` 绿，且新增单测覆盖 `from_spend(true) == Fast`、`Fast.unlimited() == false`；
- 手工：标志 `true` 提交一条 ⇒ `var/run.log` 出现「⚡ 花积分模式已设置（fast / 扣积分）」，`/mode/query` 回读 `unlimited:false`；标志 `false` ⇒「排队模式已设置（unlimited / 免费）」。

## 3. 紧邻的一步（接入已有入口）

- `gui.rs`：`GuiState.spend_mode: Arc<AtomicBool>`（启动恒 `false`）+ 命令 `set_spend_mode(enabled)`（**只写内存**，不碰 `.env`）+ 装配 `SchedulerConfig` 时克隆进去。
- `ui/index.html`：`#btnSpendMode` 紧贴 `#btnAutoConfirm` 右边，复用 `.auto-switch`（开启态本来就是危险色，加零行 CSS）。
- `ui/app.js`：`toggleSpendMode` 调命令，**用返回值立刻画**（与自动确认同一手法：不等轮询）；开关文案「花积分关 / 花积分中」。
- 为什么它在"紧邻"而不是第一性：去掉按钮，用命令也能切 ⇒ 需求不消失。

| 项 | 为什么可以等 |

## 5. 不做（本轮排除项）

| 项 | 理由 |
|---|---|
| `.env` 持久化 | 用户明确不要。忘了关 = 整批按 fast 计费 |
| 启动时还原 `Queue` | 启动就发网络请求；没配凭据的用户会多一条无意义告警。由"每条提交前必设"兜住 |
| CLI 的花积分开关 | 命令行是"永远免费"的独立入口；且 CLI / GUI 共用 `var/.lock`，**同时起不来**（`lockfile.rs`、`gui.rs:1649`、`run.rs:1051`），不存在互相覆盖 |
| 界面显示服务端回读模式 | 那是第二个真相：服务端随时被手机 / 外部客户端改，显示它只会和开关打架 |
| 追改已提交的任务 | 服务端按提交那一刻的模式跑，改不了，也不该假装能改 |
| 动 `pending_confirmation` / 自动确认 | 两者无关：fast 只买"不排队"，**不跳过确认**（`lovart/task.rs:56-67`） |

## 6. 数据链（第一性之后才有形状）

```
[唯一写内存] set_spend_mode(bool) ──► spend_mode: Arc<AtomicBool>（不落盘）
                                            │
                          [唯一映射] Mode::from_spend(bool)
                                            │
                     [唯一写服务端] ensure_mode ─► ports.set_mode(Mode) ─► /mode/set
                                            │
                              失败 ⇒ 本条不提交（现有不变量，不改）
```

- **产生**：只有 `set_spend_mode` 能改这个标志。
- **变形**：只有 `Mode::from_spend` 能把 bool 变成模式。
- **消费**：只有 `ensure_mode` 读它、写服务端。
- **失败语义**：内存照改（策略）；服务端写失败 ⇒ 该条不提交（宁可不发，不在未知模式下扣钱）。**投影失败不改策略。**
- **生效范围**：只影响**未来的提交**；正在跑 / 已提交的条目不追改。

## 7. 验收（逐条贴证据）

1. `cargo test`：`from_spend` 单测（true→Fast 且 `unlimited()==false`；false→Queue 且 `unlimited()==true`）。
2. `cargo check`；`node --check ui/app.js`。
3. 真机：
   1. 默认启动 ⇒ 按钮「花积分关」；提交一条 ⇒ 日志「排队模式已设置（unlimited / 免费）」；
   2. 点按钮 → 确认框 → 开；提交一条 ⇒ 日志「⚡ 花积分模式已设置（fast / 扣积分）」，`/mode/query` 回读 `unlimited:false`；
   3. 关掉按钮 ⇒ 下一条提交前回读为 `unlimited:true`；
   4. 重启程序 ⇒ 按钮回到「花积分关」（不持久化），服务端在下一条提交前被纠正为 `Queue`；
   5. 花积分开着时遇到上游 `pending_confirmation` ⇒ **仍然**停在「需你确认」（证明两个开关互不替代）。
4. 残留检查：`grep -n "Mode::Queue;" src-tauri/src/engine/scheduler.rs` 只应命中测试或注释，**不应命中 `ensure_mode`**（硬编码已删）。
