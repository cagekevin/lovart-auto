# 草稿通道：外部递送来，人确认后才开跑

> 状态：**待审**（2026-11-21 重写）
> 基线：`HEAD 8833cdd`（HTTP 三端点 + service 抽层）
> 前一版被撤回，原因见 §11（载荷爆炸 / 误删新草稿 / 转换堵住串行 HTTP）

---

## 0. 需求（一句话）

**外部程序可以把任务递送进来；它落在编辑窗的「待发」里，人看过、改过、删过之后点「发布」，任务才真正入队开跑。**

| 端点 | 语义 | 写 `state.jsonl` | 会开跑 | 谁有"开跑权" |
|---|---|---|---|---|
| `POST /tasks`（已有，不改） | 直接提交 | ✅ | ✅ | 外部 |
| `POST /drafts`（本 plan） | 只递送 | ❌ | ❌ | **人** |

## 1. 第一性

> **「谁有权让机器开始花钱？」——人。**

草稿通道的全部理由就是把"开跑"从外部程序手里收回给人。由此三条是**归属**，不是限制：

1. 草稿**不是任务**：不写 `state.jsonl`、不进调度器、不占槽、不影响看板；
2. 草稿**不自动开跑**：外部只有"递送"；
3. 草稿是**递送中**的东西：进程结束就没了（落盘是另一种能力，本 plan 不做）。

## 2. 形状

### 2.1 内存形状

```rust
pub struct Draft {
    pub id: String,            // d-<序号>，收到时生成，永不复用
    pub task: TaskInput,       // 就是 intake::TaskInput，不改字段名
    pub refs_state: RefsState, // 见 §2.4
}

pub enum RefsState {
    Ready,
    Converting,
    Unavailable(String),       // 原因要能给人看
}

pub struct DraftsStore {
    items: Vec<Draft>,
    seq: u32,
}
```

- `DraftsStore` 挂在 `Workbench` 上（`Mutex<DraftsStore>`），**只在内存**；
- **唯一写入口**：`Workbench::draft(tasks)`（HTTP、将来的 CLI 都只能调它）。

### 2.2 对外形状

| 面 | 形状 |
|---|---|
| HTTP `POST /drafts` | body **必须** `{ "tasks": [ { … } ] }`；成功 **204** 空 body；401（token 缺/错）/ 400（body 不合法）。**空 prompt 不拦**（发布时现有 `validate` 会拦） |
| Tauri 命令 `get_drafts()` | 返回**全部草稿**（含 `refs` 的 `data:`），**按需调用**，不进 `get_state` |
| Tauri 命令 `remove_draft(id)` | 删一条（后端 + 前端队列各删一次） |
| Tauri 命令 `clear_drafts(ids: Vec<String>)` | **按 id 删**（发布成功后清"本次发出去的"），不是全清 |
| 前端队列项 | `{ …task, draftId? }`（`TaskInput` 无 `deny_unknown_fields` ⇒ 多带无害） |

### 2.3 为什么草稿**不进** `get_state`（前一版的错）

`get_state` 是**每秒**调用的看板快照。草稿塞进去有两个致命后果：

1. 草稿的 `refs` 是 `data:`（10MB 图 ⇒ 13MB base64）⇒ 每秒 13MB IPC 载荷 ⇒ **界面卡**（这正是 2026-11-21 实测"发 25 条卡 3 秒"的形状）；
2. 前端拿到草稿后**已经**并进本地队列了 ⇒ 后端再重复发一遍是纯浪费。

⇒ 草稿走**独立命令**，前端只在需要时拉一次。

### 2.4 垫图的两段（复用仓库既有的）

```
外部给本机绝对路径
   → file → data:            ← engine::refs 新增（与 materialize_data_url 同模块、对偶方向）
   → 草稿里的 refs 存 data:   ← 编辑窗因此能显示垫图（与本地选图同构）
   → 发布时 data: → 落盘 var/refs/<哈希> → 上传   ← engine::refs::read_ref_inputs（既有，不动）
```

- **为什么需要"文件 → data:"**：GUI 选图那条链是「浏览器 FileReader → data: → `materialize_data_url`」，"文件 → data:"在**客户端**；服务器侧（草稿、外部来的本机路径）缺这一段；
- **落盘不新增规则**：发布链（`read_ref_inputs`）自己落盘 + 用 `refs-cache.json` 去重；
- **不认识的类型 / 读不到** ⇒ `RefsState::Unavailable(原因)`，**前端要看见**（不许静默丢图）。

## 3. 多来源、单一出入口

| 来源 | 怎么进来 |
|---|---|
| 外部 HTTP（maomao / 其他 AI） | `POST /drafts` |
| 将来 CLI / GUI 内部 | 直接调 `Workbench::draft()` |

**三条禁令**：

1. 除 `Workbench::draft` 外，任何地方不许往草稿里加东西；
2. 除 `DraftsStore` 外，任何地方不许持有草稿集合；
3. 草稿只有一份内存副本，`get_drafts` / 命令都读它。

## 4. 复用清单（不新写）

| 需要 | 复用 |
|---|---|
| 认证 | `/tasks` 的 `authorized()`（同一段代码） |
| body 解析 | `TasksBody` + `read_body()` |
| 队列渲染 / 缩略图 | `ui` 现成的 `renderQueue` + `taskCard`（**已经会显示垫图缩略图**） |
| 发布 | 现有 `publish()`（它本来就会给队列拍快照） |
| 垫图落盘 / 上传 / 去重 | `engine::refs::{materialize_data_url, read_ref_inputs}` |
| 参数校验 | `intake::tasks_from_inputs`（发布时那一道） |

## 5. 必须新写（最少）

| 新东西 | 为什么躲不掉 |
|---|---|
| `Draft` / `RefsState` / `DraftsStore` + 4 个方法 | 没有现成内存容器 |
| `engine::refs::file_to_data_url` | "文件 → data:"这个方向仓库没有（浏览器那步在客户端） |
| `POST /drafts` + 一条路由 | 没有现成端点 |
| `get_drafts` / `remove_draft` / `clear_drafts` 三个命令 | 没有现成通道把草稿送到前端 |
| `ui`：拉到草稿 ⇒ 并进队列、缩略图、删除联动、发布后按 id 清 | 队列现在是只读的，没有回填/清理 |

## 6. 两个必须先定的设计点（其余都能照做）

| # | 问题 | 选项 | 代价 |
|---|---|---|---|
| **A** | 转换（读盘 + base64）**在什么时候做** | **A1 后台线程**：收到即建草稿（`Converting`），转完更新；前端显示"转换中" | 多一个状态；HTTP 立即返回（不堵串行服务器） |
| | | **A2 发布时才转**：草稿只存路径，发布时交给 `read_ref_inputs` | 零新增、零卡；但**编辑窗看不到垫图**（缩略图空白） |
| **B** | 「编辑」回填要不要做 | **B1 做**：点「编辑」回填进编辑框（`writePrompt` 保芯片）→ 从草稿删除 → 改完再发送 | 要动 `promptChips` 回写；有芯片序列化风险 |
| | | **B2 不做**：只能看 / 删 / 发 | 零风险；但"改"这一条需求不成立 |

**A2+B2 = 零新增零风险的最小版**（能递送、看提示词、删、发；看不到垫图、不能改）。
**A1+B1 = 完整版**（与本地选图同构）。

> 这两条**必须由用户拍板**（属于"要不要某个能力"，不是限制）。

## 7. 施工步骤（每步绿了再下一步；每步可单独回滚）

| 步 | 内容 | 验收 | 回滚 |
|---|---|---|---|
| 1 | `engine::refs::file_to_data_url`（读文件 + MIME + base64；**不落盘**） | 单测：png/jpg/webp ⇒ `data:`；不存在 / 相对路径 / 未知类型 ⇒ `None` | 删函数 |
| 2 | `service::api`：`Draft` / `RefsState` / `DraftsStore` + `Workbench::{draft, drafts, remove_draft, clear_drafts(ids)}` | 单测：两条草稿 ⇒ 列表 2 条、id 不重复；`remove_draft` 生效；`clear_drafts(ids)` **只清给定 id** | 删新增块 |
| 3 | `POST /drafts`（复用认证与解析；成功 204；**本步不做转换**——留给步骤 5） | `curl`：合法 ⇒ 204；无 token ⇒ 401；body 不合法 ⇒ 400 | 删路由 + handler |
| 4 | `get_drafts` / `remove_draft` / `clear_drafts` 三个命令 + 注册 | 命令可调；`get_state` 载荷**不变**（草稿不在里面） | 删命令 |
| 5 | 垫图转换（时机按 §6-A 定）：结果写回草稿；`Converting → Ready/Unavailable` | 单测：成功后 refs 是 `data:`；失败 ⇒ `Unavailable(原因)`，**不静默** | 删转换块 |
| 6 | `ui`：拉到草稿 ⇒ 并进队列（按 id 去重）⇒ 缩略图/摘要照现有渲染；「×」⇒ `remove_draft` + 队列移除；发布成功 ⇒ 按本次队列里的 `draftId` 调 `clear_drafts(ids)` | 手动：递 3 条 ⇒ 待发出现 3 条（带垫图缩略图）⇒ 删 1 条（后端也没了）⇒ 发 2 条（后端只剩没发的那条） | `git checkout -- ui/app.js` |

## 8. 测试要求（前一版最大的问题：绿只是因为没覆盖）

| # | 用例 | 期望 |
|---|---|---|
| T1 | `file_to_data_url` 各种输入 | png/jpg/webp ⇒ `data:`；不存在 / 相对路径 / 未知类型 ⇒ `None` |
| T2 | `draft()` 收 2 条 | 列表 2 条、id 唯一、`refs_state` 初始正确 |
| T3 | `remove_draft` | 删后少一条；删不存在的 id ⇒ 不动 |
| T4 | `clear_drafts(ids)` | **只清给定 id**；不在列表里的草稿**必须还在** |
| T5 | `POST /drafts` 三态 | 204 / 401 / 400 |
| T6 | `get_state` 载荷 | **不含** `drafts` 字段（回归：草稿不许进看板载荷） |
| T7 | 同一张垫图出现在多个草稿 | 各自独立成条；`refs` 各自可显示 |
| T8 | 发布后清草稿 | 只清本次发布的 `draftId`；**发布期间新到的草稿必须还在** |

## 9. 失败语义

| 情形 | 行为 |
|---|---|
| token 缺/错 | 401（同 `/tasks`） |
| body 不合法 | 400 + 原话 |
| 垫图读不到 / 类型不认识 | 草稿保留、`Unavailable(原因)`、**前端显示出来**；发布时既有链仍能处理绝对路径 |
| 转换很慢（多张大图） | **不在 HTTP 线程做**（串行服务器会被堵住）；草稿先 `Converting` |
| 发布失败 | 不清草稿、不清队列 |
| 发布成功 | 按本次 `draftId` 清草稿（**不全清**） |
| 关 GUI | 草稿消失（内存）；**不做提示**（用户已定） |

## 10. 不做（本 plan 不新增）

- 不挑选 / 全选 / 只发所选；
- 不分批入队；
- 不设数量上限；
- 不自动发布、不做草稿超时清理；
- 不做草稿持久化；
- 不新增图片路由（垫图靠 `data:`）；
- 不改 `/tasks` 的响应与认证；
- 不在 HTTP 里做垫图转换（会堵住串行服务器）。

## 11. 前一版为什么被撤回（决策留痕）

| # | 问题 | 后果 | 本版怎么改 |
|---|---|---|---|
| 1 | 草稿（含 base64 垫图）每秒进 `get_state` | 每秒 13MB 载荷 ⇒ 界面卡 | 草稿走独立命令（§2.3） |
| 2 | 发布成功调 `clear_drafts()` **全清** | 把发布期间新到的草稿一起清掉 ⇒ 静默丢 | 按本次 `draftId` 清（§2.2 / T8） |
| 3 | 垫图转换在 HTTP 请求线程同步做 | 串行服务器被堵 2–3 秒 | 转换不在 HTTP 线程（§6-A / §9） |
| 4 | 转换失败静默降级 | 人看不到图，也没人知道 | `RefsState::Unavailable(原因)` 前端可见 |
| 5 | 草稿功能 0 单测 | "全绿"只是因为没覆盖 | §8 列 8 条必写用例 |

## 12. 自查（对 `docs/写plan的方法-删除测试.md` §6 四条硬规矩）

| 规矩 | 本 plan 的自查 |
|---|---|
| 需求只来自用户原话 | 能力只有"递送 + 看/改/删/发"；「编辑回填」「转换时机」标为**待用户拍板**，不替他决定 |
| 复用优先 | §4 列了 6 项复用（认证/解析/队列渲染/发布/落盘上传/校验）；§5 只列**躲不掉**的 5 项 |
| 限制必须先汇报（正确性除外） | 本 plan 不含任何自加限制：上限、分批、挑选、持久化全部不做；`refs` 校验沿用引擎既有（正确性） |
| 复杂度不许推给调用方 | 调用方只需 `POST /drafts {tasks:[…]}` + 204；路径转 `data:`、落盘、去重都由服务端做 |

## 13. 删除测试（每个新构造为什么必要）

| 备选 | 为什么不用 |
|---|---|
| 草稿进 `get_state` | 每秒重复下发 + base64 载荷炸界面（前版 P0-1） |
| 发布后全清草稿 | 会静默丢掉发布期间新到的草稿（前版 P0-2） |
| HTTP 里同步转垫图 | 串行服务器被大图堵住（前版 P0-3） |
| 转换失败静默保留路径 | 人看不到图、也没人知道（P1） |
| 草稿落盘 `var/drafts.jsonl` | 用户已定：临时递送，重启即没 |
| `/tasks?mode=draft` | 同一端点两种语义，调用方要记参数 |
| 前端 localStorage | 外部进程发不到前端 |
| 草稿写进 `state.jsonl` | 会进看板与断点续跑，草稿就不是草稿 |
| 独立草稿列表 UI | 现成「待发队列」能承载（还自带缩略图与摘要） |
| HTTP 直接往队列 push | 会长出第二套校验/落盘/id 生成 |
