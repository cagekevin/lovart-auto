## 0. 需求复述

**处理中**（`group === 'active'`）的卡片 ⋯ 菜单里加一项 **「取消所有任务」**：
停掉当前批次 → 等批次线程真退出 → 删除**全部未结束**记录（处理中 / 排队 / 待处理）。
**已结束的任务、图片文件、`var/report.csv` 一律不动。**

为什么必须"先停批再删"：`state.jsonl` 只有一个写者。
跑批期间调度器在写，`remove_*` 要整体重写同一个文件 ⇒ 早删一秒就被写回（复活），
或删到一半被覆盖（假删）。所以删除**只在批次线程收尾、且没有新批次能进来**的那一刻执行。

### 1.7.3 内部接口形状

```rust
// ── run.rs ───────────────────────────────────────────────────────────
/// 看板上「未结束」= active + queued + waiting。
/// **判据就是分组本身**（`task_group`），不另外抄一份状态清单。
pub(crate) fn is_board_open(status: TaskStatus) -> bool {
    task_group(status) != "finished"
}

// ── gui.rs ───────────────────────────────────────────────────────────
struct RunningBatch { cancelled: Arc<AtomicBool>, auto_confirm: Arc<AutoConfirm>, label: String, ids: BTreeSet<String> }

#[derive(Default)]
pub struct Board {
    batch: Option<RunningBatch>,
    wipe: bool,               // 「取消全部」意图；只在 clear_done 里复位
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Gate { Idle, Running, Clearing }

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ClearIntent {
    Now,      // 没有批次：wipe 已置位，调用方立刻删
    Waiting,  // 有批次：已置 cancelled + wipe，批次收尾时删
    Already,  // 已在清空：拒绝
}

impl Board {
    fn gate(&self) -> Gate;                          // wipe 优先于 batch
    fn batch(&self) -> Option<&RunningBatch>;
    fn request_clear(&mut self) -> ClearIntent;      // 锁内只改内存，零 I/O
    fn take_finished(&mut self) -> bool;             // batch = None; 返回 wipe（wipe 保持置位）
    fn clear_done(&mut self);                        // wipe = false
    fn set_batch(&mut self, batch: RunningBatch);
    fn clear_block(&self) -> Option<&'static str>;   // Clearing ⇒ Some(唯一文案)
}

impl GuiState {
    board: Mutex<Board>,                             // 取代 running: Mutex<Option<RunningBatch>>
    fn ensure_not_clearing(&self) -> Result<(), String>;  // 锁内判定，锁外 I/O
}

/// 删除**看板未结束**的记录。一次 compact ⇒ 全成或全不成。
pub fn remove_open_tasks_core(state_file: &Path) -> Result<usize, String>;
```

| 空闲完成（N=0） | `没有未结束的任务可删` |

| 延后失败（告警） | `清空任务失败：<原文>；记录仍在，可以重试` |

**N 的取数**：`remove_open_tasks_core` 的返回值（= 实际删除条数），不另算。

## 1.8 边缘情况判定表

| 场景 | 判定 |
|---|---|
| 空闲点、有未结束记录 | 毫秒级删完，返回 `{cleared:N, stopping:false}`，前端 notice |
| 空闲点、无未结束记录 | 返回 `{cleared:0}`，**不碰文件**（不白压一次） |
| 跑批中点 | 立即返回 `{cleared:0, stopping:true}`；批次到检查点退出后删，最坏约 60s |
| 连点 / 双击 | `Already` ⇒ `Err(正在取消全部任务，请稍候)`，不产生第二个删除者 |
| 清空期间点发布/重跑/接着查/确认/单删 | 4 个写闸全部返回同一句 `Err`；前端同时禁用 |
| 清空期间点「停止」 | 允许（幂等）：再 `store(true)` 一次，返回 Ok |
| 删除失败（磁盘满/只读） | `compact` 写临时文件再 rename ⇒ 原文件不坏；`Err` 原文，`wipe` 复位，记录仍在，可重试 |
| 删除过程中退出程序 | `wipe` 只在内存 ⇒ 记录还在；重开再点一次（幂等，不残留半清状态） |
| 人刚点「确认并继续」、那条 `confirm` 请求还在飞 | 清空可能先跑完；确认成功后**该条记录会重新出现** —— 钱已经花了，记录必须留（不写回才是静默丢账）。这是唯一允许"删完又出现"的情形，且只涉及那一条 |
| 批次是**取消**收尾还是**正常**收尾 | 同样走 `take_finished`；`wipe` 为真才删（正常收尾不误删） |
| 批次在 `run_scheduler` 之前就失败 | 同样走 `finish_batch` ⇒ 清空照常执行（否则 `wipe` 永远卡住） |
| 跑批中刚写完一条 `done` | 保留（已结束不动），只删未结束 |
| `needs_confirm`（待处理） | **删**（看板未结束）；确认框已写明「含待处理」 |
| `timeout` / `unresolved` / `download_failed` | 删（未结束） |
| 空 `state.jsonl` / 文件不存在 | `cleared = 0`，不报错（不存在 ≠ 读失败） |
| 坏行（半行 JSON） | 既有 `load` 语义：跳过坏行；未结束记录照删 |
| 清空后看板 | 只剩已结束；`btnResume` / `btnStop` 自动消失（派生自既有判据） |

# State 2 · 数据流

## 2.0 总图（单向）

```text
 处理中卡片 ⋯ ──菜单项──► askConfirm(固定文案)
                               │ 确定
                               ▼
                    invoke('cancel_all_tasks')
                               │
                    ┌──────────┴──────────┐
              batch=None               batch=Some
                    │                       │
            Board.wipe = true        cancelled.store(true)
            (Gate=Clearing)          Board.wipe = true
                    │                       │
        remove_open_tasks_core       立即返回 stopping:true
           （无写者）                       │
                    │                 前端 notice「已受理」
                    │                       │
        Board.clear_done()         批次跑完 → finish_batch
                    │                       │
                    │              take_finished()=true（wipe 仍置位）
                    │                       │
                    │              remove_open_tasks_core
                    │                       │
                    └──────────┬────────────┘
                               ▼
                    cleared 条数 → 命令返回 / push_alert
                               ▼
                    前端 notice + 1s 轮询 → 看板变空
```

## 2.1 链路 A：空闲清空（同线程，毫秒级）

```text
cancel_all_tasks(state)
  ├─ let mut board = lock
  ├─ match board.request_clear()
  │    ├─ Already   → Err(「正在取消全部任务，请稍候」)
  │    ├─ Waiting   → unlock → Ok{cleared:0, stopping:true}
  │    └─ Now       → wipe=true → unlock
  ├─ let result = remove_open_tasks_core(&state.state_file())   ← 锁外 I/O
  ├─ lock → board.clear_done()                                  ← 成功失败都要复位
  └─ result.map(|n| Ok{cleared:n, stopping:false})
```

**纪律**：`Mutex<Board>` 锁内零 I/O；`clear_done` 必须在成功与失败两条路径上都执行（失败不复位 ⇒ 写闸永久关闭）。

## 2.2 链路 B：跑批中清空（跨线程）

```text
cancel_all_tasks(state)
  ├─ board.request_clear() == Waiting
  │    ├─ batch.cancelled.store(true)      ← 与「停止」同一个标志
  │    ├─ wipe = true                       ← 从现在起 Gate=Clearing，谁都别想开新批
  │    └─ unlock → Ok{cleared:0, stopping:true}
  └─ 前端立刻 notice「已受理」；按钮/发布禁用由 clearing 驱动

批次线程（3 个收尾点统一）：
  finish_batch(state)                        ← 一把锁：batch=None，读 wipe（仍置位）
    └─ if need_wipe {
           let n = remove_open_tasks_core(&state_file);   ← 此刻无任何写者
           state.clear_done();                             ← 复位后 Gate=Idle
           push_alert(n>0 ? 完成文案 : 「没有未结束的任务可删」)   ← 0 条也要说：用户在等一个结果
           失败 ⇒ push_alert(失败文案)
       }
```

**为什么删除必须在 `finish_batch` 之后、`clear_done` 之前**：
- 之前 ⇒ 调度器还在写，删了会被写回复活；
- 之后（先 `clear_done` 再删）⇒ `Gate=Idle`，`publish_queue` 可以插进来开新批，新批又会往刚清空的表里写记录 ⇒ 用户看到"点了取消，任务又回来了"。
- 因此 `wipe` **横跨整个删除过程**，`take_finished` 只清 `batch`、**不清** `wipe`。

## 2.3 链路 C：三个收尾点（漏一个就破闭环）

| # | 位置 | 触发 |
|---|---|---|
| 1 | 参考图解析失败，批次没开跑 | `resolve_refs_core` Err |
| 2 | 状态文件打不开，批次没开跑 | `StateStore::open_with` Err |
| 3 | 正常跑完（Ok / Err / 取消） | `run_scheduler` 返回后 |

三处都必须：`batch = None` → `if wipe { 删; clear_done; 告警 }`。
**禁止**任何一处直接 `*running.lock() = None`（那会留下 `wipe=true` 而没人执行删除 ⇒ 永久禁写）。

## 2.4 链路 D：UI 状态与刷新

```text
refreshBoard()
  ├─ renderAutoConfirm(...)
  ├─ flushAlerts()                  ← 延后完成/失败从这里弹 toast
  ├─ boardSignature(data)           ← **必须含 data.clearing**
  │    └─ 未变 ⇒ 早退（只改「已持续」）；变了 ⇒ renderBoard
  └─ renderBoard:
       ├─ runningMeta 追加 ` · 正在取消全部任务`
       ├─ btnStop.hidden = !live || clearing
       ├─ btnResume / btnRetry: disabled = clearing
       ├─ syncPublishButton(): 空队列 || busy || clearing（renderBoard 与 renderQueue 都调，判据只此一份）
       └─ ⋯ 菜单项：clearing 时 disabled（建菜单时读同一个全局量）
```

**签名为什么必须加 `clearing`**：点击那一刻 `tasks` / `running` 一个都没变，只有 `clearing` 从 false → true；
签名不变 ⇒ `refreshBoard` 早退 ⇒ 界面完全没有"正在取消"的反馈 ⇒ 用户以为按钮坏了（与 `stopRun` 那段注释同一个教训）。

## 2.5 唯一入口表

|---|---|---|---|
| 清空意图 | `Board.wipe` | `request_clear` / `clear_done` | `gate` / `clear_block` / `get_state.clearing` |
| 批次取消 | `RunningBatch.cancelled` | `stop_run` **与** `request_clear`（同一标志，语义相同） | 调度器检查点 |
| 看板"未结束" | `run::task_group` | — | `is_board_open`（派生，不另抄清单） |
| 删除记录 | `state.jsonl` | `remove_open_tasks_core`（全删） / `remove_tasks`（单条） | 看板 |
| 结果条数 | `remove_open_tasks_core` 返回值 | — | 命令返回 / 告警 |

| 写闸文案 | `clear_block` 里的那一个字符串 | — | 4 个命令 |

## 2.6 失败拦截点表

| 节点 | 失败 | 拦截方式 | 用户可见性 |
|---|---|---|---|
| 点击前 | 无未结束记录 | 无菜单项可点（处理中卡片不存在） | — |
| 命令 | 已在清空 | `Already` ⇒ `Err` | notice 原文 |
| 命令 | 锁中毒 | `unwrap_or_else(into_inner)`（全仓惯例） | — |
| 删除 | 磁盘满 / 只读 | `Err` 原文；`compact` 临时文件 + rename ⇒ 原文件不坏；`wipe` 复位 | notice 原文 |
| 删除（延后） | 同上 | `push_alert` | toast |
| 批次收尾 | 线程 panic | **不在本增量兜底**（既有缺口）：`wipe` 卡在 true ⇒ 重启恢复 | 重开后可再点 |
| UI | `get_state` 失败 | 既有"读不到 ≠ 没有"分支 | 看板错误态 |

## 2.7 可变性与并发纪律

| 状态 | 类型 | 谁改 | 纪律 |
|---|---|---|---|
| `Board.batch` / `Board.wipe` | `Mutex<Board>` | 命令 / 批次线程 | 锁内只改内存；**零 I/O** |
| 取消标志 | `Arc<AtomicBool>` | `stop_run` / `request_clear` | `SeqCst`（既有） |
| `state.jsonl` | 文件 | 跑批时=调度器；清空时=`remove_open_tasks_core` | 由 `wipe` 保证**互斥**：`wipe=true` 期间开不了批，批次未收尾时不删 |
| 只读旁路 | `open_read_only` | `get_state` / 预览 | 不受影响 |

- 不新增全局 `static`；不在持锁期间做网络/磁盘 I/O。
- 依赖方向不变：`gui.rs → engine → lovart`，`run.rs` 的 `is_board_open` 只是分组派生，不反向依赖 GUI。
