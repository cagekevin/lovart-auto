## 0. 需求复述

把「per-task busy 退避」改造成「全局任务间隔 + 429 全局熔断」：

- 并发不变：默认 7，硬上限 8。
- 每个任务提交之间强制全局间歇（默认 1000ms）。
- 429 时全局暂停，不再 156 个任务各自硬撞。
- 402/409 仍按任务退避。
- `--retry-failed` 救回无 threadId 的 Failed。

## 1.7 对外契约

### 1.7.1 `ErrorClass` / `classify_error`（`lovart/errors.rs`）

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ErrorClass {
    RateLimit,    // 429 / 1429
    Concurrency,  // 402 / 2012
    ThreadBusy,   // 409 / 2011
    Transient,    // 0 / 408 / 5xx / Transport
    Hard,         // 400/401/403/404 / 2xx 非 JSON
}

/// 先查 biz_code，再查 HTTP code；Transport 直接 Transient。
pub fn classify_error(error: &LovartError) -> ErrorClass;

/// **由 classify_error 派生**，不再单独维护一份可重试码表。
pub fn is_retryable_error(error: &LovartError) -> bool {
    matches!(
        classify_error(error),
        ErrorClass::RateLimit | ErrorClass::Concurrency | ErrorClass::ThreadBusy | ErrorClass::Transient
    )
}
```

**删除**：`BUSY_CODES`、`is_busy_error`、`is_retryable_http_status`（其测试改用 `classify_error` / `is_retryable_error`）。

**映射表（唯一真源）：**

| 码 | ErrorClass | 可重试 |
|---|---|---|
| 402 / 2012 | `Concurrency` | 是 |
| 409 / 2011 | `ThreadBusy` | 是 |
| 429 / 1429 | `RateLimit` | 是 |
| 0 / 408 / 5xx | `Transient` | 是 |
| 400/401/403/404 | `Hard` | 否 |
| 2xx 非 JSON（`ErrCode::Internal`） | `Hard` | 否 |

**顺带修一个既有矛盾**：`is_retryable_http_status` 把 `409` 判为不可重试，但 `BUSY_CODES` 又把 `409/2011` 当「thread 忙」。结果 **提交阶段的 409 会退避重投，轮询阶段的 409 会被判死**。统一到 `ErrorClass::ThreadBusy` 后，两个阶段一致（都可重试）。`tests/client_contract.rs` 里 `409` 的断言要改成「可重试（ThreadBusy）」。

**为什么不是 `BusyKind` + 保留 `is_retryable_error`**：那会留下两份可重试口径（`BUSY_CODES` 与 `is_retryable_http_status`），409 的矛盾就是这么来的。`ErrorClass` 是**一张表**，`is_retryable_error` 只是它的派生谓词。

### 1.7.2 `TakeOutcome`（`engine/scheduler.rs`）

```rust
enum TakeOutcome {
    Job(Job),      // 可以干
    Wait(u64),     // 现在不能取，睡这么多毫秒
    Empty,         // 队列空，worker 退出
}
```

`take_job(&self) -> TakeOutcome`（替换原 `Option<Job>`）。

**同时删除 `idle_wait_ms` / `queue_is_empty`**：`TakeOutcome::Wait(ms)` / `Empty` 就是它们，`worker_loop` 不再需要二次判定。

**`Wait` 的取值 = 以下四者的最小非零值：**

1. `breaker_until - now`
2. `task_interval - (now - last_submit_at)`（仅当有 Submit 候选被间隔挡住）
3. 最早一个 `ready_at - now_ms()`
4. `IDLE_POLL_MS`（1000ms）

### 1.7.3 `SubmitGate`（`engine/scheduler.rs` 私有结构）

> **不是新模块、不是第二套限速**：把散在 `Ctx` 上的 5 个字段 + 3 个方法收进一个私有结构，**一个闸门只在一处**。

```rust
struct SubmitGate {
    last_submit_at: Option<Instant>,
    task_interval: Duration,
    breaker_until: Option<Instant>,
    breaker_level: u32,
    rate_limit_total_wait: Duration,
    backoff_base: Duration,            // 测试缝；缺省 60s
}

impl SubmitGate {
    /// 间隔 + 熔断，一步判定；Err(wait_ms) = 现在不能提交（`take_job` 直接拿它当 `Wait`）。
    fn try_claim(&mut self, now: Instant) -> Result<(), u64>;
    /// 锁内只改状态；日志由 `Shared` 在**锁外**打。
    fn on_rate_limited(&mut self, now: Instant) -> RateLimitEvent;
    /// 成功提交：level=0；total_wait=0；不清未来的 breaker_until。
    fn on_success(&mut self);
}
```

**不需要 `wait_hint`**：`try_claim` 的 `Err(wait)` 就是等待时长；`take_job` 只在**没有 Submit 候选**时才用 `ready_at` / `IDLE_POLL_MS`，此时闸门等待与它无关。

```rust

struct RateLimitEvent {
    wait: Duration,
    level: u32,
    alert: bool,
}

struct Ctx {
    // ...既有...
    gate: SubmitGate,
    mode_ready: bool,
}
```

**一次退避公式，两处复用（SSOT）：**

```rust
/// 指数退避 + jitter，唯一的公式实现。
fn exponential_backoff(level: u32, base: Duration, max: Duration) -> Duration;
```

- 402/409：`exponential_backoff(busy_retries, 5s, 60s)`
- 429：`exponential_backoff(breaker_level, 60s, 900s)`

**`set_mode` 的 once 守卫（不新增 `mode_initializing` 字段）：**

```rust
// Shared 上新增一个专用锁，避免网络 I/O 持 Ctx 锁
mode_init: Mutex<()>,

fn ensure_mode(&self, ...) -> Result<(), LovartError> {
    if self.lock().mode_ready { return Ok(()); }
    let _guard = self.mode_init.lock();          // 只让一个 worker 进去
    if self.lock().mode_ready { return Ok(()); } // 双检
    ports.set_mode(deps, true)?;
    self.lock().mode_ready = true;
    Ok(())
}
```

> 比 `mode_initializing: bool` + 等待循环简单，也不会在失败时留下卡住的标志。

**常量（`scheduler.rs` 顶部，与 `BUSY_BACKOFF_*` 同风格）：**

```rust
const TASK_INTERVAL_DEFAULT_MS: u64 = 1_000;
const RATE_LIMIT_BACKOFF_BASE_MS: u64 = 60_000;
const RATE_LIMIT_BACKOFF_MAX_MS: u64 = 900_000;
const RATE_LIMIT_TOTAL_WAIT_ALERT_MS: u64 = 6 * 3600 * 1000;
```

**`on_rate_limited` 语义：**

```
// 锁内：只改状态，返回日志载荷
wait = exponential_backoff(level, backoff_base, RATE_LIMIT_BACKOFF_MAX_MS)
breaker_until = now + wait
level += 1
rate_limit_total_wait += wait
return RateLimitEvent { wait, level, alert: rate_limit_total_wait > ALERT }

// 锁外：Shared 负责打日志（锁内调 log 有死锁风险，见 Shared::finish 的既有注释）
log("🚧 429 限流，全局暂停 {wait/1000}s（第 {level} 次）")
if alert:
    log("⚠️ 累计限流等待 {min} 分钟，疑似配额耗尽，建议停止并检查账户")
```

**成功提交（`on_success`）：**

- `level = 0`
- `rate_limit_total_wait = 0`（累计等待度量的是「当前这次连续限流」，不是终身累计，避免长跑误报）
- **不清未来的 `breaker_until`**：让它自然到期，避免「一个成功把别人的熔断关掉」。

### 1.7.8 状态迁移表

| from | to | 触发 | holds_slot | busy_retries | ready_at |
|---|---|---|---|---|---|
| Pending | Submitting | `take_job` 认领 | true | — | — |
| Submitting | Running | `send` 成功 | true | — | — |
| Submitting | Pending | **429** | false | **不变** | **0** |
| Submitting | Pending | 402 / 409 | false | +1 | now + backoff |
| Submitting | Pending | 其他可重试 | false | — | — |
| Submitting | Failed | 硬失败 / attempts 用尽 | false | — | — |
| Running | Running | **轮询 429（非兜底）** | true | — | **0** |
| Running | Done | 轮询成功 | false | — | — |
| Running | Timeout | 轮询超时 | true | — | — |
| Timeout | Unresolved | 超时达上限 | false | — | — |

- 兜底阶段（`is_final_sweep`）429 **只 `update` 为 `Unresolved`，不 requeue**——否则破坏「收尾只跑一轮」的语义，可能死循环。

# State 2 · 数据流

## 2.1 提交路径

```
worker_loop
  │
  ├─ take_job()
  │    ├─ 锁 Ctx
  │    ├─ breaker_remaining > 0 ? ──▶ 跳过所有 Submit 候选
  │    ├─ interval_remaining > 0 ? ─▶ 跳过 Submit 候选
  │    ├─ slots >= concurrency ? ───▶ 跳过 Submit 候选
  │    ├─ 有候选 → 认领：last_submit_at = now；状态 → Submitting
  │    └─ 无候选 → Wait(min(...)) / Empty
  │
  ▼
run_submit()
  │
  ├─ mode_ready ? ──否──▶ once 守卫 → set_mode()
  │                          ├─ 成功 → mode_ready = true
  │                          └─ 失败 → handle_submit_error()
  │
  ├─ ports.send()
  │    ├─ 成功 → 状态 → Running；submitted_at 首次写入；poll_and_finish()
  │    └─ 失败 → handle_submit_error()
  │
  ▼
handle_submit_error()
  │
  ├─ is_cancelled ? ─────────────▶ requeue(Pending, "已中断")
  ├─ classify_error == RateLimit ─▶ on_rate_limited()；requeue(Pending, ready_at=0, busy_retries 不变)
  ├─ classify_error == Concurrency | ThreadBusy
  │                                ▶ busy_retries+1；ready_at = now + exponential_backoff(...)
  ├─ is_retryable_error && attempts < max
  │                                ▶ attempts+1；requeue(Pending)
  └─ 其他 ───────────────────────▶ finish(Failed)
```

## 2.2 轮询路径

```
take_job()（Recheck）
  ├─ breaker_remaining > 0 ? ─▶ Wait（Running 任务的轮询也暂停）
  └─ 认领
  ▼
run_recheck / run_final
  ▼
poll_and_finish
  ▼
poll_thread
  ├─ get_status / get_result 返回 429
  │    └─ classify_error == RateLimit → return Err（不再自己 backoff）
  ├─ 其他瞬态 → backoff(10→60s) 继续
  └─ done / pending_confirmation / timeout / abort → 既有
  ▼
handle_poll_error
  ├─ is_cancelled ? ─────────────▶ 保留 threadId
  ├─ classify_error == RateLimit ─▶ on_rate_limited()
  │                                 ├─ 非兜底：requeue(Running, ready_at=0, error="限流，全局暂停中")
  │                                 └─ 兜底：update(Unresolved)，**不 requeue**
  │                                 **绝不回 Pending**
  ├─ NoArtifact / PendingConfirmation / Timeout / Abort → 既有
  ├─ is_retryable_error && attempts < max → attempts+1
  └─ 其他（Hard）→ finish(Failed)
```

## 2.3 终态（**删除唤醒**）

```
Shared::finish(id, new_status, patch)
  ├─ 锁 Ctx
  ├─ state.update(id, patch)
  └─ 解锁；日志
```

**删除 `finish` 里「清空所有排队任务 `ready_at`」的循环，不做任何唤醒。**

理由：

- 它是本次事故的放大器（一个终态唤醒 155 个，同步撞限流）。
- 它是纯优化：没有它，402/409 的任务最多等到自己的 `ready_at` 到期（`busy_backoff` 封顶 60s），`TakeOutcome::Wait` 会按 `ready_at` 到期唤醒。
- 删掉它，少一个机制、少一类 bug；代价只是 402 重投最多慢 60s，在 1s 全局间隔下可接受。

> 如果以后确实要「槽位释放立刻放一个进来」，正确做法是让 `take_job` 的 `Wait` 感知槽位变化，而不是在 `finish` 里改别的任务的 `ready_at`。

## 2.4 `--retry-failed` 建队流

```
run_scheduler 建队（Batch::Declared）
  for task in tasks:
      existing = state.get(task.id)
      ├─ None → create；queue.push
      ├─ terminal:
      │    ├─ retry_failed && status == Failed && thread_id.is_none()
      │    │     → reset_for_retry(state, id)；queue.push；log("🔁")
      │    ├─ retry_failed && status == Failed && thread_id.is_some()
      │    │     → log("⚠️ 已有 threadId，跳过")
      │    └─ 其他 → continue
      └─ 非终态 → 既有（参数变更 / submitting 回退 / queue.push）
```

## 2.5 熔断生命周期

```
正常 ──429──▶ breaker_until = now + 60s, level=1
                 │
                 ├─ 到期后：允许 1 次提交（受 interval 约束）
                 │    ├─ 成功 → level=0；rate_limit_total_wait=0；breaker_until 自然过期
                 │    └─ 429  → breaker_until = now + 120s, level=2
                 │
                 └─ 连续 429：60 → 120 → 240 → 480 → 900（封顶）
```

- 熔断状态**不落盘**；重启后从 0 开始。
- 熔断期间 `take_job` 对 Submit 返回 `Wait`，对 Recheck 也返回 `Wait`。
- 累计等待超过 6 小时：只告警，不新增暂停状态。

## 2.6 时钟策略

| 用途 | 时钟 | 原因 |
|---|---|---|
| `last_submit_at` / `breaker_until` | `Instant`（单调） | 内存态，不受系统时间跳变影响 |
| `ready_at` | `now_ms()`（墙钟） | 要落盘，重启后仍有效 |
| `state_since` / `submitted_at` | `now_iso()`（ISO） | 既有 |

**不混用**：`ready_at` 比较用 `now_ms()`，闸门比较用 `Instant`。
