## 1. 第一性问题

> **用户写「图1」，模型能不能唯一确定是哪张图？**

去掉它 ⇒ 多轮后历史图累积，「图1」随轮次漂移 ⇒ 需求消失。这是本轮唯一第一性。

**不做的事**（不是第一性，或用户没点名）：改上游协议、砍历史图、加 `@` 语法、UI 角标、交互复述确认。

## 2. 最小切片

一次 `assistant_send`（本轮 1～2 张图）跑通：正文里有清单、模型看到的附件顺序与清单编号一致。

## 3. 形状与数据链

**数据链**（谁产生 → 怎么变形 → 谁消费）：

```
插件 ui.attachments()             ← 本轮新图（SendArg.image_paths）
conversation.messages[].image_paths ← 历史图
        │
        ▼ assistant::flatten_prompt（本轮唯一改动点）
正文 = system
     + [本轮图片清单] 图1/图2…        ← 只编号本轮图
     + 历史消息（历史图带 [图片缺失] 时留标记）
     + 用户：本轮文字
附件 = [本轮图1, 本轮图2, …, 历史图…]  ← 本轮**置顶**，历史照样传
        │
        ▼ LovartCompletion::upload_all（不动）
CDN URLs（顺序 = 附件顺序）→ POST /chat → 模型看到图片序列
```

**为什么本轮图置顶**（这是本轮唯一的行为变化，必须论证）：

- 「图N」要对上具体一张图，只有两条锚：文件名、附件位置。文件名可能是 `var/refs/<hash>.png`，无语义 ⇒ 不可靠。
- 让 **「图N」= 附件第 N 张 = 清单第 N 条**，三者合一，只有一个真相（ADR-0003）。
- plan 23 §4 只承诺「历史图照传」，**没承诺顺序**（参照实现的遍历顺序不是契约）⇒ 本轮置顶不违反 plan 23。

**清单形状**（只在本轮有图时生成，插在 system 之后）：

```
[本轮图片]（说「图N」或「第N张」即指此处；N 按收到顺序）
图1：文件名1
图2：文件名2
（其余为历史参考图，不参与「图N」编号）
```
