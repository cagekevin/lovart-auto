# 全局限速与挂机稳定性 · 设计理解

> 给下一个接手的人 / AI：
> 这份文档**不重复「怎么做」**（那在 `03-设计` 与 `04-施工契约`），只解释**为什么这样设计、哪些路走过不能回头、哪些是刻意留下的代价**。
> 先读这份，再动代码；否则很容易把已经删掉的重复实现又加回来。

---

## 0. 一句话

**上游的 429 是「账号级全局资源」，旧实现却用「每个任务自己的退避」去应对；worker 不陪任务等，它立刻去队列取下一个。于是 7 个 worker 变成 7 台永不停歇的提交机，把 156 个任务当弹药，以约 290 请求/分钟连续轰了 65 分钟。**

所以这次不是「加一个限速」，而是**把 per-task busy 退避改造成「全局任务间隔 + 429 全局熔断」**。新加的东西必须替换掉同类的旧实现。

---

## 1. 事故现场（先看证据，别凭感觉）

`var/state.jsonl` 按 id 去重后：

- 160 条任务：`done=4`，`failed=156`。
- 156 条错误完全一致：`服务端持续并发满 61 次，放弃：Rate limit exceeded. Please slow down.`
- 156 条 `attempts=0` —— **根本没提交成功**，全部卡在提交阶段的 429。

时间线：

| 事件 | 时间 |
|---|---|
| 全局启动 | `10:44:47.894` |
| **首个 429** | `10:44:49.276`（启动后 **1.4 秒**） |
| 156 个任务全部撞到第一次 429 | `10:44:49` ~ `10:46:12`（**83 秒内**） |
| 4 个 done 完成 | `10:53:02` ~ `10:54:02` |
| 全部结束 | `11:50:23`（总耗时 **65.5 分钟**） |
| `state.jsonl` 行数 | **19,841 行** / 160 任务 ≈ 每次重试写 2 行 |

粗算：

- 156 × 61 ≈ **9,516 次提交尝试**
- 每次提交 = `set_mode` + `chat` 两个 POST ≈ **19,000 次请求**
- 65 分钟 ≈ **4.8 请求/秒 / 290 请求/分钟**

**结论：退避本身是生效的**（单任务 61 次确实花了 65 分钟）。失效的是「全局速率」——退避挂在任务上，不挂在 worker 上，聚合请求速率从没降下来。

---

## 2. 根因（按重要性排序）

1. **只有 per-task 退避，没有全局闸门**：worker 永远有活干，队列里 156 个积压 ⇒ 满速递。
2. **429 与 402 混为一谈**：`BUSY_CODES` 把 `402/409/429/2011/2012/1429` 全塞一个桶。402 是「等一个槽位」，429 是「你整体太快了」，策略必须不同。
3. **`set_mode` 每次提交前都调**：请求量 ×2，而且这个 POST 自己也会被限流。
4. **`finish` 清空所有排队任务的 `ready_at`**：任何一个终态都把其余 155 个正在退避的同时唤醒，形成同步风暴。
5. **不读 `Retry-After`**：上游让等多久完全无视，自己按 5→60s 硬猜。

---

## 3. 设计原则（这是本次改造的宪法）

1. **一个机制只留一份实现**：不加第二套限速、第二套错误分类、第二套重试计数、第二套重置逻辑。
2. **加了什么，就必须删掉它取代的什么**：见 §4 每条都写了「删了什么」。
3. **不加新状态**：限流仍显示 `pending`，靠 `error` 文案区分；不动 `STATUS_TABLE`。
4. **不加新 `TaskRecord` 字段**：429 不按任务计次，用全局熔断。
5. **参数只加两个**：`--task-interval-ms`、`--retry-failed`。
6. **闸门只在 `take_job`**：不下沉到 `lovart_request`，不在 `worker_loop` 里各睡各的。

## 4. 每个决定的「为什么」

### 4.1 错误分类：`BUSY_CODES` + `is_busy_error` + `is_retryable_http_status` → 一张 `ErrorClass`

**为什么必须收成一张表：**

- 旧代码有两份可重试口径：
  - `BUSY_CODES` 把 `409/2011` 当 thread 忙（提交阶段会退避重投）；
  - `is_retryable_http_status` 却把 `409` 判为**不可重试**（轮询阶段会判死）。
  - 同一个 409，提交能活、轮询判死 —— 这就是双口径漂移的实锤。
- 实现时还踩到一个真 bug：`classify_error` 最初写 `biz_code.or(http_code)`，上游在 429 响应里塞了一个无关的 `code: 1`，结果 `biz_code=1` 把 HTTP 429 盖成了 `Hard`，任务直接 Failed。
  - 修正：**业务码只在命中已知表时才优先**，否则回退到 HTTP 码：
    ```rust
    let by_biz = upstream.biz_code.and_then(classify_code);
    let by_http = upstream.code.as_number().and_then(classify_code);
    by_biz.or(by_http).unwrap_or(ErrorClass::Hard)
    ```

**最终分类：**

| 码 | ErrorClass | 可重试 | 处理 |
|---|---|---|---|
| 402 / 2012 | `Concurrency` | 是 | 单任务退避（等槽位） |
| 409 / 2011 | `ThreadBusy` | 是 | 单任务退避 |
| 429 / 1429 | `RateLimit` | 是 | **全局熔断** |
| 0 / 408 / 5xx / Transport | `Transient` | 是 | `attempts` 重试 |
| 400/401/403/404 / 2xx 非 JSON | `Hard` | 否 | Failed |

**删掉了什么：** `BUSY_CODES`、`is_busy_error`、`is_retryable_http_status`。`is_retryable_error` 变成 `ErrorClass` 的派生谓词，不再维护第二份码表。

**行为变化（有意）：** 409 现在提交和轮询都判 `ThreadBusy`（可重试）。`tests/client_contract.rs` 里 409 的旧断言已改；黄金用例 `05-rate-limit` 的期望值也按新行为更新。

### 4.2 全局任务间隔：为什么不是「每个 worker 睡 1 秒」

如果写成：

```rust
// 错的
run_submit(...);
sleep(1s);
```

7 个 worker 各自睡 1s ⇒ 全局仍是 **7 次/秒**，等于没加。

必须是**所有 worker 共享一个 `last_submit_at`**：

```rust
// SubmitGate::try_claim
if let Some(last) = self.last_submit_at {
    let elapsed = now.saturating_duration_since(last);
    if elapsed < self.task_interval {
        return Err((self.task_interval - elapsed).as_millis() as u64);
    }
}
self.last_submit_at = Some(now);
```

**为什么放在 `SubmitGate` 而不是 `Ctx` 散字段：** 闸门的 5 个字段 + 3 个方法收在一个私有结构里，`take_job` 只调 `try_claim`，不会出现「某处忘了检查间隔」。

**为什么在「认领时」扣间隔，而不是「提交完成后」：** 认领即代表这次请求确实要发；失败重投也占一次间隔，无法绕过闸门。

---

### 4.3 闸门为什么在 `take_job`，不在 `run_submit` / `lovart_request`

| 方案 | 问题 |
|---|---|
| 在 `run_submit` 里阻塞等令牌 | worker 已经认领了 `Submitting` 槽，等 60s 就白占一个槽；7 个 worker 全睡在提交上，**没人轮询**，在跑的任务饿死 |
| 在 `lovart_request` 里加闸门 | 那是第二套限速层，和 `take_job` 的闸门重复；而且 `lovart` 层不该知道调度策略 |
| 在 `worker_loop` 里各睡各的 | 7 个 worker 各睡 1s = 7 次/秒，不是全局间隔 |

**最终：** `take_job` 非阻塞预检；拿不到令牌就返回 `Wait(ms)`，**不认领、不占槽**；worker 在锁外 `sleep_or_abort`，200ms 粒度响应 Ctrl+C。

**副作用：** 轮询（`Recheck`）不走 Submit 闸门，但**受 429 熔断约束**（熔断期间 `take_job` 对 Recheck 也返回 `Wait`）。这是有意的：轮询也吃上游预算，熔断时不该继续打。

---

### 4.4 `TakeOutcome` 三态：为什么删掉 `idle_wait_ms` / `queue_is_empty`

旧 `worker_loop`：

```
if let Some(job) = take_job() { ... continue; }
if queue_is_empty() { break; }
let wait = idle_wait_ms();
sleep(wait);
```

三个函数都在回答「现在该不该干、该睡多久」。改成：

```rust
enum TakeOutcome { Job(Job), Wait(u64), Empty }
```

一个 `match` 解决：

```rust
match take_job() {
    Job(j)   => dispatch(j),
    Wait(ms) => sleep_or_abort(ms)?,
    Empty    => break,
}
```

**删掉了什么：** `idle_wait_ms`、`queue_is_empty`。等待时长的计算收进 `take_job`，取「熔断剩余、间隔剩余、最早 `ready_at`、`IDLE_POLL_MS`」的最小值。

**为什么 `Wait` 仍封顶 `IDLE_POLL_MS`（1s）：** 熔断 900s 时，worker 每 1s 醒一次重新检查，保证 Ctrl+C 和槽位释放能及时响应；7 次/秒的唤醒开销可忽略。

---

### 4.5 429 全局熔断，402/409 保持 per-task

**为什么不能都走全局：**

- 402（并发满）：只说明「账号的 8 个槽被占满了」。等一个槽就行，不该停掉所有提交；而且 402 时往往还有槽位余量（我们用 7/8）。
- 429（限流）：说明「你整体太快了」。必须**全局停**，因为继续发只会让限流器更久不恢复。

**实现：**

- 429 → `shared.on_rate_limited()`：`breaker_until = now + wait`，`level += 1`，`total_wait += wait`；任务回 `Pending`，`ready_at = 0`，**不写 `busy_retries`**。
- 402/409 → `busy_retries += 1`，`ready_at = now + exponential_backoff(busy, 5s, 60s)`。

**为什么 429 不写 `busy_retries`：** `busy_retries` 的语义是「这个任务自己等槽位等了几次」；429 是全局事件，按任务计次会让 156 个任务各自累计 61 次，重演事故。429 的放弃/告警由全局 `rate_limit_total_wait` 负责。

**`on_success` 的细节（已按审查修正）：**

```rust
fn on_success(&mut self, now: Instant) {
    if self.breaker_until.is_some_and(|until| until > now) {
        return; // 熔断未到期：这是熔断前发出的滞后成功，不能抹掉升级
    }
    self.breaker_level = 0;
    self.rate_limit_total_wait = Duration::ZERO;
    self.breaker_until = None;
}
```

闸门串行化的是**认领**，不是**请求完成**：worker A 在 T 时刻 429 开熔断，worker B 在 T-ε 认领、POST 超过 1s 才成功，会在 T+1s 调到这里。若直接清零，`level` 会永远停在 60s 不再涨。所以熔断未到期时忽略这次成功。

### 4.6 为什么删掉 `finish` 的唤醒循环

旧 `finish`：

```rust
if is_terminal(status) {
    for queued_id in queue {
        if ready_at != 0 { update(ready_at = 0); }  // 清空所有排队任务
    }
}
```

**这是事故的放大器**：一个任务到终态，把另外 155 个正在退避的同时唤醒 → 一起撞 429 → 又各自退避 → 下一个终态再全部唤醒。

**为什么可以整段删掉，而不是改成「只唤醒 1 个」：**

- 它是纯优化：没有它，402/409 的任务最多等到自己的 `ready_at` 到期（`busy_backoff` 封顶 60s）。
- 完成任务的 worker 会立刻回 `worker_loop` 再 `take_job`；`slots_in_use` 是从状态表派生的，空槽立即可见，**完成者自己就会接下一个**。
- 删掉它，少一个机制、少一类 bug；代价只是 402 重投最多慢 60s，在 1s 全局间隔下可接受。

**如果以后确实要「槽位释放立刻放一个进来」：** 正确做法是让 `take_job` 的 `Wait` 感知槽位变化，而不是在 `finish` 里改**别的任务**的 `ready_at`。

---

### 4.7 `set_mode` 为什么改成惰性初始化 + `Mutex` 双检

**旧实现：**

- `run.rs:920` 启动调一次；
- `scheduler.rs:590` **每次提交前又调一次**。
- 每次提交 = 2 个 POST，请求量 ×2。

**为什么不能简单删掉 per-submit 调用：** 启动那次如果失败（比如开局 429），后面就再也没人设置模式，可能按 fast 扣费。

**最终：**

```rust
fn ensure_mode(&self, deps, ports) -> Result<(), LovartError> {
    if self.lock().mode_ready { return Ok(()); }
    let _guard = self.mode_init.lock();          // 只让一个 worker 进去
    if self.lock().mode_ready { return Ok(()); } // 双检
    ports.set_mode(deps, true)?;
    self.lock().mode_ready = true;
    Ok(())
}
```

**为什么用 `Mutex<()>` 而不是 `mode_initializing: bool` + 等待循环：** 双检更简单，失败时不会留下卡住的标志；网络 I/O 不持 `Ctx` 锁。

**净效果：** 两个调用点合并成一个惰性初始化点；正常跑批只调 1 次。

### 4.8 `--retry-failed` 为什么复用 `reset_for_retry`

GUI 早就有一份私有的 `reset_for_retry`（`gui.rs:717`）。CLI 的 `--retry-failed` 如果另写一份补丁，两条路一定会漂移（尤其是 `ref_urls` / `ref_signature` 要不要保留）。

**最终：** 抽成 `engine/state.rs::reset_for_retry`，GUI 与 CLI 共用。

**只重置 `Failed && thread_id.is_none()`：**

- 无 threadId：图根本没生成，重置安全。
- 有 threadId：重新提交会**重复生成**，只记日志跳过。

**作用域（容易误解）：** `--retry-failed` 只对 `Batch::Declared`（CLI 的 `--prompts`）生效，且 prompts 文件必须仍包含这些 id。

**与「参数变更重置」的区别：** 如果模型/比例/尺寸/参考图变了，`!same_params && is_terminal` 分支会重置**所有**终态（包括有 threadId 的 Failed）——这是有意的：旧 threadId 只对旧参数有效，参数变了就该重新生成。不要把它和 `--retry-failed` 混为一谈。

**保留 `ref_urls` / `ref_signature`：** 重跑仍要带垫图。

**这 156 个正好 `attempts=0`、没有 threadId，重置完全安全。**

---

### 4.9 默认值为什么只留在 `run_scheduler`

旧代码里 `max-attempts` / `max-timeouts` / `download-retries` / `task-timeout` / `recheck-timeout` 的默认值在 `run.rs` 和 `run_scheduler` 各写一份。改一个默认值要改两处，必漂。

**最终：** `run.rs` 未给参数时传 `None`，默认值只在 `run_scheduler` 的 `unwrap_or(...)` 里。`run.rs` 只负责「解析用户给了什么」。

**例外：** `concurrency` 是 `usize`（不是 `Option`），CLI 默认 7、GUI 从 `.env` 读；这是两个**用户配置入口**，不是同一条代码路径的重复。

---

### 4.10 并发为什么保持 7（硬上限 8）

用户明确要求：**不砍预算**。并发上限是「服务端槽位」的本地映射，不是限速手段；限速由 `SubmitGate` 负责。

- 并发 7 + 全局 1s 间隔：前 7 秒把槽填满，之后由完成/失败释放槽位来补位。
- 不要把并发降到 1~3 来「限速」——那是用错工具，而且会让槽位长期空着。

## 5. 不变量（改代码前先确认没破坏这些）

| # | 不变量 |
|---|---|
| I1 | 任意两次 Submit 认领的间隔 ≥ `task_interval`（全局，含重试）。 |
| I2 | `breaker_until > now` 时，Submit 认领数 = 0。 |
| I3 | 429 **不**增加 `busy_retries`。 |
| I4 | 轮询 429 **不**把任务改成 `Pending`。 |
| I5 | 终态**不修改任何其他任务的 `ready_at`**（唤醒已删除）。 |
| I6 | `set_mode` 正常跑批只调用 1 次（并发首提也不重复）。 |
| I7 | `reset_for_retry` 保留 `ref_signature` / `ref_urls`。 |
| I8 | `TaskRecord` schema 不变，无新字段。 |
| I9 | 闸门等待不占 `Submitting` 槽（在 `take_job` 返回 `Wait`）。 |
| I10 | 兜底阶段（`is_final_sweep`）429 只 `update(Unresolved)`，**不 requeue**。 |
| I11 | `rate_limit_total_wait` 在成功提交时清零（度量当前连续限流，不是终身累计）。 |

## 6. 明确拒绝的方案（以及为什么）

| 方案 | 为什么拒绝 |
|---|---|
| 新增 `RateGate` 模块 | 闸门就在 `SubmitGate` + `take_job`；再加一个模块就是第二套限速 |
| 令牌桶 + `--max-api-per-min` | 用户明确不要砍预算；间隔已经足够 |
| `rate_retries` 独立计数 | 429 用全局熔断，不按任务计次 |
| `RateLimited` 新状态 | 会动 `STATUS_TABLE`、GUI、状态机；用 `pending` + `error` 文案足够 |
| `Retry-After` 解析 | `HttpResponse` 只有 `status/body`，要改传输层；本期用指数退避，Phase 2 再说 |
| 文件锁 | GUI 已有 `state.running` 闸；CLI 由使用者保证单实例。本期不加 |
| 把闸门下沉到 `lovart_request` | 会变成第二套限速，且 `lovart` 层不该知道调度策略 |
| 恢复 `finish` 唤醒 | 事故放大器；删了就不回头 |
| `biz_code.or(http_code)` | 会让无关的 `code:1` 盖掉 HTTP 429（实现时已踩过） |
| 把并发降到 1~3 当限速 | 用错工具；限速是 `SubmitGate` 的事 |

## 7. 已知代价 / 剩余债（不是 bug，是取舍）

1. **402/409 可能多等 ≤60s**：删了 `finish` 唤醒，槽位空出来时不会提前解除别的任务的 `ready_at`。在 1s 全局间隔下可接受。
2. **没有文件锁**：两个 `lovart-client` 同账号各有一份闸门，合计速率翻倍。CLI 由使用者保证单实例。
3. **没有 `Retry-After`**：429 的等待是 `60s → 120s → 240s → 480s → 900s` 指数退避 + jitter，不读上游建议值。
4. **熔断状态不落盘**：重启后 `breaker_until` / `breaker_level` 清零，第一次提交重新探测。
5. **`rate_limit_total_wait` 只告警，不自动停**：连续限流 6 小时会打一条「疑似配额耗尽」的日志，但不会把任务判 Failed，也不会自动退出。挂机的人要自己看日志。
6. **轮询 429 的特殊分支在 `lovart/task.rs`**：`poll_thread` 只负责「不吞、向上返回」，开熔断由 `handle_poll_error` 做。这是刻意的最小泄漏——把闸门塞进 `lovart` 才是更大的问题。
7. **GUI 也用默认 1s 间隔**：`gui.rs` 的 `SchedulerOptions` 传 `task_interval: None` → 1000ms。GUI 没有暴露这个设置。
8. **`run_submit` 内部 bug 边界**：如果任务/记录缺失导致提前 `return`，id 已被 `take_job` 取走、不会回队，任务会停在 `submitting`。这是既有内部异常路径，正常跑批不会触发。

## 8. 数据流 / 代码地图

### 8.1 提交

```
worker_loop
  └─ take_job()
       ├─ 熔断中 / 间隔未到 / 槽满 → 跳过 Submit
       ├─ 有候选 → 认领：gate.try_claim(now)；状态 → Submitting
       └─ 无候选 → Wait(min(熔断, 间隔, 最早 ready_at, 1s)) / Empty
  └─ run_submit()
       ├─ ensure_mode()（首次）
       ├─ send()
       ├─ 成功 → on_success()；Running；poll
       └─ 失败 → handle_submit_error()
            ├─ RateLimit → on_rate_limited()；Pending，ready_at=0
            ├─ Concurrency/ThreadBusy → busy_retries+1；ready_at=now+backoff
            ├─ Transient → attempts+1
            └─ Hard → Failed
```

### 8.2 轮询

```
take_job()（Recheck）
  └─ poll_thread()
       ├─ 429 → return Err（不再自己 backoff）
       ├─ 其他瞬态 → 10→60s 退避继续
       └─ done / pending_confirmation / timeout / abort → 既有
  └─ handle_poll_error()
       ├─ RateLimit → on_rate_limited()
       │    ├─ 非兜底：requeue(Running, ready_at=0)
       │    └─ 兜底：update(Unresolved)，不 requeue
       ├─ NoArtifact / PendingConfirmation / Timeout / Abort → 既有
       ├─ is_retryable_error && attempts < max → attempts+1
       └─ 其他 → Failed
```

### 8.3 终态

```
Shared::finish(id, new_status, patch)
  ├─ 锁 Ctx
  ├─ state.update(id, patch)
  └─ 解锁；日志
```

**不碰队列、不碰别人的 `ready_at`。**

## 9. 测试为什么这样写

- **全部走假 `Transport`，零网络**：`ReplayTransport` 在传输层回放，真调度器 + 真轮询机 + 真协议层全部跑起来。
- **`send_times`**：每次 `POST /chat` 记 `Instant`，用来断言全局提交间隔；不是断言 wall-clock 字符串。
- **`rate_limit_backoff_ms` 测试缝**：测试里调到 1ms，避免真等 60s。
- **`task_interval_ms` 测试缝**：测试默认 1ms，避免拖慢现有 fixture；T2 显式设 30ms。
- **T1~T9 对应关系（已全部落地）：**
  - T1：`classify_error` 六个码 + 409 可重试 + Transport/Hard；`client_contract` 额外钉死 `(429, Some(1))`，防止业务码掩盖 HTTP 429。
  - T2：3 任务、100ms 间隔，`send_times` 相邻差 ≥80ms（留 20ms 给首次 `set_mode`）。
  - T3：提交 429，`busy_retries=0`，日志有「🚧」。
  - T4：轮询 429，任务保持 `Running`，`/chat` 只 1 次。
  - T4b：兜底 429，`Unresolved` 不 requeue。
  - T5：402 只退避该任务，日志无「🚧」。
  - T6：种子任务 `readyAt` 在 200ms 后，另一个任务先完成；断言它的 `submitting` 行里 `readyAt` 仍为未来值（未被 `finish` 清零）。
  - T7：`--retry-failed` 重置无 threadId 的 Failed，保留 `refUrls`（`refSignature` 同样不在补丁里）；有 threadId 的保持 failed。
  - T8：3 并发、间隔 0，`/mode/set` 只 1 次。
  - T9：160 任务 + 前 3 次 429，全部完成，`/chat` 次数 ≤ 160+3+5。
- **黄金 `05-rate-limit` 已用真实回放重新生成**（临时 bless 测试跑 `run_fixture` 后写回，不是手改）：429 不再计入 `busyRetries`，`readyAt=0`，错误文案为「限流，全局暂停中：rate limited」。这是**有意的行为变更**，不是测试放水。

## 10. 如果下个 AI 要改，先读这里

### 10.1 想加一个新的错误码

1. 在 `errors.rs` 的 `classify_code` 里加映射。
2. 如果它属于「全局停」，映射到 `RateLimit`；属于「等槽位」，映射到 `Concurrency`/`ThreadBusy`；属于「普通瞬态」，映射到 `Transient`。
3. **不要**在 `scheduler.rs` 里再加一份 `match code`。

### 10.2 想加一个新的状态

1. 先读 `engine/state.rs` 的 `STATUS_TABLE`——`job` / `holds_slot` / `priority` / `actions` 都在那一列。
2. 加状态意味着 `take_job`、`finish`、GUI、`is_unfinished`、`is_terminal` 都要跟着改。**能不加就不加**；429 就是刻意没加新状态。

### 10.3 想改限速策略

- 只改 `SubmitGate::try_claim` / `on_rate_limited` / `exponential_backoff`。
- **不要**在 `worker_loop` 里加 `sleep`，**不要**在 `run_submit` 里阻塞等令牌，**不要**在 `lovart_request` 里加第二套闸门。
- 改完确认 I1 / I2 / I9 仍成立。

### 10.4 想恢复「完成一个立刻放一个进来」

- 不要恢复 `finish` 改别人 `ready_at`。
- 正确做法：让 `take_job` 的 `Wait` 感知槽位变化（例如 `finish` 时记一个 `slot_freed_at`，`take_job` 把它算进 `Wait` 的最小值）。
- 但先问自己：在 1s 全局间隔下，这 60s 的延迟真的值得再加一个机制吗？

### 10.5 想加 `Retry-After`

- 需要扩 `HttpResponse`（加 headers）+ `ReqwestTransport` + `UpstreamError`。
- 然后在 `on_rate_limited` 里优先用 `retry_after`，没有再用 `exponential_backoff`。
- 这是 Phase 2，不是本期。

### 10.6 不要做的事（血泪）

- ❌ 不要写 `biz_code.or(http_code)` —— 会让无关的 `code:1` 盖掉 HTTP 429。
- ❌ 不要在 `finish` 里清空所有排队任务的 `ready_at`。
- ❌ 不要在 `run_submit` 里每次调 `set_mode`。
- ❌ 不要把 429 写进 `busy_retries`。
- ❌ 不要把轮询 429 回 `Pending`（会重复生成）。
- ❌ 不要在兜底阶段（`is_final_sweep`）429 时 requeue（会死循环）。
- ❌ 不要在 `worker_loop` 里各睡各的当限速。
- ❌ 不要为「重跑」另写一份重置补丁，用 `reset_for_retry`。
- ❌ 不要在熔断未到期时清零 `breaker_level` / `rate_limit_total_wait`（滞后的成功会抹掉升级）。
- ❌ 不要先 `min(max)` 再 `jitter`（封顶会变成 1.3 倍）。

## 12. 一句话总结给下个 AI

**队列是全局的（`Ctx.queue` 唯一一份），节奏也必须是全局的（`SubmitGate` 唯一一份）。**
**429 停全局，402/409 停单任务；成功补位由完成者自己回队列完成，不靠 `finish` 去改别人的状态。**
**任何「再加一套」的冲动，先回来读 §3 和 §10.6。**
