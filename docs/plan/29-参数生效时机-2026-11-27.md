# 参数生效时机：让「生效值」成为唯一事实 · 施工契约（v4）

> 状态：**待评审**（2026-11-27 · v4 重写）
> 起点：用户问「并发数不能正在跑的时候改吗，还有花积分这些」→「还不能有半态」
> →「从架构角度出发，别一味满足用户要求」→「用结构，不用 ADR」
> 判据：ADR-0004（结构优先）· ADR-0005（一个能力一个入口）· ADR-0001（一处样本）

---

## 0. 上一版（v3）的评估

v3 的事实基础成立，**修法层级错了**：它把「没有半态」当成「把话说对」，于是一整篇在改文案。

| # | v3 的做法 | 问题 |
|---|---|---|
| 1 | §3.1 让 `Workbench::output_dir()` 委托给 `Scheduler::output_dir()` | `ensure_scheduler` 已持有 `scheduler` 槽锁（`workbench.rs:245`），`output_dir()` 会再锁同一把 `std::sync::Mutex` ⇒ **同线程重入死锁**。v3 把它叫「自我引用」，还打算在创建处保留「旧的直接方言」⇒ 又造出第二个来源 |
| 2 | §3.2 / §3.3 改 UI 文案、改 plan/07 §2.7、重写 plan/08 §1.3.8 | 全是文档级。同一批事实已经在 plan/07 与 plan/08 各漂过一次（v3 自己列了 4 条假话）；再写一遍，第三次照样漂。ADR-0004：文档是最弱一级 |
| 3 | 引用 `run_final:1688` | 行号错。1688 在 `handle_poll_error`（`scheduler.rs:1627` 起）里读 `ctx.max_attempts`；`run_final` 是 `1445` |
| 4 | 结论「参数只在重启时生效」 | 结论本身对（F1–F3 已核实），但「生效值」在代码里**不是一个可查询的对象** ⇒ 界面自己编一句「已保存」没有任何东西拦得住。结论靠人守，不是靠结构 |

## 1. 第一性问题（删除测试，每次只删一个）

| 要素 | 删掉后 | 定性 |
|---|---|---|
| 批次参数在进程里**只有一个值** | 看板读环境、报告读 `Ctx`，同一批两个输出目录（今天就这样）⇒ 需求消失 | **第一性** |
| 「生效值」是后端算出来、**类型上必须存在**的数据 | 前端自己拼「已保存」，文档一漂就骗人 ⇒ 需求消失 | **第一性** |
| 运行中改批次参数 | 停批 → 改 → 重启 → 再发，需求仍成立 | 非第一性 → §5 不做 |
| 空闲时重建调度器 | 重启进程也能满足 | 非第一性 → §5 不做 |
| 改 UI 文案 / 改 plan 文字 | 结构保证不骗人后，文案只是表达 | 非第一性 → §5 不做 |
| 凭据热更新、兜底参数逐条生效 | 今天已成立，且各自只有一个入口 | 维持现状 |

两个第一性同时覆盖的最小切片：

> **删掉 `Settings::from_env()`（让「随手读环境」编译不过），批次参数只留 `Workbench` 启动时的一份快照；把「文件值 ≠ 生效值」算成 `get_settings` 返回值里的字段。**

## 2. 已核实的事实

| # | 事实 | 证据 |
|---|---|---|
| F1 | 调度器命中即返回克隆，不再重读设置；生产路径上 `scheduler` 槽只写 `Some`、从不销毁 ⇒ 批次参数 = 进程生命周期 | `workbench.rs:244-251`、`:172`、`:330` |
| F2 | 保存设置只写盘 + `reload_dot_env`，不通知任何消费者 | `gui.rs:1191` |
| F3 | 一条任务只认它开头那份参数 | `run_submit:1188`、`run_recheck:1433`、`handle_poll_error:1688` |
| F4 | **批次参数有第二个读法**：`Workbench::output_dir()` 每次读环境；看板每 3 秒用它，报告用 `Ctx.output_dir` | `workbench.rs:387`、`snapshot.rs:307`、`app.js:498 REFRESH_MS`、`scheduler.rs:700` |
| F5 | **批次参数有第二个写入时点**：`ensure_scheduler` 建调度器时会 `reload_dot_env + from_file`。这只在「进程内第一次投喂」发生 ⇒ 「手改 `.env` 后点开始生效」只在第一次成立，之后不成立 | `workbench.rs:254-256` |

F4 + F5 就是半态的根：同一个 `output_dir` 有两个来源、两个时点。v3 只看到 F4 的一半。

## 3. 形状

### S1 状态形状：一份 `Settings`，一个所有者，一条投影

- `Settings` 只能由 `from_file(path)` 产出。**`from_env()` 删除** ⇒ 想给批次参数开第二个入口，编译不过。
- 唯一所有者是 `Workbench`：新增字段 `effective: RwLock<Arc<Settings>>`，只在 `Workbench::new` 写一次。
- 所有消费者（看板、报告、打开输出文件夹、`SchedulerTuning`、`output_dir()`）都读它；调度器不存在时也读它，不读环境。
- **会红的测试**：改进程环境里的 `LOVART_OUTPUT_DIR` 后，`Workbench::output_dir()` 不变。

### S2 写入形状：保存只写盘，生效点只有一个

- `save_settings`：写 `.env` → `reload_dot_env`（只服务凭据与兜底参数）→ **不碰 `effective`**。
- 批次参数的生效点 = 进程启动（`Workbench::new` 那一次 `from_file`）。
- `ensure_scheduler` 删掉 `reload_dot_env + from_file`，改用 `effective`；**先取快照再拿槽锁**，消除重入死锁。
- **会红的测试**：`ensure_scheduler` 之后 `effective` 仍是同一个 `Arc`（`Arc::ptr_eq`）。

### S3 失败形状：不新增失败类型，只新增一个「差异」字段

- 新增 `Settings::drift(&file, &effective) -> Vec<&'static str>`（键名列表），纯函数。
- `get_settings` 返回 `pendingRestart: [string]` 与 `effective: {…}`。
- 差异由后端算，前端只渲染；前端**不判断**该不该提示。
- **会红的测试**：文件里改 `LOVART_CONCURRENCY` 后 `drift` 恰为 `["LOVART_CONCURRENCY"]`；两份相同时为空。

### S4 两端契约

- `get_settings` 返回形状新增 `effective`、`pendingRestart` 两个字段，其余不变。
- 前端不再有写死的「重启后生效」；提示是否出现，由 `pendingRestart` 是否为空决定。文案里只出现键名（`LOVART_CONCURRENCY`），不翻译 —— 翻译要第二份标签表，那是 ADR-0001 禁止的。
- **会红的测试**：`pendingRestart` 为空时不渲染提示（手工清单一项）。

## 4. 形状与数据链

```
启动：Workbench::new
        ├─ migrate_layout
        ├─ load_dot_env        ← 凭据 / 兜底参数的来源（唯一一次）
        └─ Settings::from_file → effective   ← 批次参数的唯一写入
                 ↓
  看板 / 报告 / 打开输出文件夹 / 建调度器 —— 全读 effective
                 ↓
保存：save_settings
        ├─ update_env_keys（写盘）
        ├─ reload_dot_env → 凭据、兜底参数立即生效（各自只有一个入口）
        └─ effective 不动 → get_settings 算出 pendingRestart
```

谁产生：`from_file`。怎么变形：不变形（`Settings` 已是解析后的快照）。谁消费：看板、报告、调度器、设置页。

## 5. 不做

| 不做 | 理由 |
|---|---|
| 运行中改批次参数（`retune` / 锁内改 `Ctx`） | 一条任务只认开头那份（F3），中途改必然让同一批出现两套参数 |
| 空闲时重建调度器 | `stop_session` 后 `processing` 里还有在飞任务，`is_live()` 真值区间最长约 60 秒（`api.rs:117`）⇒ 判据不可靠，造出更隐蔽的半态 |
| 拆出 `Credentials` 类型（凭据走 `resolve_connection` 读环境 + `reload_dot_env`） | 今天已经是单一入口、无一致性要求、无半态。留着，写进「之后」 |
| 给 `save_settings` 加 `takesEffect` 单值字段 | 只有一种取值 = 增实体；`pendingRestart` 有多值，是事实 |
| 改 UI 文案 / 改 plan/07 §2.7 / 重写 plan/08 §1.3.8 的正文 | 结构保证不骗人后这些是表达；且它们已经漂过一次。只把两处表格删掉，指向 `Settings::drift` |
| 文件监视（手改 `.env` 自动感知） | 新增探针 + 「改到一半被读到」竞态 |

**行为变化（必须让用户裁定）**：F5 的那个隐藏时点消失 —— 「手改 `.env` 后点开始生效」不再成立，统一为「重启程序」。这是消除第二个写入时点的必然代价。

---

## 6. 紧邻的一步 / 之后

- **紧邻**：`pendingRestart` 接进设置页（一次渲染，一个 `if`）。
- **之后**：① 拆 `Credentials` 类型（让凭据也不再读环境）；② 若将来要做运行中改参数，先立「批次生命周期」契约（可靠的结束事件），那是新机制，不混进本轮。

## 8. 验收

### 8.1 决定性

| # | 操作 | 判据 |
|---|---|---|
| D1 | 改并发 → 保存（不重启） | `get_settings.pendingRestart` 含 `LOVART_CONCURRENCY`；跑一批仍是旧并发 |
| D2 | 重启 → 打开设置 | `pendingRestart` 为空；并发是新的 |
| D3 | 改输出目录 → 保存（不重启） | 看板 `outputDir` **仍是旧值**；报告写旧目录；「打开输出文件夹」打开旧目录 —— 三者一致 |
| D4 | 改访问密钥 → 保存（不重启） | 下一条提交能用新密钥（`reload_dot_env` 仍在） |
| D5 | 改兜底模型 → 保存（不重启） | 下一条投喂用新兜底（`PromptDefaults` 仍是逐次读） |

### 8.2 回归

- `make check` 全绿；`scheduler.rs` 一行未动。
- `Workbench::new` 的启动告警仍会报出 `.env` 里的非法值。

### 8.3 反证（必须为红）

- `grep -rn "Settings::from_env" crates src-tauri` 计数为 **0**。
- 把 `output_dir()` 改回读环境 ⇒ S1 的单测必须红。
- 把 `drift()` 改成恒返回空 ⇒ S3 的单测必须红。

## 9. 怎么撤
