## 0. 结论（一句话）

预设从「一段文本」升级为「**文本 + 一组图**」，并且**整套住在工作区**：预设编辑器里有一条跟编辑区
**同一套**的垫图条（拖进去 / 拖排序 / 删）；加图时图落进 `<工作区>/data/presets/`；
清单（`manifest.json`）与图**同目录** ⇒ 拷 exe + 工作区目录，预设完整跟着走；
将来「素材库」也住同一个工作区（§11）⇒ 输入 / 输出 / 预设 / 素材全在一棵树下。

## 1. 第一性问题（删除测试）

| 要素 | 删掉后 | 定性 |
|---|---|---|
| 预设编辑器里的垫图条（拖入 / 排序 / 删） | 「存预设时把垫图也存进去」没有载体 | **第一性** |
| 图**落进预设自己的存储**（不是记一个外部路径） | 预设里没有"存着"图，只有一条会失效的路 | **第一性**（用户追问「存哪」＝ 要它跟着预设走） |
| 取用时把图写回编辑区 | 存进去也拿不出来 | **第一性** |
| 顺序（可拖拽调序） | 图还在，但「图片1 是谁」不可控 —— 顺序**就是**语义（plan 12） | **第一性** |
| **清单与图同域、一起住工作区** | 清单在 `localStorage`（WebView2 用户数据目录 `%LOCALAPPDATA%`）、图在工作区 ⇒ **两处地方**；搬 exe 时「图走、清单不走」⇒ 预设只剩孤儿图；且它是**唯一不在同一棵树下**的东西 | **第一性**（用户原话：「跟着 exe 走的」＋「所有文件都在同一个目录」） |
| 文本里指向某张图的引用（`[img=图片N]` ↔ 芯片） | 预设仍能带图，只是文本点不到名某一张 | 非第一性 → **紧邻**（复用既有函数，成本≈0） |
| 「把当前编辑区一键存为预设」 | —— | **不做**（用户明说「不加，单一入口，单一出口」） |

**五条第一性 ⇒ 最小切片必须同时覆盖**：存得进（图 + 落盘）、取得出（写回编辑区）、顺序可控、**清单与图同域**。

> ⚠️ 核实过的事实（决定 §3.2）：`localStorage` 由 WebView2 存在它的**用户数据目录**，
> 全仓 **0 处**设置 `user_data_folder` / `data_dir` / `app_local_data_dir`
> ⇒ **清单不在 exe 目录、不在工作区**；跟着 exe 走的只有**工作区目录**。

## 3. 形状与数据链

### 3.1 预设清单（形状真源 = **Rust 一处**）

```rust
// crates/lovart-core/src/lovart/preset.rs（新增）
pub struct Preset {
    pub id: String,             // 主键，永不变（名字会重名会改，不能当主键）
    pub name: String,           // 标签，可空
    pub text: String,           // 唯一正文载荷（trim 后）
    pub images: Vec<PresetImage>,
}

pub struct PresetImage {
    pub file: String,           // presets/ 里的**文件名**，不是绝对路径
}
```

- **存储格式的真源在 Rust 一处**（serde）⇒ 前端不再做"解析 / 校验字段类型"那套（plan 13 把它放在 `ui/presets.js`，v2 删掉）；
  前端只剩「调命令 + `displayName` 兜底」。
  ⚠️ 诚实说：跨进程必然还有第二处"**调用形状**"（前端 `create_preset(name,text,images)` 要写字段名），
  它靠**命令参数收窄**（不是塞一个整表对象）来限制漂移面，而不是靠"类型检查"。
- `file` = **工作区 `data/presets/` 里的文件名** ⇒ 清单与图同目录、跟着 exe 走。
- **只存 `file`，不存 `label`**：显示名是**派生**的（派生规则只在**后端一处**：`import` / `resolve` 的返回里带 `label`）。
  - 落盘文件名 = `<原文件名主干>-<内容哈希前 8 位>.<扩展名>`（`data:` 图无原名 ⇒ `图片-<哈希>.png`）
    ⇒ 文件名**可读**（不是纯哈希）⇒ 复制进编辑区后显示的名字也认得出来。
  - ⚠️ 派生规则若在前端再写一份（去掉哈希后缀）⇒ 两处会漂（ADR-0003）⇒ 归后端。
  - ⚠️ 原文件名含 Windows 非法字符（`\ / : * ? " < > |`）⇒ 后端清洗（**正确性**：不清洗就落不了盘）。
- **`PresetImage` 与 `draft.refs` 故意不同形**（`{id,url,label}`）：`id` 是**编辑区会话内**的引用
  （`@` 芯片按 id 指它），跨会话无意义 ⇒ **不能存进预设**。两者是两种东西，形状不同**不是重复**。

### 3.2 存在哪：`<工作区>/data/presets/`（**运行数据根之下**，不是仓库根）

```
<工作区>/data/
  ├─ .env                 ← 凭据（plan 19 迁移后在这）
  ├─ inbox/               ← 提示词输入
  ├─ presets/             ← 本能力：预设清单 + 图
  │    ├─ manifest.json
  │    └─ <原名>-<hash8>.ext
  ├─ output/              ← 出图
  └─ var/                 ← 机器状态（state.jsonl / run.log / refs/ …）
```

**判据由 `docs/plan/19-目录归属与访问器收口-2026-11-26.md` 统一给出**（最终落 `AGENTS.md §2`）：
**「运行数据全部在 `data/` 下，按用途分子目录；源码与打包输入不进 `data/`」**。
本节只消费其中一行：`data/presets/`（用户资产；二进制 ⇒ 不进 git）。

1. **跟着 exe 走**：`data/` 在工作区里 ⇒ 拷 exe + 工作区目录 = 预设（清单 + 图）完整。
2. **清单与图同域** ⇒ 一份事实只放一处（清单若留 `localStorage`，就是「清单在 `%LOCALAPPDATA%`、图在工作区」两处）。
3. **和素材库、出图、提示词在同一个根下** ⇒ 用户要的「所有文件都在同一个目录」成立；
   备份 = `Compress-Archive .\data\*` 一条命令全带走。
4. **不再需要单独的 `.gitignore` 行**（`data/` 一行由 plan 19 加，覆盖 `presets/`）。

> 将来「素材库」= `data/library/`（§11），与 `data/presets/` 同级、互不嵌套。

### 3.3 数据链（谁产生 → 怎么变形 → 谁消费）

⚠️ **命令拆细，前端不持有整表**：真相只有后端 `manifest.json` 一份；前端只调"一个动作一个命令"，
不构造整表、不做"整表写回"（否则前端缓存立刻变成第二个真相 + 多一个"谁赢"的问题）。

```
启动 / 打开面板
  → invoke('get_presets') → { presets, fresh }
        presets：清单（有 manifest 就按它；没有就是空）
        fresh：这个工作区**从未建过 manifest** ⇒ 前端可尝试从 localStorage 迁移（§3.5）
  → 面板用返回的列表渲染（**不缓存整表**；每次打开面板拉一次）

面板里拖入本机文件 / 用「+」选文件
  → invoke('import_preset_images', [路径或 data: URL])
        → 后端 materialize（复制 / 解码）进 presets/ ⇒ 可读文件名（原名主干-哈希8位.ext）
        → 返回 [{file, path, label}]（保序、同长）
  → 面板本地态 presetEditor.images（只在内存）
  → 点「保存」⇒ 一个命令：
        invoke('create_preset', { name, text, images })   // 新建
        invoke('update_preset', { id, name, text, images })  // 修改
        → 后端读-改-写 + **原子写** manifest.json（照抄 `engine/state.rs` 的 tmp+rename）
        → 返回 { ok } / { ok:false, reason }（reason 由 `app.js` 的 `presetMessage` 翻译）

取用：点列表一行 ⇒ applyPreset(preset)
  → invoke('get_presets') **重读**（列表是快照：取用时可能已被删/改）
        → 按 id 取最新那条 `latest`；取不到 ⇒ 提示且**面板不关**（plan 13 口径）
  → invoke('resolve_preset_images', latest.images.map(i => i.file))
        → [{file, path, label}] —— **只拼路径、不判存在**（用户裁定 2026-11-26）：
          文件被删 ⇒ 前端 `<img>` 加载失败显示破图，用户自己看得见、自己处理；
          省掉 missing 判定与前端分支（plan 17「不许静默丢图」在这里由**破图**满足，不是由提示满足）
  → **复用 applyDraft**（唯一「换一批内容」入口）：
        applyDraft({ prompt: latest.text, refs: paths })
        · refs 仍是**字符串数组**（既有形状不变 ⇒ 既有调用点零迁移）
        · applyDraft 的入参**键缺失 = 不动** ⇒ 预设不传 model/ratio/size ⇒ **参数保持不变**
  → 关面板
```

**六条命令，一个动作一条**：`get_presets` · `create_preset` · `update_preset` · `remove_preset` ·
`import_preset_images` · `resolve_preset_images`。

- **写编辑区只有一条路**：取用预设**不自己写** `draft.refs` / `renderRefs` / `inflatePromptChips` / `writePrompt`
  —— 那些全在 `applyDraft` 里（ADR-0005：同一能力一个入口；否则「写编辑区」立刻变两条路）。
- **覆盖不提示**（用户已定）：`applyDraft` 内部 `draft.refs = []` ⇒ 编辑区原有垫图被清空，不弹窗。
  ⚠️ **无图预设不动编辑区的图**（本裁定 2026-11-26）：`images` 为空 ⇒ **不传 `refs` 键**
  ⇒ `applyDraft` 的「键缺失 = 不动」自然生效（`applyDraft({ prompt })`）。
  「这条预设没有图」≠「把编辑区的图清空」—— 后者会静默丢掉人正在垫的图。
  ⇒ 有图才替换、无图就不动，**仍是同一条路**（同一个 `applyDraft`，只是传不传 `refs` 键）。
- **id 不复用**：`applyDraft` 内部经 `addRefs` → `pushRef` 分配新 `ref-${++refSeq}` ⇒ 与编辑区既有 id 空间不冲突，
  且 `inflatePromptChips` 生成的 token 自动对上（**不需要 id 重映射表**）。
- **缺失的图**：路径照样传 ⇒ `<img>` 显示**破图**，不提示、面板照关（用户裁定 2026-11-26：最简单，别增加复杂度）。
- 预设文本里手写的 `@{id:label}` token 取用时没有对应垫图 ⇒ **按文字原样保留**（既有语义，不吞掉）。

### 3.4 文本里怎么点名某张图

- 唯一格式：`[img=图片N]`（既有、可序列化、`applyDraft` 已在用）。
- 面板的垫图条显示**序号角标**（同编辑区 `.ref-num`）⇒ 用户知道「图片1」是谁。
- 取用时由 `applyDraft` 内部的 `inflatePromptChips(text, draft.refs)` 把它变回芯片（**零新格式**）。

### 3.5 一次性迁移（localStorage → manifest.json）

| 情形 | 行为 |
|---|---|
| 有 `manifest.json` | 用它（**localStorage 一概不读**，它只是历史）；`fresh = false` |
| 无 `manifest.json` + 有 localStorage v2 | `fresh = true` ⇒ 前端读出 v2 的预设 ⇒ `create_preset` 逐条写入（**一次性**） |
| 无 `manifest.json` + 无 localStorage | 空清单 ⇒ 写一个空 `manifest.json`（此后不再问 localStorage） |
| `manifest.json` 坏了（JSON 解析失败） | 回退**空清单** + 一条告警（**不许崩**）；⚠️ 不覆盖原文件（留证据），只在下一次成功写入时替换 |

- **握手**：`get_presets` 返回 `fresh`（= 这个工作区还没建过 manifest）⇒ 前端**只看这个位**决定要不要迁移，
  不自己猜"空清单是不是等于没迁过"（迁移完 `create_preset` 会写出 manifest ⇒ 下次 `fresh = false`）。

- **不删 localStorage**（用户数据不擅自销毁，同 plan 13 保留 v1 的先例）⇒ 它**不再是真相**，只是历史。
- ⚠️ 迁移是**复制**不是移动 ⇒ 另一个工作区也会各得一份（用户只有一个工作区 ⇒ 无感）。

## 4. 紧邻的一步（同批做，因为它就是用户裁定的「抽公共组件」）

### 4.1 抽的是**垫图条**，不是整个编辑区

用户原话：「你完全可以把编辑区抽成公共组件」/「那如果整个抽公共组件会不会更好呢？」

**结论：不整个抽；抽垫图条（refs strip）。** 依据 ADR-0002 事前四问：

| 问 | 答 |
|---|---|
| 1 调用方现在必须知道什么？ | 两处都要：怎么显示一张垫图、怎么按序号排、怎么删、怎么拖拽排序 |
| 2 抽出来后少知道哪几条？ | 两处都不用再知道「角标怎么算 / 拖拽落点怎么定 / 删键怎么防误触」 |
| 3 旧写法能不能全删干净？ | **能** ⇒ 旧 `renderRefs` / `placeRefNode` / `commitRefOrder` 同批删（不留第二份） |
| 4 这些概念会不会**一起变**？ | **垫图条会**（顺序语义一改，两边都得改）⇒ 真模块；**文本容器不会**（见下） |

**为什么整个编辑区不行**：

- 编辑区的文本容器是 `contentEditable` + 芯片（`promptChips.js`）+ `@` 弹层（`promptMention.js`）
  + 占位符 + 「发送」可用性判定（`isComposerClean` / `syncComposerState`）；
  预设编辑器的文本是**纯 textarea**（存字符串、存 `[img=图片N]`，不存芯片）。
  ⇒ 一个组件住两种文本容器 + 一堆预设侧**一个都用不到**的分支 ⇒ 判据 4 不过 ⇒ **是壳不是模块**
  （ADR-0002 反例明写：「抽出来必须靠泛型 + 字符串字段名才能通用 ⇒ 是壳」）。
- 改动面也不成比例：整个编辑区抽组件要动 `writePrompt` / `serializeDOM` / `resolvePromptChips` /
  `inflatePromptChips` / mentions / 占位符 / `applyDraft` / `applyPreset` / `publish` 全套行为；
  而本轮只需要「预设里也能放图」。

### 4.2 组件形状

```
ui/refStrip.js  →  window.RefStrip
  render(box, refs, { onRemove(ref), onReorder(refs) })   // 纯 DOM；不持状态；不写 draft
  startPointerDrag(event, handlers)                        // 指针手势骨架（编辑区排序与看板拖图共用）
```

- `refs` 形状两边一致：`{id, url, label}`（编辑区 = `draft.refs`；预设面板 = `presetEditor.images`）。
- **组件不拥有数据**：删 / 排完把结果**回交**调用方 —— 编辑区写回 `draft.refs`，预设面板写回 `presetEditor.images`。
- **「+」按钮不归组件**：它接的是**各自的**文件选择 input（编辑区 `#refPicker` / 预设 `#presetRefPicker`）
  ⇒ 组件若自带「+」就会硬编一个 input（一条线）。**组件只渲染缩略图**，「+」由调用方放在容器里。
- **组件不做业务校验**：找不到 id 这类事**回交**调用方处理（现在 `commitRefOrder` 直接 `throw`，
  在 DOM 事件里抛会变成未捕获异常）⇒ 组件只负责「显示 + 排序交互」。
- `placeRefNode` 现在硬编码 `$('refs')` ⇒ **参数化**（`box`）。
- `startPointerDrag` 一并搬进 `refStrip.js`（它无 app 状态耦合；`startRefPull` 也用它 ⇒ 同一手势不许两份）。

### 4.3 两个调用点

| 调用点 | 数据 | 删除时 | 排序时 |
|---|---|---|---|
| 编辑区 `#refs` | `draft.refs` | 删 `draft.refs` 那条 + `removeChipsById` + `renderMentions` | 写回 `draft.refs` 新序 + `renderMentions` |
| 预设编辑器 `#presetRefs`（新容器） | `presetEditor.images` | 删本地那条 | 写回本地新序 |

### 4.4 顺带（同批，不做会静默出错）

- **拖放分流**：`wireDropZone`（`ui/app.js:2380`）的 `onDragDropEvent` 是**窗口级**的 ⇒
  预设面板开着时拖文件进窗口，图会落进**下面的编辑区**。必须改：面板处于编辑器态 ⇒ 图进面板的图区。
  ⚠️ 判据只有一处（`presetEditor` 非空 ⇒ 进面板）⇒ **一条路**，不是"两套 drop 处理"。
- **文件选择**：预设面板用**自己的** `#presetRefPicker`（不与编辑区 `#refPicker` 共用 —— 两个入口抢一个 input 就是两条线）。
  ⚠️ 但**读文件的代码只许一份**：`FileReader` → `data:` 那段（`ui/app.js:3422`）抽成一个共用函数，
  两个 input 都调它（**两个 input ≠ 两份读取逻辑**）。
- **加图即落盘**：`import_preset_images` 在加图那一刻就把文件落进 `data/presets/` ⇒
  「本机路径」与「data: URL」**只有一条路**（后端各自 materialize），前端不分叉。
  代价：取消编辑会留下**没被任何预设引用的文件**（见 §10 风险；本轮不做 GC）。
- **原子写清单**：写 `.tmp` → `fs::rename` 覆盖（**照抄** `engine/state.rs:977-983`，本仓已在 Windows 上天天这么写 `state.jsonl`）。
  ⚠️ **本轮不抽共用**（裁定 2026-11-26）：`state.rs` 是全仓最要紧的写盘路径（任务真相），
  为 5 行去动它是**弊大于利** ⇒ 预设清单**照抄那 5 行 + 注释指 `state.rs:977` 当范本**（ADR-0006：有唯一范本可照抄即合格）。
  ⚠️ 不需要"先删旧"、不需要 `.tmp` 恢复兜底（那是把 Windows 的 `rename` 想错了）。

### 11.1 它在本轮架构里的位置（不猜它的库是谁的）

- **素材库 = `<工作区>/data/library/`**（与 `data/presets/` `data/inbox/` `data/output/` 同级，
  不嵌在 `data/presets/` 里；⚠️ 仓库里已有 `packaging/`（打包输入）⇒ 不占用它）。
  目录名本轮**只定名不建目录**；`.gitignore` **不需要新增行**（`data/` 一行已覆盖）。
- 用户给的 `G:\品牌更新.library\images\<id>.info\{metadata.json, 原图}` 是**外部**目录：
  它长得很像某个图库软件导出的库（目录形如 `images/<一串ID>.info/` + `metadata.json`
  + 原图；`metadata.json` 的字段是 `id/name/size/btime/mtime/ext/tags/folders/isDeleted/url/
  annotation/modificationTime/noThumbnail/width/height/palettes`）——
  ⚠️ **但「它是哪个软件的库」本轮不断言**：那是素材库 plan 的第一性问题，由用户裁定。
  **本轮不写任何针对外部图库软件的读写代码**（那会引入索引 / 导入机制 / 说谎风险）。

### 11.2 本轮预埋的底座（架构级，plan 18 顺带做好）

| # | 预埋 | 为什么素材库 plan 不用重写 |

| 1 | **垫图条公共组件** `RefStrip`（§4.2） | 素材库「点图 → 进编辑区垫图」最终调 `pushRef`（**唯一加图入口**）⇒ 不新写第二条加图路 |

### 11.3 明确**不预埋**（留给素材库 plan 决定）

素材库面板 UI（按钮位置 / 网格 / 滚动 / 缩略图）· 素材库目录名与是否可配 ·
**「发送到素材库」的语义**（复制过去 / 移动过去 / 同名怎么办）· 是否记录来源与时间 ·
搜索 / 标签 / 分组 · 是否做索引文件（还是每次扫目录）· 外部图库软件（如那个 `*.library`）的读写 —— 一律**后置**。

### 11.4 素材库 plan 的第一性问题（开工前必须先答）

> **「素材库」是本工具自己的一个图片目录，还是某个外部图库软件（用户给的那个 `*.library`）的库？**

- 若是**本工具自己的目录** ⇒ 完全可控（扫目录即列表），但与外部库里的图不互通。
- 若是**外部库** ⇒ 「发过去」必须让那个软件**认得**（索引 / 导入机制）⇒ 否则「写进去了但那边不显示」=
  **界面说谎**（AGENTS：失败必须上报不许静默、界面不许说谎）。

⚠️ 这个答案决定素材库 plan 的工作量级别（一个目录 vs 一套导入机制），
但**不影响 plan 18** —— plan 18 只交付上面 11.2 的五条底座。
